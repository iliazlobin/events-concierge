# ADR-007: DB-anchored lifecycle state machine with Temporal as the durable executor

**Status:** accepted — with owner-ratification riders (see Consequences) · **Date:** 2026-07-10

## Context

The per-(user, event) lifecycle needs exactly one source of truth, and three binding requirements discriminate where it can live. FR-8.9 and NFR-8 name the transactional outbox the system of record for lifecycle events, and an outbox row can only be atomic with the state it announces if that state is a Postgres row — Temporal history and Postgres cannot share a commit. FR-10.5 and NFR-11 require erasing lifecycle/event history within ≤72h, which is impossible against immutable Temporal histories but trivial against rows. And the system already commits to one durable workflow per `{user_id}:{canonical_event_id}` with reject-duplicate reuse (FR-8.1, AC-55), so the lifecycle store must compose with — not compete against — that execution spine.

- **Atomicity:** FR-8.9/AC-63 — every lifecycle event lands in the outbox in the same transaction as the state it describes; forced redelivery must converge idempotently.
- **Erasure:** FR-10.5/AC-74/NFR-11 — lifecycle/event history is erasable ≤72h via crypto-shred of PII fields, retaining non-PII operational fields (reconciled with NFR-10 immutable audit).
- **Tenancy:** FR-1.3 — FORCE RLS, non-owner role, `SET LOCAL` tenant context, tenant_id leading index.
- **Latency:** NFR-2(b) — handoff task available p95 ≤ 60s, user notified p95 ≤ 120s from routing decision, measured at delivery, not enqueue.
- **Terminality:** AC-46 — an ignored handoff task past TTL reaches `expired`, closes its workflow, and notifies the user; terminal states are completed/cancelled/expired/failed_no_candidate.
- **Detection economics (adjacent constraint):** NFR-17 ≤6h reconcile and the Meetup quota ambiguity (gate G2, per-token sharding unconfirmed) penalize any design that multiplies polls per watching user.

## Options considered

1. **Temporal workflow state as source of truth; Postgres tables as disposable projections.** Rejected on three binding failures. FR-10.5/NFR-11 erasure ≤72h is impossible against immutable Temporal Cloud histories — the only escapes (retention <72h, or keeping all PII in Postgres claim-checks) either cripple operations or hollow out the single-SoT claim, since the readable truth ends up in rows anyway. NFR-8 names the outbox the system of record, which this option must explicitly reinterpret — an exception the chosen design does not need. And its in-workflow 6h poll loops cost ~96M Temporal actions/month at 200k watched events by its own arithmetic, duplicating fetches N-watchers-fold per popular event against an unconfirmed Meetup quota; its own documented contingency fallback is the central poller, so we decide that now rather than pay to migrate later. Secondary costs: ops reads become eventually-consistent projections whose authoritative fallback (workflow Query) fails on closed workflows, and lifecycle-schema changes become workflow-versioning discipline instead of a migration.

2. **Append-only event-sourced LifecycleLog as source of truth (the log IS the outbox); all subsystems as idempotent log consumers.** Architecturally sound, but the log-as-SoT buys nothing the requirements do not already provide more cheaply: FR-7.3/NFR-10 auditability comes from the outbox-fed immutable audit log, NFR-13 rebuildability from backups plus outbox replay, AC-63 convergence from idempotent consumers — all present in the chosen design. What it costs is a standing discipline tax: append-before-act bracketing, single-writer grant enforcement, snapshot-xip offset cursors, CI rebuild-equivalence fixtures, and a second replay semantic (fold-the-stream) coexisting with Temporal's own history replay — two representations of lifecycle state is exactly the drift class this decision exists to eliminate. Current-state reads still require projections, converging on the chosen design's tables plus extra machinery. Its canonical-event detection keying, conservative matching posture, lane tagging, and nightly invariant query are grafted into the decision.

3. **Postgres lifecycle table as source of truth; Temporal workflows as durable executors (chosen).** State is queryable, erasable, and renderable without history replay; the FR-8.9 outbox transaction is structurally satisfied because state, ledger, and outbox share one commit. One within-option element was rejected: per-watching-user Meetup poll batching, which duplicates fetches for popular events and under the G2 per-app-quota worst case scales with user-event pairs — replaced by canonical-event-keyed dedup (one status check per distinct watched event per cycle, round-robin across watchers' tokens through the FR-10.4 fair-share scheduler).

## Decision

We will anchor the per-(user, event) lifecycle in a Postgres `lifecycle` table and use the settled Temporal workflow per `{user_id}:{canonical_event_id}` as the durable executor and sole transition driver.

- **Lifecycle Store.** `lifecycle` (tenant_id, canonical_event_id, workflow_id, state enum found|handoff|awaiting_confirmation|registered|scheduled|reconciled|withdrawing plus terminals completed|cancelled|expired|failed_no_candidate, conflict_warning flag, lane tag) under FORCE RLS with tenant_id leading index (FR-1.3). A partial unique index enforces exactly ONE non-terminal row per (tenant_id, canonical_event_id), paired with the engine-level reject-duplicate workflowId (FR-8.1/AC-55).
- **One guarded transition function.** Every transition executes through `fn_transition(lifecycle_id, expected_from, to, transition_id, payload)`, which in ONE transaction performs: a guarded UPDATE that raises on an illegal from-state; a transition-ledger INSERT with UNIQUE(transition_id) checked BEFORE the guarded update, so activity retries no-op; and an outbox INSERT (FR-8.9/AC-63). DB grants deny lifecycle writes to every role except the workflow-activity path and the sweeper repair path.
- **Temporal as executor.** The workflow mints all transition_ids and idempotency keys once in workflow state (FR-8.3); owns all durable timers — handoff TTL = min(7 days, event start), reminders at T+24h and T+5d, confirmation wait 24h, park-to-event_end+24h before terminal completed; receives all signals (handoff_completed, organizer_change deduped on change fingerprint, un_rsvp, kill_switch); and advances state only through fn_transition inside activities. Every path ends in exactly one terminal fn_transition which, in the same activity, cancels open handoff tasks, removes watch-registry interest, and releases timers. TTL expiry performs a final drain-check for a buffered completion signal before committing terminal `expired`; if present, completion wins.
- **Erasure.** FR-10.5 is a row-level crypto-shred of PII columns retaining non-PII operational fields (idempotency key, policy decision, workflow ID per NFR-10); Temporal histories carry only claim-check keys and non-PII state (FR-2.6/FR-8.5) and age out on retention.
- **Safety net, never authority.** A 15-minute sweeper (5-minute grace) repairs orphans only — tasks past ttl_expires_at with a dead workflow, lifecycle rows with no live execution, event_change rows whose fanout found no live workflow — through the same fn_transition and idempotent CalendarPort calls, emitting a divergence metric. A nightly invariant query proves zero non-terminal rows with closed workflows and zero watch rows for terminal rows.
- **Launch parameters.** Handoff TTL min(7d, event start); reminders T+24h/T+5d; notification retry 5 attempts over ~43 minutes; SLA alerts at p95 > 45s task-available and p95 > 90s user-notified (headroom inside the 60s/120s NFR-2(b) budgets); sweeper 15min + 5min grace; detection cadence 3h against the ≤6h NFR-17 bound.

Invariants: (1) every transition = exactly one fn_transition commit, workflow-minted transition_id, retries no-op; (2) exactly one non-terminal row per (tenant, event) ↔ exactly one open workflow; (3) state written only through fn_transition from workflow activities or the sweeper; (4) every workflow ends in exactly one terminal state whose transition releases all resources.

## Consequences

**Easier.** Lifecycle state is queryable by ops dashboards and the future UI without history replay; erasure is a row operation with a fixed ≤72h path; the FR-8.9 outbox atomicity claim is structurally true rather than argued; the worker-crash dual-write window (Postgres committed, Temporal ack lost) is closed by ledger idempotence — the retry no-ops and the workflow proceeds (AC-56/AC-63 pattern); schema evolution is a migration, not workflow versioning; detection cost scales with distinct watched events, not user-event pairs.

**Harder / risks accepted.** Two systems must be kept convergent: divergence between committed transitions and workflow progress is idempotence-closed but must be OBSERVED — we commit to alerting on ledger rows without matching workflow progress beyond N minutes, or the sweeper silently becomes load-bearing instead of a safety net. fn_transition is a single choke point: every new transition is a plpgsql change with its own test surface. The DB is on the critical path of every state change, so lifecycle writes inherit Postgres availability. Reopen after a terminal requires new workflow attempts rather than resuming closed histories.

**Follow-ups committed.** Wire the divergence alert and the nightly invariant query into paging; instrument the sweeper divergence metric with an alarm at sustained nonzero; land crash-injection fixtures asserting fn_transition retry no-ops (NFR-8 measurement); resolve gate G2 (Meetup quota scoping) which sizes the detection side this store feeds.

**Owner-ratification riders:**
- OWNER RATIFY — conflict-at-completion semantics (AC-43/FR-6.3): the decided behavior surfaces the conflict warning AND still advances the lifecycle to `registered` and writes the calendar entry, because the user factually holds the registration. If the owner intends a conflict to BLOCK the calendar write, it is a one-activity change — but it must be settled now.
- OWNER RATIFY — reopen-after-terminal: re-requests after expired/cancelled terminals start a NEW workflow with attempt-suffixed workflowId `{user}:{event}:r{n}` under the single-non-terminal-row guard, as a clarification of FR-8.1's reject-duplicate key; a closed history is never mutated.
- OWNER RATIFY — handoff TTL = 7 days capped at event start (min(7d, event_start)) with reminder cadence T+24h and T+5d; these are the O-9 staffing/escalation tuning knobs and feed the NFR-2 handoff-lane target.
