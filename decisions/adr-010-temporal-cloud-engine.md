# ADR-010: Temporal Cloud as the durable-execution engine (DBOS documented fallback) - sizing and outage posture

**Status:** accepted — with owner-ratification riders (see Consequences) · **Date:** 2026-07-10

## Context

The engine choice was settled at requirements time: FR-8.1 mandates one durable workflow per `(user_id, canonical_event_id)` on an external durable-execution engine — **Temporal Cloud primary, DBOS documented fallback** — with `workflowId = {user_id}:{canonical_event_id}` and a reject-duplicate reuse policy as the engine-level idempotency key. This ADR does not relitigate the vendor; per O-6 it ratifies the choice and parameterizes it — sizing against the load basis, payload posture, cost basis, and the outage posture — and records what would trigger the DBOS fallback. What the engine must carry is crash-critical by construction: the FR-5.0 attempt counter and start-child-then-record window, months of durable lifecycle waits, and the intake guarantee that a request "starts exactly one durable workflow" (FR-6.8/AC-48).

- FR-8.1 / AC-55: reject-duplicate workflowId — two starts of the same `{user}:{event}` yield exactly one execution. FR-8.4 / AC-57: confirmation waits as durable timer + signal holding no worker. FR-8.5 / AC-58: claim-check over the engine's 2 MB payload limit. AC-56 / NFR-8: crash injection replays no completed side effect — exactly-once observable effects.
- Load basis: 750 req/min Friday peak → ~390 child starts/min (0.4 conversion × 1.3 attempts), worst-case ~1,600 engine transitions/s, ~240k open lifecycle children, browser pool ~135.
- Availability and recovery bind the posture: NFR-3 (99.9% monthly), NFR-13 (RPO ≤ 60 s, projections rebuildable from engine history + outbox), NFR-2 (handoff-task p95 ≤ 60 s), NFR-15 (fail-safe to handoff).
- Cost binds materiality arguments: NFR-5 per-lane bounds (API ≤ $0.12, browser ≤ $0.40, blended ≤ $0.20 per confirmed RSVP) set the ~$104k/mo envelope at 100k users against which engine action costs are weighed.
- Gate O-6: sizing/limits confirmation at contract — multi-tenant SLA and the 2 MB payload constraint must hold; fall back to DBOS only if they fail.

## Options considered

1. **Temporal Cloud as the single durable spine (chosen).** Engine journaling eliminates the entire hand-rolled crash-state class — the attempt counter, the start-child window, the ack-lost retry seams — that every alternative must protect by hand; the requirements settled Temporal as the spine precisely to avoid that class. Load verifies with roughly an order of magnitude of headroom: worst-case ~1,600 transitions/s at the Friday peak against engine ceilings in the tens of thousands per second, and ~240k open lifecycle children consume zero worker resources during durable waits. The claim-check codec keeps every payload with hard margin under the 2 MB payload / 4 MB gRPC limits.

2. **DBOS as primary (rather than documented fallback).** Not adopted as primary because the requirements pinned Temporal Cloud first (FR-8.1, `d13`) and nothing in the verified analysis dislodged it; DBOS is retained as the contingency the shape was deliberately designed to port to — the two-tier parent/child topology maps to two DBOS workflow functions — activated only if O-6 contract review shows the Temporal Cloud SLA, namespace throughput, or cost basis failing their thresholds. Keeping the fallback documented (not built) avoids paying for two engines at v1.

3. **Hand-rolled durability over Postgres (stateless coordinator + request-state row + outbox), engine scoped down or out.** Rejected because the crash-critical state it must protect requires bespoke SELECT FOR UPDATE, outbox redelivery, and crash-injection CI — work engine journaling gives for free — while the quantified savings are immaterial: the ~2–3× lower engine action volume is roughly a low-$1k/mo delta against the ~$104k/mo NFR-5 envelope, and the versioning-hostile surface it protects is the hours-lived parent, whereas the months-lived versioned surface (the child lifecycle) is identical in both designs. It also trades the FR-6.8/AC-48 letter.

4. **Maximal engine usage — Temporal-native pacing via per-(source,credential) entity RateLimiterWorkflows.** Rejected as over-reliance on the engine: it puts an engine Update round-trip (~50–200 ms plus a billed action) in front of every source call and sprawls to ~100k long-lived entity workflows, buying durability that pacing does not need — rate limiting is politeness, not correctness, and its fail-safe direction on state loss is throttle-first re-initialization, which a Redis bucket does trivially. Pacing therefore stays off-engine, bounding parent-tier action volume.

5. **A second non-Temporal handoff path to cover engine outages.** Rejected deliberately: building an independent handoff-creation path solely for the outage window adds a parallel execution substrate, its own failure modes, and standing ops surface to close a gap that is bounded by the engine's SLA. Instead the outage posture is declared, bounded, and put to the owner for ratification (see Consequences).

## Decision

We will run Temporal Cloud as the sole durable-execution engine for the two-tier topology ratified in ADR-003: the parent EventRequestWorkflow (`workflowId = req:{tenant}:{request_id}`, closes within hours) and the per-`(user_id, canonical_event_id)` child RegistrationWorkflow (`workflowId = {user_id}:{canonical_event_id}`, WorkflowIdReusePolicy=REJECT_DUPLICATE, ParentClosePolicy=ABANDON) — the workflowId is the engine-level idempotency key (FR-8.1, AC-55).

We will size against the declared load basis and treat it as a contract input, not an assumption: 750 req/min peak → ~390 child starts/min → worst-case ~1,600 engine transitions/s, verified at O-6 against namespace throughput limits; ~240k open lifecycle children hold zero worker resources in durable waits (24 h confirmation timer, 7 d handoff TTL, months-long lifecycle), so open-execution count is a history-retention and versioning concern, not a capacity one.

We will run a claim-check Payload Codec on every worker, auto-offloading payloads >256 KB to object storage with per-tenant prefixes (FR-8.5); the 100–200-candidate ranked set (~400–800 KB), screenshots, and raw DOM always offload, keeping hard margin under the 2 MB payload / 4 MB gRPC limits (AC-58).

We will make intake loss-proof against engine unavailability with the Postgres start-outbox: the gateway commits a tiny outbox row, then calls StartWorkflow reject-duplicate, so a Temporal Cloud blip never loses an inbound request and replayed starts are dedup-safe (AC-48). We accept the declared outage posture: during an engine outage, in-flight state resumes losslessly on recovery (NFR-13) and buffered starts replay, but no NEW handoff task can be created for the window — a bounded NFR-2/NFR-15 exception accepted over building a second non-Temporal handoff path.

We will keep the shape portable to DBOS as the documented fallback: parent and child become two DBOS workflow functions, preserving the reject-duplicate idempotency contract, the claim-check discipline, and the saga/lane structure — the fallback is exercised only if O-6 contract review fails on SLA, throughput, payload, or cost.

Launch parameters bound to the engine: claim-check threshold 256 KB; mutating activities (create_rsvp, browser_submit) RetryPolicy maximumAttempts=1 with all retries as explicit workflow loops re-entering through read_rsvp_state/browser_detect; browser task-queue ScheduleToStartTimeout 120 s (saturation ⇒ handoff, AC-45); children continue-as-new after reconcile bursts to bound history growth.

## Consequences

**Easier:** the crash-critical state class disappears into engine journaling — AC-56 crash injection becomes a replay property, not bespoke CI; AC-48/AC-55 are satisfied by workflowId construction alone; durable waits at every horizon (hours, days, months) cost zero worker resources; NFR-13 recoverability inherits the engine's history as execution truth with Postgres as a rebuildable projection; the DBOS port stays cheap because the topology was chosen to be two workflow functions in either engine.

**Harder / risks accepted:** Temporal Cloud is a correlated failure domain for BOTH lanes — the autonomous path and handoff-task creation share the engine, so an outage stalls new handoffs for its window (the bounded NFR-2/NFR-15 exception). Workflow patch-versioning is a standing operational competency: the LaneRouter and child saga/lifecycle logic are replayed code across ~240k open executions, and a sloppy patch is a non-determinism incident — mitigated by pushing volatility into policy data and keeping decision functions stable, but never eliminated. Child history bloat from chatty pollers is bounded by signal coalescing and continue-as-new, and must be load-tested rather than assumed. Engine action cost rides on a non-dossier list price and must be re-verified before any "parent actions are immaterial" reasoning is reused. Follow-ups committed: O-6 contract review executes the sizing/limits confirmation with DBOS as the fallback trigger; the outage posture is drilled (start-outbox replay + lossless resume) as part of the NFR-13 restore drill.

**Owner-ratification riders:**
- OWNER RATIFY: the outage posture — accept a bounded handoff-creation gap during an engine outage (no new handoff task for the window; intake buffers in the start-outbox, in-flight state resumes losslessly) rather than build a second non-Temporal handoff path — a declared, bounded NFR-2/NFR-15 exception.
- O-6 contract checks: Temporal Cloud SLA ≥ 99.9% (NFR-3) and namespace throughput ≥ ~1,600 transitions/s peak, and the ~$25/M-actions cost basis (→ ~$1.6–2.5k/mo at 100k users) — these are external list figures NOT dossier-backed; verify at contract before treating parent-workflow action volume as immaterial, and fall back to DBOS only if they fail.
