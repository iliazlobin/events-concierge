# ADR-003: Two-tier Temporal orchestration: parent EventRequest workflow + per-(user,event) child sagas

**Status:** accepted — with owner-ratification riders (see Consequences) · **Date:** 2026-07-10

## Context

The system must reconcile two orchestration obligations that live at different granularities: FR-5.0 mandates a request-level attempt loop (select the top-ranked candidate, fall through on failure, ≤3 attempts, terminal handoff or `failed_no_candidate`), while FR-8.1 mandates one durable workflow per `(user_id, canonical_event_id)` with `workflowId = {user_id}:{canonical_event_id}` and a reject-duplicate reuse policy on Temporal Cloud (DBOS documented fallback, O-6). The structural tension is that the FR-8.1 workflowId cannot exist before discovery mints `canonical_event_id`, so the FR-5.0 loop — and FR-8.2's discover→rank→select prefix — must be owned by some durable structure above the per-event workflow. Whatever owns it holds crash-critical state (the attempt counter, the start-child-then-record window) and must satisfy FR-6.8/AC-48's letter that intake "starts exactly one durable workflow."

- FR-8.2 saga steps as journaled activities with compensation; FR-8.3 idempotency keys minted once in workflow state; FR-8.4 confirmation as durable timer + signal (AC-57: no worker held); FR-8.5 claim-check over the 2 MB engine payload limit (AC-58).
- AC-55 (reject-duplicate: two starts of the same `{user}:{event}` yield one execution); AC-56 (crash injection replays no completed side effect); AC-32 (autonomous lanes exhausted before handoff is chosen — lane ordering is within-candidate).
- FR-5.9/FR-7.2/AC-40/AC-50 (policy gate + kill-switch freeze with no deploy) and NFR-15 (fail-safe to handoff) bind the mutation boundary; FR-10.4/AC-73 and gate G2 bind pacing; NFR-2 fixes handoff-task p95 ≤ 60 s and defers the autonomous-lane SLA to G1/G2.
- Load envelope: 750 req/min Friday peak → ~390 child starts/min, worst-case ~1,600 engine transitions/s (well under Temporal's tens-of-thousands/s), ~240k open lifecycle children holding zero worker resources during durable waits.

## Options considered

1. **Two-tier Temporal spine (chosen):** a short-lived parent EventRequestWorkflow owns parse→discover→rank→conflict-gate and the FR-5.0 loop; per-(user,event) child RegistrationWorkflows own the FR-8.1 saga and months-long lifecycle. Selected because the parent is the lowest-risk owner of the crash-critical request state: engine journaling eliminates the hand-rolled protection every alternative needs, it satisfies FR-6.8/AC-48's letter, and the engine-load and versioning objections dissolve on inspection — the parent closes within hours so patched code drains in days, and the months-lived versioned surface (the child) is identical in every design.

2. **Thin-workflow fat-services:** a stateless RequestCoordinator over a transactional Postgres request-state row plus the FR-8.9 outbox owns the FR-5.0 loop; Temporal is scoped to one per-event RegisterSaga. Rejected because the attempt counter and the start-child-then-commit window are exactly the crash-critical state this design must hand-protect with SELECT FOR UPDATE, outbox redelivery, and bespoke crash-injection CI — a class of work engine journaling gives for free — while the quantified savings are immaterial (a Temporal action delta of roughly low-$1k/mo against a ~$104k/mo NFR-5 cost envelope at 100k users), and it trades the FR-6.8/AC-48 letter; its own remediation (a thin per-request Temporal wrapper) concedes the parent while keeping a now-redundant state machine. Its Pacer, policy mechanism, and compensation stance are sound and are grafted into the decision.

3. **Event-driven choreography:** transactional outbox + broker as the spine between stages, a Selection Coordinator reducer owning the attempt loop, Temporal scoped to per-event register sagas. Rejected on three verified defects: it closes the registration workflow at `scheduled` — not a terminal state — and spawns per-change reconcile workflows, fragmenting the one-workflow-per-(user,event) lifecycle FR-8.1 requires; its own risk analysis concedes the NFR-1 p95 ≤ 5 s read path may have to abandon the broker spine for request/response, paying for a broker that is not the transport; and NATS/Kafka + relay + inbox tables are net-new ops surface (DLQ handling, redelivery tuning, schema governance across ~10 consumer groups) for a v1 already committed to Temporal Cloud. Its freeze-then-handoff kill-switch grace semantics are grafted in.

4. **One flat workflow per EventRequest carrying registration + lifecycle inline:** rejected on the binding constraint, not convenience — it violates FR-8.1's granularity outright (no `{user}:{event}` workflowId, no reject-duplicate dedup across concurrent requests targeting the same event, AC-55 unmeetable), and a single history spanning the attempt loop plus a months-long lifecycle has no clean continue-as-new seam.

## Decision

We will run a two-tier Temporal topology. The parent **EventRequestWorkflow** (`workflowId = req:{tenant}:{request_id}`, history ~40–60 events, closes within hours) executes parse→discover→dedupe→rank→hard-constraint filter + freeBusy conflict gate (FR-4.5, hard overlap ⇒ BLOCKED, never attempted, AC-27) as journaled activities, pins the RankedCandidateSet to object storage via claim-check, and runs the FR-5.0 attempt loop with a counter ≤3 in workflow state: per attempt it starts one child with that candidate's `lane_plan`, awaits the child's outcome signal, and falls through on failure; terminal state is either directing the best handoff-eligible candidate's child into handoff-mode or `failed_no_candidate` with the FR-6.6 notification (AC-33).

We will run the per-(user,event) child **RegistrationWorkflow** (`workflowId = {user_id}:{canonical_event_id}`, WorkflowIdReusePolicy=REJECT_DUPLICATE, ParentClosePolicy=ABANDON so children outlive the parent) as the FR-8.1 saga: load_selection freshness + freeBusy re-check → resolve_membership → policy_gate → lane ladder → await_confirmation (durable timer 24 h + signal, FR-8.4) → dedupe_calendar → write_to_calendar → months-long durable lifecycle wait to one terminal state. The lane ladder is within-candidate (AC-32): the child exhausts autonomous-on-SLA then browser-best-effort before reporting ONE failed attempt to the parent — attempts are per-candidate, lane fall-through is within-candidate.

We will resolve REJECT_DUPLICATE vs FR-5.0's terminal handoff with a **directive-signal protocol**: on lane exhaustion the child signals the parent `outcome=failed(reason, handoff_eligible)` and parks on a 10-minute directive wait; the parent replies `close` (fall-through continues) or `demote-to-handoff` (the already-open child becomes the request's terminal handoff — no second workflow for an already-tried event); timer expiry defaults to `close`.

We will make intake loss-proof with a Postgres **start-outbox**: the gateway dedups on hash(tenant, normalized_text, time_bucket) to deterministically mint `request_id`, writes the outbox row, then calls StartWorkflow reject-duplicate — an engine blip never loses a request and replays are dedup-safe (AC-48). We will mint idempotency keys once into child workflow state and pass them into activities, never generating them inside a retried activity (FR-8.3): source-mutation key `{workflow_id}:{run_id}:{step}:{seq}`; calendar id `base32hex(hash(tenant_id + canonical_event_id))` computed in workflow code so cross-source registration collides at the primary key (FR-9.2, AC-65); compensations reuse the minted keys. We will run a claim-check payload codec on every worker auto-offloading payloads >256 KB (FR-8.5, AC-58). Mutating activities (create_rsvp, browser_submit) carry RetryPolicy maximumAttempts=1; all retry paths re-enter through read_rsvp_state / browser_detect so blind re-POST is structurally unrepresentable (FR-5.3/5.5, AC-56).

Launch parameters: attempt budget 3 (FR-5.0, ratified); confirmation timeout 24 h; handoff TTL 7 d (ratified); directive wait 10 min; kill-switch grace 30 min; G2 DEGRADE threshold 5 min; browser submit loop ≤2; browser task-queue ScheduleToStartTimeout 120 s (saturation ⇒ handoff, AC-45); organizer-change poll ≤6 h (NFR-17); claim-check 256 KB; policy propagation ≤2 s.

## Consequences

**Easier:** the crash-critical attempt/state machinery is journaled by the engine — AC-56 crash injection is a replay property, not bespoke CI; AC-48 and AC-55 are satisfied by workflowId construction alone; durable waits (24 h confirmation, 7 d handoff TTL, months-long lifecycle) hold zero worker resources; concurrent-request dedup, re-request handling, and terminal-handoff demotion are race-free under REJECT_DUPLICATE plus the directive protocol; the FR-8.9 outbox stays a projection (audit, notifications, dashboards) rather than the drive shaft.

**Harder / risks accepted:** Temporal Cloud becomes a correlated failure domain for both lanes — during an engine outage no new handoff task can be created (bounded NFR-2/NFR-15 breach for the window; intake buffers in the start-outbox, in-flight state resumes losslessly) — accepted over building a second non-Temporal handoff path, contingent on O-6 confirming SLA ≥ NFR-3's 99.9% and namespace throughput ≥ ~1,600 transitions/s, neither figure dossier-backed. The ~$25/M-actions cost basis (~$1.6–2.5k/mo at 100k users) likewise needs O-6 contract verification. Patch-versioning discipline over ~240k open child executions is a standing operational competency; mitigated by pushing volatility into policy data and keeping the LaneRouter decision function stable. Child history bloat from chatty pollers is bounded by signal coalescing and continue-as-new after reconcile bursts, but must be load-tested. Follow-ups committed: the G2 spike measures real Meetup consumedPoints and quota scoping before any autonomous-lane SLA is declared (NFR-2 deferral); Redis Pacer loss re-initializes buckets empty (throttle-first) and must be fault-injection-tested.

**Owner-ratification riders:**
- OWNER RATIFY: FR-8.2 interpretation — discover/rank/select run as journaled activities in the PARENT, since the child workflowId cannot exist before discovery mints `canonical_event_id`; this ADR records that as the closest achievable reading of FR-8.2 at FR-8.1's granularity, an interpretation rather than an exception.
- OWNER RATIFY: re-request of a previously failed (user,event) defaults to a handoff task with deep link (strict FR-8.1 REJECT_DUPLICATE, NFR-15-compliant); the ALLOW_DUPLICATE_FAILED_ONLY reuse relaxation permitting one autonomous re-attempt deviates from FR-8.1's letter and needs explicit sign-off.
- OWNER RATIFY: confirmation-wait timeout = 24 h before handoff (FR-8.4 fixes the mechanism, not the number).
- OWNER RATIFY: child directive wait = 10 min, defaulting to `close` on expiry.
