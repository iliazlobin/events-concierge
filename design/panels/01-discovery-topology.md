# Panel 1: Discovery and catalog-ingestion topology

## The fork

(Fork question text was not included in the panel result JSON; the fork is the discovery and catalog-ingestion topology choice contested by the three proposals below — crawled single-store catalog vs. staged replayable pipeline vs. query-time federation, including where dedup, identity, and tenant isolation live.)

## Decision

Single-Postgres Catalog with Versioned-Replay Ingest and Tenant-Overlay Serving (graft: Proposal 1 base + Proposal 2's provenance/versioning + Proposal 3's structural enforcement). One Postgres 16 cluster (primary + 1 read replica) is both store of record and serving index: an append-only raw landing table, a tenant-neutral canonical catalog with pgvector HNSW + tsvector GIN, and RLS-forced per-tenant tables. Ingestion is batch micro-cycles via Temporal Schedules (no Kafka, no second datastore); dedup runs at ingest for the shared catalog and at query time only for the small per-user overlay, both through one pinned match-function library; the interactive path is a single fused SQL query (catalog UNION ALL tenant overlay) feeding the settled d07 rank stack.

## Rationale

The corpus (~150–500k active canonical rows, single-digit GB) and load (12.5 QPS interactive peak at 100k users, d15 line 49) sit three orders of magnitude inside pgvector's documented win regime (<50M rows, filter-heavy — d07 lines 25/50, which explicitly recommends Postgres+pgvector as the single store with no second search cluster), so a staged multi-schema pipeline or a federation tier buys failure-isolation and freshness this system does not need at the price of cross-store consistency bugs — the classic source of AC-17/AC-21 violations. Proposal 1's shape satisfies every binding constraint with stated arithmetic, but two of Proposal 2's mechanisms are load-bearing, not nice-to-have: (1) because canonical_event_id keys the FR-9.2 calendar idempotency hash and the FR-8.1 workflowId, identity repair after a false merge/split must be an append-only alias chain resolved through one library, not P1's ad-hoc tombstone-split; (2) because the TM 5,000/day budget makes re-fetching the one unaffordable operation and d07 flags dedup thresholds as medium-confidence/domain-dependent, raw payload retention + normalizer_version/merge_version stamps + shadow re-merge with a diff gate are the only way to recalibrate dedup or absorb source drift (the Eventbrite/Luma page-drift class both dossiers document) at zero quota cost.

Proposal 3 is rejected as base: its 14-day TM horizon violates NFR-1 for far-out publications, it puts SerpApi's 1–3s+ latency variance on the interactive path, it parks match-key metadata of private per-user events in a shared registry (the weakest NFR-7 posture of the three), and its own G2 contingency admits it grows back the crawl it rejected.

Crawl arithmetic (O-8): 25 metros × 5 TM segments × 2 date windows {0–14d, 15–90d}, both at 6h cadence (5h30m schedule + ≤15min pipeline lag ⇒ publication→discoverable ≤6h): ~4 pages/metro-segment/cycle at size=200 ⇒ ~500 calls/cycle × 4 = ~2,000/day typical (~40% of budget), soft cap 4,500 with a 500-call reserve for registered-event re-polls, retries, cell splits, and miss-fills; 500 calls ÷ 2 rps ≈ 4 min wall-clock per cycle, so the daily budget — never the 5 rps cap — is the binding constraint.

Tenant isolation is structural: catalog tables carry no tenant column and admit no credentialed writer; per-user Meetup/Luma results live and die inside RLS tenant tables at launch (no promotion), deleting both the NFR-7 misclassification gate P1 itself ranked as a top risk and the unexamined question of redistributing data fetched under one user's OAuth token to other tenants.

## Decided mechanism

- **STORE:** one Postgres 16 cluster (managed Multi-AZ primary + 1 read replica, PITR/WAL, pgBouncer transaction mode + SET LOCAL). Two logical schema families. CATALOG (tenant-neutral, no tenant_id column anywhere): raw_source_events (append-only JSONB, UNIQUE(source, source_event_id, content_hash), fetched_at, monthly partitions, detach to S3 parquet after 90 days; identical content_hash re-crawl is a no-op); canonical_events (canonical_event_id UUID minted once, schema.org/Event columns incl. eventStatus + IANA tz, embedding vector with HNSW index, tsv GENERATED tsvector column with GIN, pg_trgm GIN on normalized title, btree (city_norm, start_date) for dedup blocking, normalizer_version + merge_version stamps); event_source_links (source, source_event_id UNIQUE, canonical_event_id, registration_url, last_seen_at — AC-17 all-URLs retention); canonical_alias (append-only loser_id→survivor_id; ids never deleted or re-minted); sources policy table (automation_allowed{api,browser}, paid_allowed per FR-10.1); tm_budget_ledger; transactional outbox. TENANT (RLS-FORCED, non-owner non-BYPASSRLS role, tenant_id leading index per FR-1.3): user_candidate_events / overlay rows, preferences, lifecycle.
- **TM CATALOG CRAWLER** (the only code path linked against the TM client — no live-path TM client exists, so AC-21 zero-added-tenant-calls holds by construction, not caching heuristics): Temporal Schedule every 5h30m; facet planner enumerates cells = (metro, segment, window) over 25 metros × 5 segments × {0–14d, 15–90d}; BudgetLedger decrement strictly precedes every dispatch (soft cap 4,500/day, 500 reserved); global 2 rps token bucket; adapter makes violating requests unconstructible (size=200, page index 0–4, 200×4=800<1000); a cell projected >1,000 items recursively splits by genre then date-bisection, never deep-pages; upsert raw_source_events keyed (source, source_event_id) — idempotent under Temporal at-least-once retry.
- **TM RECONCILE RE-POLLER:** every 6h, by-id GET of every TM canonical event with an active registered/scheduled lifecycle, drawn from the 500-call reserve — guarantees NFR-17 ≤6h organizer-change detection for exactly the population NFR-17 scopes, independent of any future cell-cadence demotion; this plus crawl-upsert hash deltas is the declared FR-8.7a TM modality.
- **SERPAPI SWEEPER** (scheduled, per FR-3.6 wording — not request-time): 4 query templates × 25 metros × 4 cycles/day = 400 searches/day ≈ 12k/mo ⇒ $150/15k plan (d11 pricing); lands raw rows with per-provider ticket_info; Eventbrite discovery arrives exclusively here (FR-3.2).
- **DEDUP-GATED ENRICHMENT** (from P2, mechanizing FR-3.6): every funnel candidate runs the canonical match FIRST; a match only appends its registration URL to event_source_links and dispatches NO fetch; only unmatched/stale candidates trigger a credential-less human-cadence JSON-LD page fetch (DOM fallback) that lands as raw — cross-provider dedup strictly precedes per-source enrichment spend.
- **ACL NORMALIZER:** one versioned pure-library translator on every ingest path (FR-3.7): prefer JSON-LD Event block, fall back to source-field mapping, emit canonical schema.org/Event; every staging output carries raw_ref + normalizer_version; parse failures quarantine with alerting, never head-of-line block; contract-tested per source with recorded fixtures (d08).
- **DEDUP/CANONICALIZER** (ingest-time, shared catalog): block on (city_norm, start_date ±1d) under a Postgres advisory lock on the block; score pairs on pg_trgm/Jaro-Winkler title + description-embedding cosine + start-time delta + geo delta (d07 line 39); above threshold merge into existing canonical_event_id (elder id survives, alias row appended on canonical-canonical merge, registration URL appended); below, mint a new UUID once, UNIQUE(source, source_event_id) backstopped. Stamped merge_version; fully re-runnable over raw in SHADOW with a merge/split-count diff gate before cutover. Dedup completes before serving publish — ranking only ever reads canonical rows (FR-3.8 by construction).
- **PER-USER DISCOVERY** (Meetup GraphQL / Luma browser off-SLA): runs inside the EventRequest workflow's discover step under the requesting user's OWN stored credential only — adapter constructors require a tenant-bound credential handle, so no shared-token call site can exist (FR-3.5/AC-24). 2s budget with stale-while-revalidate: fresh working-set rows serve as-is; on timeout serve last-known + async backfill (p95 never hostage to Meetup latency). Results normalize through the same ACL and match through the same library; matched rows become tenant overlay rows carrying the canonical_event_id FK; misses become tenant-shadow canonicals with a stable minted id, alias-reconciled if the shared crawl later absorbs the same event. ALL per-user results stay inside the tenant RLS boundary — no promotion to the shared catalog at launch. Working-set freshness stamp 30–60 min, retention 24h. FairShare limiter keyed (source, credential); Meetup backoff off consumedPoints/resetAt (FR-10.4).
- **EMBEDDING WORKER:** batch-embeds new/changed canonical rows (persisted, so serving rebuild costs zero model calls — P2); tsvector is a generated column so rows are BM25-discoverable IMMEDIATELY and degrade to single-leg retrieval, never invisibility, until the dense leg lands minutes later.
- **QUERY/SERVING:** one SQL on the read replica with SET LOCAL tenant context: (canonical serving rows UNION ALL tenant working set under forced RLS) → pgvector ANN top-k + tsvector/BM25 top-k with geo/time/free filters pushed down → RRF k≈60 → 100–200 candidates deduped on canonical_event_id with source_links merged (an overlay row matching a catalog canonical yields ONE candidate carrying both URL sets) → settled d07 stack (Cohere cross-encoder 80–150ms → LightGBM → optional top-10 LLM tie-break ≤1s). p95 budget ≈2.5s ≪ 5s. Zero live TM or SerpApi calls on this path; the one Meetup call is the user's own quota by construction.
- **IDENTITY DISCIPLINE:** canonical_event_id minted exactly once, never reused; identity changes only APPEND canonical_alias rows; every consumer (FR-8.1 workflowId, FR-9.2 calendar key) resolves through ONE alias-resolver library, enforced by an AC-17-style CI fixture (same event via TM + Meetup + SerpApi ⇒ exactly one merged record, three registration URLs) plus a match-library version pin shared by ingest and overlay paths.
- **POLICY + CHANGE PROPAGATION:** automation_allowed/paid_allowed as sources-table rows read at call time behind a ≤30s LISTEN/NOTIFY-invalidated cache; both discovery dispatch and the FR-5.9 register check consult the same row (AC-23, no deploy). Crawler hash-deltas on canonical events with active lifecycles write an outbox row in the SAME transaction; the rate-shaped relay signals affected (user, canonical_event_id) Temporal workflows (FR-8.7/8.9).
- **LAUNCH PARAMETERS:** 25-metro grid; both windows at 6h cadence; ~2,000 TM calls/day typical / soft cap 4,500 / reserve 500; degrade ladder at 80% ledger = demote 15–90d window to 12h first (≈55 calls/metro/day ⇒ ~81-metro ceiling), then 24h (≈42.5 ⇒ ~105), never the 0–14d window; SerpApi 400 searches/day; per-user discover budget 2s; policy cache 30s; RRF k=60 into 100–200 candidates.

## Rejected alternatives

- **Query-time federation minimalist (Proposal 3) as base** — Its 14-day TM crawl horizon breaks NFR-1: a newly-published event starting >14 days out is not discoverable within 6h — it is not discoverable at all until T-14d — and its ~112-metro headroom and ~50k-row corpus numbers are artifacts of that truncated horizon, never flagged as a trade. Cold-path p95 of 4–7s survives NFR-1 only on a lawyer's reading of the 'cache-served' qualifier, against FR-3.3 and d15's explicit 'catalog crawl is LAUNCH architecture, not optimization.' It places SerpApi's 1–3s+ latency variance and synchronous fuzzy identity resolution on the interactive hot path where a mis-merge under latency pressure keys the wrong calendar hash. Its shared identity registry holds match-key metadata of private per-user Meetup events behind a single visibility predicate — the weakest NFR-7 posture offered. Its own G2 contingency concedes the design grows a Meetup mini-crawl under plausible evidence. Finally, no standing corpus starves LightGBM training snapshots (O-5).
- **Four-schema staged pipeline (Proposal 2) as base** — The replay/versioning payoff is real and is grafted in, but the full raw→staging→canonical→serving machinery with per-stage watermark workers, a rebuildable serving projection, and 2–3× storage is over-tooled for a 100–500k-row corpus — the same guarantees (catalog as a deterministic function of raw; quota-free re-normalize and shadow re-merge; zero-model-call rebuild) are achieved with raw retention + version-stamp columns + persisted embeddings inside two logical schema families. Its '20-metro launch footprint is the stated owner-scale assumption feeding O-8' anchor is invented — no owner decision or dossier pins a metro count. Its newest-sorted delta crawl as the sole NFR-1 mechanism leaves modified-far-out-event detection to a daily backfill and depends on unverified TM sort semantics; kept only as a post-launch budget optimization spike.
- **Proposal 1's public-Meetup promotion rule (at launch)** — Promoting per-user-token-fetched 'verifiably public' Meetup events into the tenant-neutral catalog makes a single classification predicate the only gate against an NFR-7 tenant-isolation incident (P1 itself listed this as a top risk), and silently answers an unexamined compliance question — whether Meetup's commercial-use-clause ToS permits redistributing data fetched under user A's OAuth grant to all tenants. Deferred to an owner-ratified post-launch decision; the SerpApi funnel already lands public Meetup events in the shared catalog through a shared, tenant-neutral key.
- **Streaming ingestion (Kafka/CDC-fed pipeline) and any second datastore (OpenSearch/managed vector DB)** — No binding freshness target is tighter than 6h; idempotent batch micro-cycles through Temporal Schedules meet NFR-1 with a ≤15-min pipeline lag and are replay-safe by upsert keying. d07 line 50 explicitly recommends against a second search cluster at this corpus; a sync pipeline between stores is the classic origin of exactly the AC-17/AC-21 consistency violations this fork is judged on. The transactional outbox (already required by FR-8.9) covers the only streaming-shaped need: change signals to workflows.

## Salvaged ideas

- From P2: BudgetLedger decrement-BEFORE-dispatch with a hard-arithmetic daily cap plus an explicit reconcile reserve (500 calls) — the 5,000/day limit enforced by ledger accounting, not monitoring.
- From P2: append-only canonical_alias chain (loser→survivor) with a single alias-resolver library used by every canonical_event_id consumer — replaces P1's weaker tombstone-split for the FR-9.2/FR-8.1 key-stability problem.
- From P2: normalizer_version/merge_version stamps + raw retention with content-hash suppression and 90-day S3 detach + shadow re-merge with a merge/split diff gate — dedup recalibration and source-drift absorption at zero TM quota cost.
- From P2: dedup-gated enrichment as the mechanical form of FR-3.6 (match first; only misses spend a fetch), and the single pinned match-function library shared by ingest dedup and query-time overlay, verified by the AC-17 CI fixture.
- From P2: embeddings persisted at normalize time so any index rebuild costs zero model calls; parse-failure quarantine with rate alerting instead of head-of-line blocking.
- From P3: structural nonexistence of a live-path TM client (the TM adapter links only into the crawler and re-poller) — AC-21 by construction; and adapter-level unconstructibility of size×page/rps-violating requests (AC-20 structural, not caller discipline).
- From P3: stale-while-revalidate semantics with explicit freshness stamps (30–60 min) and 24h retention on the per-user working set, plus warm-hit-rate tracked as the SLO that keeps the p95 number honest.
- From P3: advisory-lock + unique-constraint handling of the concurrent canonical-minting race, with loser-re-reads-and-attaches semantics.
- From P1 (base, beyond the topology): the budget-pressure shed order that degrades far-out-window freshness first and never the 0–14d window users actually book; tsvector-immediate/BM25-degrade so embedding lag never makes events invisible; the 2s per-user discovery budget with async backfill protecting p95.

## Edge cases

- Facet cell still >1,000 items after genre + date-bisection splits (e.g. NYC Music festival weekend): truncate at the API cap, log a completeness metric, rely on SerpApi funnel + per-user discovery to backfill the tail — declared limitation, never deep-page (AC-20).
- Dedup false-merge discovered after live workflows key on the id: split mints a new canonical id for the wrongly-attached source_links, appends alias + audit rows, re-points event_source_links, and signals affected (user, event) workflows to re-resolve through the alias resolver; calendar keys re-derive through the same resolver. Split tooling ships at launch.
- Two paths mint the same brand-new event concurrently (funnel enrichment + per-user overlay in the same second): advisory lock on the (city_norm, date) block + UNIQUE(source, source_event_id) backstop; the loser re-reads and attaches to the winner's canonical_event_id — no duplicate canonicals, no re-key.
- A tenant-shadow event later absorbed by the shared crawl: alias row reconciles the tenant-minted id to the catalog canonical; the tenant overlay re-points; any workflow started on the shadow id keeps resolving through the alias chain.
- Member-gated / private-group / unknown-visibility Meetup event discovered under user A's token: written ONLY to user_A's RLS-scoped tables (no promotion path exists at launch); the adversarial two-tenant suite extends AC-1 with a member-gated-event fixture asserting zero reachability from tenant B, including via the retrieval union.
- Event cancelled between crawl cycles or inside the working-set TTL: tolerated at discovery; the execution-time guards (FR-4.5 freeBusy gate, FR-5.5 detect-then-submit, FR-5.3 read-before-mutate) ensure staleness costs at most one attempt of the FR-5.0 ≤3-attempt budget, never a wrong side effect.
- Registered/scheduled TM event whose facet cell was demoted or shed under budget pressure: the by-id reconcile re-poller covers the entire registered/scheduled TM population every 6h from the reserve, independent of cell cadence — NFR-17 never depends on the crawl schedule.
- TM 429 or ledger exhaustion mid-day: honor retry-after; at 80% ledger shed the 15–90d window first, alert; hard exhaustion pauses the crawler until midnight UTC while serving continues from cache unaffected — the ledger's decrement-before-dispatch makes breaching 5,000/day arithmetically impossible.
- Embedding API failure or backlog: rows serve BM25-only via the generated tsvector column (RRF degrades to one leg for exactly those rows); alert at 2× cycle time; embeddings backfill on recovery — degraded recall, never invisibility.
- Replica lag beyond threshold during an ingest burst: interactive queries fall back to the primary and the crawler's write rate is throttled — batch ingest waits, the user request does not.
- Mass-cancellation delta storm (venue closure, festival cancellation): outbox relay is rate-shaped; reconcile fan-out flows through Temporal signals which absorb the burst durably rather than dropping reconciles.
- Source page-schema drift (Eventbrite/Luma JSON-LD layout change): recorded-fixture contract test fails CI; production quarantine-rate alarm fires; fix the transform, bump normalizer_version, replay raw from the drift date — zero re-crawl, zero quota spend.
- Policy flip mid-flight (automation_allowed=false): discovery dispatch skips the source-modality at next read (≤30s cache); in-flight register workflows short-circuit to handoff at the FR-5.9 policy check — no deploy (AC-23).
- Query with no SET LOCAL tenant context: the tenant leg of the retrieval union fails closed to zero rows and emits the FR-1.4 policy-violation audit event; the catalog leg, containing no tenant data, is safe to serve regardless.

## Open risks

- G2 (Meetup 500pt/60s scoping per-token vs per-app) remains the largest external unknown and is already a DESIGN-BLOCKING spike (requirements §8): if per-app, request-time Meetup discovery degrades to stale-serve-plus-backfill for most users at scale behind the fair-share queue, and Meetup-exclusive event freshness between requests worsens; the topology survives (retrofit = a shared geo-keyed Meetup sweep tier) but no Meetup-lane SLA number may be set before the spike. The ~15 pts/search cost is likewise an unpublished estimate (d15 lines 24–25) — measure, don't assume.
- Dedup threshold calibration is medium-confidence and domain-dependent (d07): a false merge propagates into calendar idempotency keys and workflowIds. Mitigated by conservative thresholds, the alias/split machinery, and shadow re-merge — but split tooling and a labeled events-corpus calibration set are LAUNCH deliverables, not deferrable.
- Single-cluster blast radius: a pathological ingest event (vacuum storm, HNSW bloat, migration lock) shares a failure domain with serving. Mitigated by replica-pinned serving, throttleable batch ingest (ingest can always wait; the user request cannot), and minutes-scale reindex on a small corpus — accepted deliberately as the price of one backup story and one query surface.
- Crawl-plan page-count assumptions (~1.5 pages hot / ~2.5 pages lookahead per metro-segment) are estimates; a build-time probe against the live Discovery API must validate them and the genre/date-bisection split coverage before the 6h-both-windows promise is confirmed. Ultra-dense cells that exceed 1,000 items after all splits are truncated at the API cap — a TM property no topology fixes; funnel + per-user discovery partially backfill.
- SerpApi is a single third-party proxy carrying all Eventbrite and (practically) Luma discovery; an outage bounds their staleness to its length with no in-scope fallback, and google_events title/venue noise bounds funnel dedup precision.
- Metro expansion couples to third-party discretion: beyond ~81 metros (12h lookahead) the options are 24h lookahead or a TM quota raise that is case-by-case and compliance-gated (d03/d11) — an ops posture the owner must pre-decide, not improvise.
- pgvector HNSW write amplification on a churning catalog is trivial at 150–500k rows but must be re-benchmarked before any 10× corpus growth (≥5M rows) is assumed safe on the single-index posture.

## Owner ratification items

- Launch metro grid = 25 metros. NO proposal's metro count is grounded in any signed decision (Proposal 2's '20-metro stated owner assumption' is invented; O-8 pins nothing). Ratify 25, plus the expansion ladder: >~40 metros at uniform 6h approaches budget; demoting the 15–90d window to 12h carries ~81 metros, 24h carries ~105; beyond that requires the discretionary TM quota raise.
- NFR-1 interpretation: the ≤6h discoverability target applies to BOTH date windows at launch (uniform 6h cadence, ~2,000 calls/day), and the budget-pressure degrade ladder sacrifices far-out-window freshness FIRST. Ratify that far-out freshness (12–24h under pressure or at metro expansion) is the accepted negotiating chip — an explicit product posture, not an ops improvisation.
- Per-user-discovered public Meetup events are NOT promoted into the shared catalog at launch (cross-tenant Meetup catalog benefit sacrificed; the SerpApi funnel partially compensates). Ratify this posture and, if promotion is wanted post-launch, commission both the adversarial visibility-classification fixture AND a Meetup ToS/commercial-use-clause review of redistributing token-fetched data before flipping.
- SerpApi launch spend: 400 searches/day ≈ 12k/mo on the $150/15k plan (scales linearly with metros and templates).
- Apply for the Ticketmaster quota raise EARLY (case-by-case after ToS/branding review, d03/d11) as a parallel track, accepting it may be refused — it is the only escape from the ~105-metro hard ceiling on the default key.
- Confirm the TM registered-event re-poll reserve sizing (500 calls/day supports ~125 concurrently registered/scheduled TM handoff-lane events at 6h cadence) once G1's request-mix measurement lands.

## Proposals (for the record)

### Proposal 1 — single-Postgres pragmatist

Bias: single-Postgres pragmatist — one Postgres cluster is the store of record AND the serving index; crawlers and the SerpApi funnel are plain Temporal-scheduled workers upserting rows; no Kafka, no OpenSearch, no second datastore. Boring technology sized to the actual corpus (~150k–500k active event rows, 12.5 QPS interactive peak at 100k users — three orders of magnitude inside pgvector's documented win regime, d07 line 25).

One Postgres 16 cluster (primary + 1 read replica, PITR/WAL) holds everything this fork decides: an append-only raw_source_events staging table, a tenant-neutral canonical_events catalog with pgvector HNSW + tsvector GIN + pg_trgm indexes, an event_source_links provenance table, and RLS-forced per-user tables (user_candidate_events, preferences, lifecycle). Ingestion is batch, not streaming: a Temporal-scheduled Ticketmaster facet crawler (50 metros × 5 segments × 2 date windows, every 6h, ~3,200 calls/day = 64% of the 5,000/day budget — arithmetic below), a SerpApi google_events sweep on the same cadence, and per-user Meetup/Luma discovery running under the requesting user's own token inside the EventRequest workflow. Dedup into CanonicalEvents runs at INGEST time (SQL blocking by city/date + pg_trgm fuzzy title + pgvector description-cosine + time/geo delta), so the interactive path is a single fused SQL query over pre-deduped rows: shared catalog UNION ALL the requester's RLS-scoped shadow rows, RRF-fused, then the settled d07 ranker. Tenant isolation is structural: catalog tables carry no tenant data and only source-public events; anything discovered under a per-user credential that is not verifiably public never leaves the RLS boundary. One backup story, one query surface, one failure domain to operate — and every binding constraint is met with stated arithmetic.

### Proposal 2 — staged-pipeline separation

Bias: Staged-pipeline separation: ingestion is an explicit, replayable pipeline — append-only raw landing → versioned ACL normalize → versioned dedupe/merge → published serving projection. The decisive argument in THIS system: the Ticketmaster 5,000-calls/day budget makes re-crawling the one thing you can never afford, so raw retention is not an ops nicety — it is the only mechanism by which dedup can ever be re-run, a source-schema drift absorbed, or the serving index rebuilt at zero quota cost. Replay is free; re-fetch is quota-bounded and ToS-bounded.

One Postgres cluster hosts four explicit pipeline stages as separate schemas — append-only `raw` landing (JSONB + S3 claim-check), versioned `staging` (ACL-normalized schema.org/Event CandidateEvents), versioned `canonical` (deduped CanonicalEvents + source_links + an append-only alias table), and a rebuildable `serving` projection (pgvector HNSW + tsvector GIN) — so the whole catalog is a deterministic function of raw payloads and can be re-normalized or re-merged without one source API call. Shared-app-key ingestion (Ticketmaster faceted crawl, SerpApi sweeps, credential-less JSON-LD page enrichment) runs as Temporal-scheduled micro-batches through these stages with a hard budget ledger: 100 (metro×segment) shards, size=200/max-5-pages, 4 delta cycles/day + 1 daily lookahead backfill = worst-case ~2,500 TM calls/day against a 4,750 soft cap, with hot-shard cadence 5h45m + ≤15 min pipeline lag holding publication-to-discoverable ≤6h. Per-user discovery (Meetup GraphQL, Luma) runs at request time under the user's own token into RLS-scoped tenant tables and merges with the tenant-neutral catalog via a query-time OverlayMerger that reuses the exact ingest match-function library — dedup is ingest-time for the shared catalog (replayable, versioned) and query-time only for the small per-user overlay, which is the honest price of never letting credential-fetched data touch shared schemas. Ranking reads only serving + tenant overlay; a second tenant adds zero live Ticketmaster calls by construction because the crawl is driven by the shard registry, not by requests.

### Proposal 3 — query-time federation minimalist

Bias: query-time federation minimalist — the catalog is a quota workaround for exactly one source (Ticketmaster), not an architecture; every other surface is federated live at request time under the requesting user's own credential, with short-TTL per-user result caches and a slim shared identity registry as the only durable state.

One Postgres (pgvector + tsvector) holds exactly three things: a slim tenant-neutral CanonicalEvents identity registry (stable IDs + match keys + the per-source registration-URL set), the Ticketmaster catalog content maintained by the only scheduled crawl in the system (sharded 25-metro × 5-segment sweep at 5.5h cadence, ~1,200 of the 5,000 daily calls), and RLS-scoped per-tenant working sets holding short-TTL federated results. Everything that is not Ticketmaster — Meetup under the user's own OAuth token, the SerpApi google_events funnel behind a tenant-neutral 6h read-through response cache, Luma browser discovery off-SLA — is fetched at request time by a FederationGateway with per-source deadlines and stale-while-revalidate, normalized through the ACL, and resolved synchronously through a single IdentityResolver into the registry BEFORE ranking, so dedup-before-ranking and stable canonical_event_id hold identically on the crawl path and the live path. Hybrid RRF retrieval runs as one SQL query over the union of the public catalog and the requesting tenant's own working set; tenant isolation is structural because the only tenant-scoped rows in the read path are behind forced RLS, and registry rows minted from a user's token-scoped discovery are visibility-restricted and unreachable from any other tenant's query. Freshness beats staleness: a Meetup or SerpApi result served to the user is minutes old at worst, not one crawl-cadence old, and the entire ingestion machinery the staged-pipeline alternative must build, monitor, backfill, and re-embed simply does not exist here. The honest costs are stated below: a cold-path first request in a novel geo can breach the 5s p95 (NFR-1 conditions that target on cache-served requests, and the warm path meets it with ~2.5s to spare), and the G2 Meetup quota-scoping unknown is the one result that could force this design to grow a Meetup mini-crawl.
