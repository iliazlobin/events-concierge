# Panel 4: Human-handoff, lifecycle and organizer-change-detection subsystem

## The fork

Where does the per-(user,event) lifecycle state machine live, and how is organizer change detected? Proposal 1: the Temporal workflow IS the state machine and source of truth, with all Postgres tables as disposable projections and per-workflow poll loops for detection. Proposal 2: a Postgres `lifecycle` table with a guarded transition function is the source of truth, Temporal workflows are durable executors, and detection is one central service. Proposal 3: an append-only event-sourced LifecycleLog (which IS the transactional outbox) is the source of truth, all subsystems are idempotent log consumers, and detection is a central DiffService keyed on canonical events.

## Decision

DB-anchored lifecycle state machine with Temporal as durable executor, and one central canonical-event change-detection service (Proposal 2 as base, with grafts from Proposals 1 and 3). The per-(user,event) lifecycle lives in a Postgres `lifecycle` table whose every transition is executed by a single guarded plpgsql `fn_transition` that atomically commits state change + transition ledger row + transactional-outbox row; the settled Temporal workflow per (user_id:canonical_event_id) remains the sole execution spine — it mints all keys, owns the handoff-TTL/confirmation/reminder durable timers, receives all signals, and advances state only through fn_transition inside activities. Handoff queue, Notifier (SES email to the real address), Inbound Gateway, and Completion Matcher are product subsystems over that table; organizer-change detection is one central service keyed by distinct watched canonical events (not user-event pairs) that normalizes all four per-source modalities to schema.org eventStatus and fans out Temporal signals to affected workflows.

## Rationale

Three binding constraints discriminate the fork. (1) FR-8.9 + NFR-8 name the transactional outbox as the system of record for lifecycle events, and an outbox row can only be atomic with the state it announces if that state is a Postgres row — Temporal history and Postgres cannot share a commit. Proposal 2 satisfies NFR-8 at full strength; Proposal 1 must explicitly trade its wording, and Proposal 3 satisfies it by identity but at the cost of a whole event-sourcing discipline. (2) FR-10.5/NFR-11 require erasing lifecycle/event history within ≤72h; Temporal Cloud histories cannot be selectively erased, so workflow-state-as-SoT (P1) forces either <72h retention or keeping all PII in Postgres claim-checks anyway — the DB-row SoT makes erasure a crypto-shred row operation and keeps histories to claim-check keys per FR-2.6/FR-8.5. (3) Detection economics: per-workflow polling (P1) costs ~96M Temporal actions/month at 200k watched events by its own arithmetic and multiplies fetches N-watchers-fold per popular event against a Meetup quota whose per-token sharding is UNCONFIRMED (d17 forum-sourced, G2 spike) and a TM key budget of 5,000/day (d11); central detection keyed by distinct canonical events (P3's shape) scales cost with distinct watched events — ~50k distinct Meetup events at 4 checks/day fits even the per-app worst case, and TM detection is a zero-extra-call diff of the settled d15 catalog crawl. P3's full event-sourced log was rejected because its paid-for benefits (replayability, audit-as-byproduct) are already obtained by the FR-7.3 immutable audit log + FR-8.9 outbox + NFR-13 backups, while its costs (append-before-act discipline, single-writer enforcement, snapshot-xip offset cursors, dual replay semantics alongside Temporal versioning) are standing engineering taxes. NFR-2(b) closes with large headroom in the decided design: task-available ≈5s worst case (single INSERT+transition commit as the first activity, 12x headroom on 60s) and user-notified ≈40s p50/~90s p95 measured at the SES delivery event (delivery, not enqueue), with the final recipient-MTA hop flagged for owner ratification. All three proposals converged on email-to-real-address, TTL-as-durable-timer, deterministic completion matching with a signed mark-done floor, and signal-based reconcile — those consensus mechanics are adopted; where they diverged on fuzzy-match posture, the conservative never-auto-complete-on-fuzzy stance wins because a wrong-task completion advances lifecycle and writes a calendar entry for an event the user never registered for, while the alternative costs exactly one user tap.

## Decided mechanism

- Lifecycle Store: Postgres `lifecycle` table (tenant_id, canonical_event_id, workflow_id, state enum found|handoff|awaiting_confirmation|registered|scheduled|reconciled|withdrawing + terminals completed|cancelled|expired|failed_no_candidate, conflict_warning flag, lane tag) under FORCE RLS with tenant_id leading index (FR-1.3); partial unique index enforces ONE non-terminal row per (tenant_id, canonical_event_id), paired with the engine-level reject-duplicate workflowId (FR-8.1). `fn_transition(lifecycle_id, expected_from, to, transition_id, payload)` does, in ONE transaction: guarded UPDATE (raises on illegal from-state), transition-ledger INSERT with UNIQUE(transition_id) so activity retries no-op, and outbox INSERT (FR-8.9/AC-63). Erasure (FR-10.5) = row-level crypto-shred of PII columns retaining non-PII operational fields; Temporal histories carry only claim-check keys and non-PII state.
- Temporal per-(user,event) workflow = durable executor and sole transition driver: mints transition_ids and idempotency keys once in workflow state (FR-8.3); owns durable timers — handoff TTL = min(7 days, event start time), reminder timers at T+24h and T+5d, park-to-event_end+24h before terminal completed; signal handlers handoff_completed, organizer_change (deduped on change fingerprint in workflow state), un_rsvp, kill_switch; every path ends in exactly one terminal fn_transition which, in the same activity, cancels open handoff tasks, removes watch-registry interest, and releases timers.
- Handoff Task Service (FR-6.1): `handoff_task` table under RLS (ULID id, tenant_id, workflow_id, canonical_event_id FK, reason enum {browser-fail, captcha, identity-wall, approval-gated, dues, deferred-register, saturation, unexpected-paywall}, deep_link, denormalized event summary, ttl_expires_at, state open→notified→completed|expired|cancelled). CreateHandoffTask is the FIRST activity after the routing decision: one commit = task INSERT + fn_transition(→handoff) + notification outbox row — task-available at ~5s worst case vs the 60s NFR-2(b) budget. Deep-link builder keyed by (source, reason): Meetup approval/dues/non-member → group-join URL + event URL from FR-3.8 provenance; Eventbrite → /e/{id} registration/checkout page from the SerpApi funnel; Luma → lu.ma/{slug}; RelayInbox address prefilled where the source form accepts an email query param (best-effort, gated on G3).
- Notifier (launch channel decision = email to the user's REAL address): outbox consumer woken by LISTEN/NOTIFY with 2s poll fallback, claiming rows FOR UPDATE SKIP LOCKED; renders and sends via SES v2 from notify.<domain> — a distinct SES identity/subdomain from the RelayInbox u.<domain>, with a config/CI lint forbidding any outbound send from the relay domain (FR-6.6). Notification ledger UNIQUE(dedup_key = workflow_id:type:transition_id) makes at-least-once outbox delivery at-most-once user-visible. Bounded retry: 5 attempts at 0/30s/2m/10m/30m, then failed+alert; hard bounce → suppression list + ops escalation. SES configuration-set delivery events stamp delivered_at = the NFR-2(b) 'delivery, not enqueue' measurement point; alerts at p95>45s task-available and p95>90s user-notified preserve reaction headroom. Twilio SMS adapter ships as a stub behind the same NotificationPort with a documented channel-swap runbook.
- Inbound Gateway (the three UI-less launch contracts, FR-6.7/6.8 + mark-done): (a) signed one-tap mark-done URL in every task notification — HMAC token over task_id+tenant+expiry(=TTL), GET /t/{token}/done → signal handoff_completed(evidence=user_mark_done); (b) un-RSVP — Reply-To act+<task_token>@in.<domain> on every notification parsed deterministically for DONE/CANCEL/UNRSVP, plus POST /v1/unrsvp → signal un_rsvp; (c) EventRequest intake — request@<domain> + POST /v1/requests, deterministic header/param extraction first, free text to a QUARANTINED no-tool LLM emitting a structured EventRequest only (FR-10.6/FR-7.4), workflow start idempotent on Message-ID hash (AC-48).
- Completion Matcher (FR-6.3): RelayInbox confirmation emails pass sender-domain allowlists (order.eventbrite.com, Luma domains, meetup.com) → per-source deterministic extractors pull source_event_id/URL → EXACT match on (tenant from localpart, source from sender, source_event_id against the task's FR-3.8 provenance URLs) → SignalWorkflow(handoff_completed, evidence=relay_email). Fuzzy match (normalized title + start ±15min + venue token overlap, the FR-9.3 recipe) NEVER auto-completes — it attaches evidence and sends a one-tap confirm prompt. No match → unmatched_confirmations ops table; nothing auto-advances. Source-webhook completion is a port contract with zero bound launch sources (d11: no third-party attendee webhooks exist). On any accepted completion the workflow re-runs the SHARED freeBusy activity (same implementation as the FR-4.5 pre-registration gate, two call sites) over the event window across all connected calendars: overlap → conflict_warning flag + warning notification; then advance to registered and run dedupe_calendar → write_to_calendar (deterministic id = base32hex(tenant + canonical_event_id), insert→409→patch, extendedProperties.private keys per FR-9.2/9.3) → scheduled.
- Change Detection Service (single, central — FR-8.7a): watch_registry = distinct (canonical_event_id, source) rows maintained by an outbox consumer on lifecycle enter/leave of registered|scheduled. Per-source feeders: TICKETMASTER = delta comparator on the settled d15 catalog crawl (eventStatus/startDate/venue vs stored CanonicalEvent, ZERO extra API calls) plus a targeted event-by-id refresh only for watched events starting <48h, capped at 500 of the 5,000/day key budget; MEETUP = 3h poller issuing ONE status query per distinct watched canonical event, drawing round-robin on the watchers' own OAuth tokens through the FR-10.4 fair-share scheduler (batched event-ID queries where the G2 spike confirms point economics), degrading to public event-page JSON-LD on consumer revocation; LUMA + ALL HANDOFF-LANE EVENTS = 3h unauthenticated public event-page GET parsing the JSON-LD Event block (FR-3.7 ACL path) at human cadence (~1 rps global self-cap), PLUS RelayInbox organizer change-emails through the same allowlisted extractors as a near-real-time accelerator. Everything normalizes to schema.org eventStatus + new start/end into an `event_change` table with a UNIQUE dedup fingerprint hash(event_id+status+dates); a fanout worker joins affected lifecycle rows and signals each workflow organizer_change{fingerprint,...}. Per-(source, watched-event) staleness gauges alarm at the 6h NFR-17 bound.
- Reconcile branch (in-workflow, journaled activities — FR-8.7/AC-60/61): EventCancelled → delete calendar entry by deterministic id + notify + terminal cancelled; EventRescheduled → freeBusy re-check over the new window, patch start/end/timeZone (IANA), notify (+ conflict warning if the new time collides) → reconciled, watch continues. Redelivered signals no-op on the fingerprint.
- Un-RSVP branch (FR-8.8/AC-47/62): policy-engine check first (kill-switch honored); Meetup member registration → createEventRsvp(response=NO) under the user's own token with read-before-mutate (FR-5.3); Luma → browser detect-then-submit withdraw, best-effort off-SLA; handoff-lane registration → withdrawal handoff task (manage-registration deep link, same task/TTL/notify machinery). The calendar entry is removed IMMEDIATELY on the un_rsvp signal (reflects user intent); terminal cancelled recorded via fn_transition; no payment path exists.
- TTL machinery (AC-46): the workflow's durable timer is the SOLE TTL authority — expiry runs one commit (task=expired + fn_transition terminal expired + expiry-notification outbox row), after a final drain-check for a buffered completion signal, then the workflow completes. A 15-min safety-net Sweeper (NOT an authority) repairs orphans only: tasks past ttl_expires_at+5min grace with a dead workflow, lifecycle rows with no live execution, event_change rows whose fanout signal found no live workflow — repairing through the same fn_transition + idempotent CalendarPort calls and emitting a divergence metric.
- Lane isolation (FR-6.4/NFR-15): the handoff subsystem runs on its own Temporal task queue, its own outbox partition, and its own poller budgets, sharing no queue or rate budget with the autonomous lane; every transition row and notification carries a lane tag and autonomous-lane SLA math reads lane=autonomous only, so browser-pool saturation or Meetup consumer revocation floods the handoff lane without appearing in autonomous-lane metrics. Failover is the same CreateHandoffTask code path triggered by typed activity failures.
- Invariants: (1) every lifecycle transition = exactly one fn_transition commit (state + ledger + outbox atomic), transition_id workflow-minted, retries no-op; (2) exactly one non-terminal lifecycle row per (tenant, event) ↔ exactly one open workflow; (3) lifecycle state is written only through fn_transition from workflow activities or the Sweeper repair path — DB grants deny all other roles; (4) every workflow ends in exactly one terminal state and its terminal transition releases all resources, proven by a nightly invariant query (zero non-terminal rows with closed workflows, zero watch rows for terminal rows); (5) RelayInbox is structurally inbound-only; (6) ambiguous completion evidence never advances state; (7) no raw inbound email reaches a tool-holding LLM and no plaintext secret enters histories, payloads, or rows (FR-10.6, FR-8.5, NFR-6).
- Launch parameters: handoff TTL = min(7 days, event start); reminders T+24h, T+5d; notification retry 5 attempts over ~43min; poll cadence 3h (one-missed-cycle headroom inside the ≤6h NFR-17 target); TM targeted refresh cap 500 calls/day; SLA alerts 45s/90s; Sweeper 15min + 5min grace; Meetup/Luma point-cost figures are ASSUMPTIONS (~5 pts/status query) pending the G2 spike.

## Rejected alternatives

- **Proposal 1 — workflow-native purist (Temporal workflow state as source of truth, DB as disposable projections).** Fails cleanly at three binding constraints. (1) FR-10.5/NFR-11: erasing lifecycle/event history within ≤72h is impossible against immutable Temporal histories — the proposal never addresses it, and the only fixes (retention <72h, or keeping all PII in Postgres claim-checks) either cripple operations or hollow out the single-SoT claim since the readable truth ends up in rows anyway. (2) NFR-8 names the transactional outbox the system of record; P1 concedes it must invert that reading — an owner-ratification exception the base design simply doesn't need. (3) Its in-workflow 6h poll loops cost ~96M Temporal Cloud actions/month at 200k watched events (its own arithmetic) and duplicate polls N-watchers-fold per popular event against a Meetup quota whose per-token sharding d17 marks forum-sourced/UNCONFIRMED — P1 presents per-user quota more confidently than the dossier supports, and its own documented fallback under the G2 contingency IS the central poller; we decide that now instead of paying to migrate later. Secondary: fleet ops reads (aging tasks, staleness) become eventually-consistent projections whose 'authoritative' fallback (workflow Query) does not work on closed workflows, and lifecycle-schema changes become workflow-versioning discipline rather than a migration.
- **Proposal 3 — event-sourced CDC log (append-only LifecycleLog as SoT, all subsystems as log consumers).** Architecturally sound and its detection topology is the best of the three, but the log-as-SoT buys nothing the requirements don't already provide more cheaply: FR-7.3/NFR-10 auditability comes from the outbox-fed immutable audit log, NFR-13 rebuildability from backups + outbox replay, AC-63 convergence from idempotent consumers — all present in the base design. What it costs is a standing discipline tax it itself lists as a risk: append-before-act bracketing, single-writer DB-grant enforcement, snapshot-xip contiguous-prefix offset cursors, CI rebuild-equivalence fixtures, and a second replay semantic (fold-the-stream) coexisting with Temporal's own history replay and versioning — 'two representations of lifecycle state' is the drift class this fork exists to eliminate. Current-state reads still require projections, converging on the base design's tables plus extra machinery. Its 31s total notification-retry envelope also gives up on a multi-minute SES incident where the base's ~43min envelope still delivers. Its canonical-event detection, conservative matching posture, lane tagging, and nightly invariant query are grafted.
- **Within-base rejection: Proposal 2's per-watching-user Meetup poll batching.** Polling every (user,event) pair under each watcher's token duplicates fetches for popular events and, under the G2 per-app-quota worst case the requirements explicitly carry as contingency, scales with user-event pairs instead of distinct events. Replaced by Proposal 3's canonical-event-keyed dedup (one status check per distinct watched event per cycle, round-robin across watchers' own tokens through the fair-share scheduler), which fits even the per-app worst case at launch scale.
- **SMS (Twilio) as the launch notification channel.** FR-6.6 permits it, but US A2P 10DLC carrier registration adds weeks of lead time for zero launch requirement, the SES estate already exists for RelayInbox inbound, deep links and the reply-based un-RSVP/intake contracts (FR-6.7/6.8) compose naturally on email threads, and no phone number is collected at onboarding today. SMS ships as a stubbed adapter behind the NotificationPort with a channel-swap runbook, promoted if the measured email-delivery p95 ever breaches.

## Salvaged ideas

- From P1: SES delivery-event SLA telemetry with explicit alert headroom (45s task-available / 90s user-notified alerts against the 60s/120s p95 budgets) so a breach is paged before it lands.
- From P1: the shared freeBusy Gate activity — one implementation, one test surface, two call sites (FR-4.5 pre-registration gate and FR-6.3 completion re-check).
- From P1: NotificationPort with the Twilio SMS adapter stub and a documented channel-swap runbook, making the channel a config change if email deliverability degrades.
- From P1: TTL expiry with no sweeper-as-authority — the durable timer racing the completion signal is the machinery, including a final buffered-signal drain check before committing terminal expired.
- From P1: begin sending-domain warm-up (DKIM/SPF/DMARC, reputation) during the NFR-12 Google sensitive-scope verification wait (3–6 weeks) so the two pre-launch clocks overlap.
- From P1: 'expired — reply to reopen' page on a mark-done link past TTL, with reopen as a NEW workflow attempt, never a mutation of a closed history.
- From P3: canonical-event-keyed detection roster — detection cost scales with distinct watched events, not user-event pairs; one poll covers all subscribers of a popular event.
- From P3: TM detection as a pure crawl-generation delta with ZERO additional API calls as the default posture (the capped <48h targeted refresh from P2 layered on top).
- From P3: launch-conservative completion matching — exact per-source event-id match auto-completes, everything else degrades to a one-tap confirm, tuned later from unmatched-confirmation telemetry.
- From P3: lane tag stamped on every transition and notification so autonomous-lane SLA math is structurally blind to handoff-lane volume (NFR-15 by construction).
- From P3: nightly invariant query proving zero closed-workflow non-terminal rows and zero watch rows for terminal rows.
- From P3: DLQ/park semantics for poison outbox entries — one bad event stalls one consumer's one entry, never the relay; pager on DLQ depth > 0.
- From P2 (base, but worth naming): reminder timers at T+24h and T+5d inside the TTL as the O-9 escalation knob, and the RelayInbox-prefill deep-link trick that routes source confirmations/change-emails onto the channel we control.

## Edge cases

- Completion signal arrives BEFORE the workflow reaches its wait (fast user, slow saga): Temporal signals are durably buffered (WorkflowExecutionSignaled journaled, d16) — the signal is consumed when the wait is reached; no custom buffering.
- Late completion evidence after terminal expired: SignalWorkflow returns not-found/closed → evidence routed to unmatched_confirmations for ops; the mark-done URL past TTL serves an 'expired — reply to reopen' page; reopen starts a NEW attempt workflow (attempt-suffixed workflowId under the single-non-terminal-row guard), never mutating a closed history.
- TTL timer fires while a completion signal is in flight: the expiry activity performs a final drain-check for a buffered handoff_completed before committing terminal expired; if present, completion wins.
- Organizer cancel/reschedule lands while the handoff task is still OPEN: cancel → task cancelled + 'event cancelled, no action needed' notification + terminal cancelled; reschedule → task summary and deep link refreshed + re-notification, and freeBusy re-runs at completion regardless.
- Fanout signal hits a just-closed workflow (terminal race): the signal failure is recorded on the event_change row; the 15-min Sweeper repairs calendar truth directly via idempotent CalendarPort delete/patch + notification, converging within one sweep.
- Duplicate detections of one organizer change (3h poll AND RelayInbox change-email): event_change UNIQUE fingerprint no-ops the second insert; workflows additionally dedup on the fingerprint in workflow state, so redelivered signals are no-ops.
- Worker crash between the fn_transition Postgres commit and the Temporal activity ack: the activity retries, fn_transition sees the duplicate transition_id and no-ops, the workflow proceeds — the dual-write window is closed by idempotence (AC-56/AC-63 pattern).
- Outbox consumer crash mid-batch: SKIP LOCKED rows unlock and redeliver; the notification ledger dedup_key makes redelivery at-most-once user-visible.
- freeBusy conflict discovered at handoff completion (commitment gained since routing): conflict-warning notification sent and conflict_warning flag stamped, lifecycle still advances to registered and the calendar entry is written — the user factually holds the registration (AC-43 interpretation; flagged for owner ratification).
- Fuzzy-only confirmation match (two similar events, template drift): NEVER auto-completed — evidence attached, one-tap confirm prompt sent; still ambiguous → ops parking lot. A wrong-workflow completion is treated as strictly worse than a delayed one.
- Spoofed confirmation email: sender-domain allowlist rejects it (FR-10.6); an email matching a tenant but no open task lands in unmatched_confirmations; nothing auto-advances; raw HTML never reaches an LLM.
- Hard-bouncing real address (email is the only launch channel): suppression + ops escalation + account flagged notification-degraded; the task and its TTL proceed, so the user may reach expiry without effective notice — accepted launch posture mitigated by onboarding address verification (owner ratification).
- Event starts sooner than the 7-day TTL: effective TTL = min(policy TTL, event start), so no task outlives its event; expiry notice says the event has started/passed.
- Un-RSVP for a handoff-lane registration (registered outside our surface): calendar entry removed immediately on the un_rsvp signal (user intent), a withdrawal handoff task with the source's manage-registration deep link runs in parallel on the same TTL machinery; if it expires unactioned, terminal cancelled stands and the notice states the source-side registration may persist.
- Kill-switch engaged mid-flight: delivered as a signal and checked by the policy activity before any register/withdraw side effect — pending actions short-circuit to handoff without a deploy (AC-40); un-RSVP withdrawals are equally policy-gated.
- Meetup consumer revocation mid-watch: the Meetup feeder circuit-opens on auth errors and degrades to public event-page JSON-LD polling (status is public), so detection survives the revocation that kills the RSVP lane; registration traffic separately fails over to handoff (FR-6.4) with no autonomous-lane metric impact.
- Poll failure / source outage: bounded per-fetch retry; a missed 3h cycle still meets the ≤6h NFR-17 bound on the next; N consecutive failures flip the per-(source,event) staleness gauge to alarm — the calendar entry is kept (stale beats wrongly-deleted).
- Duplicate EventRequest email (client resend): Message-ID-hash start idempotency yields exactly one workflow (AC-48); duplicate (user,event) starts are rejected by the engine (AC-55) and the partial unique index.
- Erasure request during an in-flight handoff (FR-10.5): terminal-cancel the workflow, cancel tasks, crypto-shred PII columns across lifecycle/task/notification/event_change rows, delete concierge-written calendar entries, retain non-PII operational fields; Temporal histories contain only claim-check keys and age out on retention.
- Popular-event mass cancel (one TM delta, thousands of watchers): fanout worker signals each workflow (well inside Temporal throughput, d13 §6); notification burst rides the outbox relay's ~1k msg/s headroom; per-user entries reconcile independently and idempotently.

## Open risks

- G2 (Meetup quota scoping + point cost) remains design-blocking for detection sizing, not just RSVP: the ~5 points/status-query figure used by all three proposals is an ASSUMPTION not present in d11/d17, and if the quota is per-app AND points scale per event node, ~50k distinct watched Meetup events at 4 checks/day (~1M pts/day) exceeds the per-app 720k pts/day ceiling at 100k users — mitigations are per-token sharding (if the spike confirms it), adaptive cadence above the 6h floor for far-future events, and explicit coverage-loss alerting rather than silent staleness.
- G3 (RelayInbox acceptance at Luma/Eventbrite signup validators) gates the highest-quality completion and change-email channels; if rejected, those sources degrade to mark-done-only completion and page-poll-only detection — the signed one-tap URL is therefore a launch requirement, and its click-through rate must be instrumented from day one.
- Handoff-lane users may register with their REAL email despite the relay prefill, silencing both the confirmation-match and change-email channels for that (user,event); detection then rests solely on the public page, and an invite-gated page (403) reduces it to nothing — tasks completed without a relay binding are flagged poll-only and surfaced on the reconcile SLO dashboard.
- Email deliverability is the single most credible NFR-2(b) breach: a cold notify.<domain> hitting greylisting/reputation throttles pushes the delivery tail past 120s; warm-up must complete pre-launch and per-provider delivery-latency SLOs must alert continuously.
- Public event pages dropping or restructuring their JSON-LD Event block (Luma/Eventbrite redesign) degrades handoff-lane detection until the fetcher is patched; staleness gauges surface it within one 3h tick but the window is real.
- Dual-write divergence (Postgres committed, Temporal activity retrying) is idempotence-closed but must be OBSERVED: alert on transition-ledger rows without matching workflow progress beyond N minutes, or the Sweeper silently becomes load-bearing instead of a safety net.
- unmatched_confirmations and expired-task ops queues need a staffing/escalation answer (O-9) before volume; correct-by-design refusal to guess creates human work.
- Meetup Pro consumer revocation (d17 sole-discretion, commercial-use clause) removes the API poll path; detection degrades to public-page JSON-LD + relay change-emails with a coverage-loss notice — accepted as alert-not-silent degradation; scraping-grade workarounds are ToS-prohibited and rejected.
- G1 (autonomous vs handoff mix) is unmeasured; all handoff-volume sizing is assumption-based — the subsystem is deliberately 3–4 orders of magnitude over-provisioned at its bottleneck (outbox relay ~1k msg/s vs ~0.12/s demand) so the mix moves cost, not correctness.

## Owner ratification items

- AC-43/FR-6.3 conflict-at-completion semantics: the decided design surfaces the conflict warning AND still advances to registered and writes the calendar entry (the user factually holds the registration); if the owner intended conflict to BLOCK the calendar write, it is a one-activity change but must be settled now.
- Launch notification channel = email to the real address only (FR-6.6 offers email OR SMS); consequence to ratify: a hard-bouncing address can reach TTL expiry without effective notice at launch — mitigation is onboarding address verification + bounce alerting, with the SMS adapter as the post-launch second channel.
- NFR-2(b) measurement boundary: 'user-notified' is measured at the SES delivery event — the honest edge of our control; a greylisting/deferring recipient MTA can push the p99 tail past 120s and no architecture on our side removes that. Ratify the boundary plus the 45s/90s alert thresholds.
- Handoff TTL = 7 days capped at event start (min(7d, event_start)), with reminders at T+24h and T+5d — the O-9 tuning knobs.
- Detection cadence 3h for Meetup/Luma/handoff-lane pollers (headroom inside the ≤6h NFR-17 target) and the TM targeted-refresh carve-out of 500 calls/day from the 5,000/day key budget (O-8 coupling).
- Fuzzy completion posture: never auto-complete on fuzzy match — costs one user tap in exchange for zero wrong-task advances; ratify as product behavior.
- Reopen-after-terminal mechanism: attempt-suffixed workflowIds ({user}:{event}:r{n}) under the single-non-terminal-row guard, as a clarification of FR-8.1's reject-duplicate key for re-requests after expired/cancelled terminals.
- RelayInbox prefill in handoff deep links: when the user registers with the relay address, organizer emails route to a mailbox the user does not monitor and the user depends on OUR re-notifications for source-side changes — ratify this coupling (it is also what makes near-real-time change detection work).
- unmatched_confirmations / expired-task ops-queue staffing and escalation policy (O-9) before launch volume.

## Proposals (for the record)

### Proposal 1 — workflow-native purist

Bias: workflow-native purist — the per-(user,event) Temporal workflow IS the lifecycle state machine; every other store is a disposable projection.

The per-(user,event) Temporal workflow (workflowId = "{user_id}:{canonical_event_id}", reject-duplicate) is the single authoritative lifecycle state machine: handoff is a workflow phase implemented as a durable timer (policy TTL, default 7 days) raced against a normalized completion signal; the handoff-queue row, the notification send, the freeBusy re-check, and the calendar write are idempotent activities whose keys are minted once in workflow state. Postgres tables (handoff_task, lifecycle_projection, watch_index, notification_dedup) are read-only projections written exclusively by one TransitionRecorder activity that commits projection-row + outbox-row in a single transaction, so FR-8.9's at-least-once delivery holds while zero second state machine exists to drift. Change detection is signal-delivery, not a parallel system of record: Ticketmaster reuses the settled catalog crawl with a delta-emitter that fans out signals via a watch_index projection; Meetup, Luma, and handoff-lane events are polled by the workflow's own 6h durable-timer loop (each poll a short activity through the fair-share scheduler, using the user's own token where applicable), complemented near-real-time by RelayInbox organizer-change emails routed by the ConfirmationMatcher. Launch notification channel is email to the user's real address over SES with delivery-event-measured latency, bounded retry, and workflow-minted dedup; completion matching resolves RelayInbox confirmations deterministically (recipient localpart → tenant, allowlisted sender → source, source-event-ref → canonical_event_id) and falls back to a signed one-tap mark-done URL — never a guessed signal. Every workflow ends in exactly one terminal state via a shared release_resources finalizer; the engine's already-solved timers/retries/signal buffering replace an entire bespoke queue-TTL-scheduler subsystem.

### Proposal 2 — product-subsystem pragmatist

Bias: product-subsystem pragmatist — handoff tasks, notifications, lifecycle rows, and change history are conventional product data: Postgres tables with guarded state columns are the source of truth; Temporal workflows are durable EXECUTORS that call into the product subsystem and subscribe to its signals; no product read path ever replays a workflow history.

The lifecycle state machine lives in a Postgres `lifecycle` table (RLS-scoped, one non-terminal row per (tenant, canonical_event_id)) whose every transition is executed by a single guarded plpgsql function that atomically writes the state change, a transition-ledger row keyed by a workflow-minted transition_id, and a transactional-outbox row — the same transaction FR-8.9 already mandates, which is structurally impossible if workflow state were the source of truth because Temporal history and Postgres cannot share a commit. Temporal per-(user,event) workflows remain the durable spine for execution — retries, saga compensation, the handoff-TTL and confirmation-wait durable timers, and all inbound signals — but they advance state only by invoking the transition function inside activities, so state is queryable, erasable (FR-10.5 crypto-shred is a row operation, not a history rewrite), and renderable by the future UI without history replay. The handoff queue is a `handoff_task` table (open→notified→completed|expired|cancelled) written as the first activity after the routing decision with the notification outbox row in the same commit, giving a measured budget of ~5s to task-available and ~40s p50 / ~90s p95 to SES-confirmed email delivery against the 60s/120s targets. Completion matching is a deterministic Completion Matcher keyed on (tenant, source, source_event_id) extracted from RelayInbox confirmation emails, plus a signed one-click mark-done link and reply-token parsing, all converging on one `handoff_completed` Temporal signal that re-runs freeBusy before advancing to registered. Organizer-change detection is ONE central detection service — a watch registry derived from registered/scheduled lifecycle rows, fed by the TM crawl-delta hook, a Meetup per-user-token poller, and a Luma/handoff-lane public-page JSON-LD poller plus RelayInbox change-emails, all normalizing into an `event_change` log whose fanout worker signals each affected workflow — because per-workflow polling timers would multiply fetches per popular event and blow the TM 5,000/day and Meetup 500pt/60s budgets.

### Proposal 3 — event-sourced CDC separation

Bias: Event-sourced CDC separation: the lifecycle is an append-only event log (the transactional outbox IS the log); handoff queue, notifications, calendar-reconcile triggering, and analytics are independent idempotent consumers; change detection is a dedicated diffing service emitting normalized schema.org eventStatus deltas onto the same log.

The per-(user,event) lifecycle is a single append-only Postgres event stream (LifecycleLog) that IS the FR-8.9 transactional outbox — every transition is one immutable event row, written in the same transaction as the activity's business effect, so at-least-once delivery with idempotent consumers is the substrate, not a bolt-on, and NFR-10 auditability plus AC-63 redelivery-convergence fall out structurally. The settled Temporal workflow per (user_id:canonical_event_id) remains the single WRITER and decider for its stream — it appends an intent event before every external side effect and a confirmation event after, and owns exact durable timers (7-day handoff TTL, confirmation waits) — while everything downstream (HandoffProjector, email Notifier, SLA/analytics projectors, WatchList) is an independent consumer keyed idempotently by (stream_id, stream_seq) that can crash, lag, and replay without touching any other consumer or the autonomous lane. Change detection is one DiffService that watches CANONICAL events (not user-event pairs): TM catalog-crawl generation deltas, batched Meetup GraphQL polls, Luma page JSON-LD polls plus RelayInbox change-emails, and public-page polls for handoff-lane events, all normalized to schema.org eventStatus deltas appended to canonical-event streams; a ChangeRouter consumer joins the WatchList projection and signals each affected workflow, which executes the reconcile as journaled activities. Launch notification channel is email to the user's real address via SES (RelayInbox stays inbound-only), with LISTEN/NOTIFY log tailing giving a sub-5s controllable pipeline against the 60s/120s NFR-2(b) budgets, measured at delivery via SES delivery events. Completion confirmation is a three-way port — signed one-click mark-done link (launch-guaranteed), RelayInbox confirmation-email matching with a confidence threshold, and a stubbed source-webhook port (no launch source offers one) — every completion re-running the freeBusy gate inside the workflow before the calendar write. The whole system is replayable end-to-end: any projection, dashboard, or handoff queue can be rebuilt from the log, and a divergent workflow can be reset and re-derived from its stream.

## Post-panel reconciliation (2026-07-10, design integration)

Panel 4's decided Ticketmaster feeder ("catalog-crawl delta + targeted by-id refresh only for watched events starting <48h, capped at 500 calls/day") conflicts with Panel 1's decided TM RECONCILE RE-POLLER ("every 6h, by-id GET of EVERY TM canonical event with an active registered/scheduled lifecycle, drawn from the 500-call reserve"). The rubric-gate consistency adversary surfaced the conflict; the design adopts **Panel 1's full-population 6h re-poll as canonical** for FR-8.7a TM detection, because it is the only variant under which NFR-17 (≤6h reconcile) survives the DD1 budget-degrade ladder (a watched event starting >48h out in a demoted 12–24h cell would otherwise detect late). Reserve sizing (~125 concurrently watched TM events at 4 polls/day) and the overflow posture (prioritize soonest-starting, alert, fall back to crawl delta) are carried as an owner-ratification item in the ADR log (ADR-008). Panel 4's <48h refinement survives as the *priority order* within the reserve, not as a cap.
