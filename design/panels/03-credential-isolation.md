# Panel 3: Credential, identity and browser-worker isolation topology

## The fork

Who owns the browser fleet and where does the trust boundary sit: a self-hosted fleet we operate from day one (Firecracker on bare metal, or minimal-TCB gVisor), or a managed vendor fleet (Browserbase) with every security-critical primitive kept first-party?

## Decision

"Sovereign Trust Plane on a Managed Fleet" — Proposal 2 (managed-vendor pragmatist) as the base topology, hardened with mandatory grafts from Proposals 1 and 3. Every secret-touching capability (siloed KMS-envelope vault, the sole-kms:Decrypt non-LLM Injection Broker, the default-deny egress proxy with per-(tenant,source) sticky identity, RelayInbox claim-check OTP path, CaMeL Reader/Planner split) runs in OUR VPC; the per-(user,event) ephemeral Firecracker microVM substrate is Browserbase (Developer tier at launch → Scale 250+ at the 100k horizon), with all session traffic forced through our egress proxy and no vendor-side persistence. A vendor-agnostic Fleet Port plus a pre-committed tripwire at sustained ~70 concurrent sessions makes the NFR-4b self-host decision a data-driven adapter swap whose named migration target is Proposal 3's self-hosted gVisor design (not bare-metal Firecracker).

## Rationale

The fork is who owns the fleet and where the trust boundary sits; the binding numbers decide it. Launch needs ~13.5 peak concurrent sessions (d15: 4,500 req/hr × 0.4 × 0.3 × 90s/3600) for exactly one off-SLA source (Luma), and 100k users needs ~135 peak with ~90 sessions/min creation demand — inside Browserbase Scale 250+/150-per-min, the branch NFR-4b explicitly names. Self-host economic breakeven is ~5,000 concurrent (d02), 37× the 100k design point. Proposal 1's day-one bare-metal fleet breaches NFR-5 for the whole launch window (infra alone $1.15–1.91 per browser RSVP at 1k users vs the $0.40 bound, ~$3k/mo fixed for ~13 sessions), converts a pre-PMF team into hypervisor operators for an explicitly best-effort lane, and worsens the lane's realized success via datacenter-IP anti-bot friction (d02: Cloudflare alone removed 55/586 tasks for one harness) — while its decisive claim that vendors cannot satisfy FR-2.4 is false: per-session proxy config through our own sticky-IP egress pins (tenant, source) network identity, which is d14 directive 7's actual requirement ("same isolated worker/network identity"). The vendor path keeps NFR-5 trivially satisfied at every scale because vendor infra is ~$0.0025/session against a $0.05–0.30 model cost (~98% of lane cost, d15 line 55): $0.15–0.40 per confirmed browser RSVP with Haiku/Sonnet tiering.

Every security FR that is enforceable by construction stays first-party: FR-2.2 (pooled CMK + per-tenant DEK + {tenant_id, credential_type} context PLUS kms:EncryptionContext IAM condition keys — d05's load-bearing correction), FR-2.5/2.6 (single central broker, pin-BEFORE-decrypt ordering grafted from P1 so a pin failure releases zero secret material; P3's single-decrypt-principal CI assertion), FR-5.7/5.8+FR-2.6 (OTP as a consumed-once KMS-encrypted vault ref in the Temporal signal — grafted from P1/P3, fixing P2's confirmed history-leak defect), FR-7.4/AC-52 (raw page bytes reach only the tool-less Reader; the Planner's input schema has no raw-text field, CI-asserted — rejecting P3's screenshot-ingesting pilot, which trades a binding AC's letter). What remains vendor-attested rather than first-party-proven — the AC-13 kernel-separation half and fill-time plaintext transit through the vendor CDP gateway — is bounded (cookie-first per FR-2.4/AC-12 means the transported secret is usually a revocable short-TTL cookie; nothing tenant-scoped persists vendor-side), explicitly flagged for owner ratification, and time-boxed: the Fleet Port plus P3's gVisor design (FR-2.7 names gVisor as acceptable; ~$500/mo launch-equivalent, standard EC2, no bare-metal step function) makes the ~100-concurrent migration an adapter change, at which point AC-13 becomes fully first-party.

## Decided mechanism

- Credential Vault (ours, siloed, FR-2.2): dedicated Postgres in its own subnet/IAM boundary storing {KMS-wrapped per-tenant DEK, AES-256-GCM ciphertext, bound_origin set, credential_type, capture-time worker-identity hash}; pooled CMK; {tenant_id, credential_type} encryption context enforced by kms:EncryptionContext IAM condition keys; vault role holds GenerateDataKey/Encrypt but NOT Decrypt (P3 graft). Plus an ephemeral-secrets table: KMS-encrypted OTP/magic-link rows with provider-TTL and a consumed-once flag.
- Injection Broker (ours, non-LLM, in the vault network segment): the ONLY IAM principal with kms:Decrypt on the credential CMK — checked as a one-line CI policy assertion (P3 graft). One gRPC method fill(session_ref, credential_id|otp_ref, field_ref, kind∈{username,password,cookie,otp}) callable only by Session Drivers over mTLS. Fixed order per fill: (1) live CDP read of top-frame AND focused-element-frame URL, exact-origin match vs bound_origin — BEFORE any KMS call, so a pin failure releases zero secret material (P1 graft, AC-7); (2) KMS Decrypt with tenant context; (3) plaintext into mlock'd MADV_DONTDUMP buffer (Rust zeroize/memsec); (4) Playwright fill()/Network.setCookie/char-typed OTP over the session's CDP websocket; (5) zeroize buffer + DEK on every exit path (finally semantics); (6) secret-free audit event. Broker also enforces FR-2.4: refuses cookie injection unless live identity-tuple hash == capture-time hash, and captures the fresh post-login cookie via CDP directly into the vault (never transits driver or any LLM). Placement note: central HA pair at launch (there is no host of ours on vendor infra to daemonize on); the same fill() contract redeploys as a per-node host daemon at self-host migration.
- Managed Browser Fleet (Browserbase): one session = one vendor Firecracker microVM per (user, event) attempt (d14 confirms this is Browserbase's isolation unit), created inside the register_or_rsvp activity, destroyed at activity end; keepAlive off; contexts/persistence hard-disabled by a session-creation wrapper + CI assertion against the vendor API; every session created with proxy config pointing at our egress proxy. Tiers: Developer (25) at launch → Startup (100) → Scale 250+ contract before the ~75k-user horizon.
- Egress Proxy (ours, mandatory): default-deny CONNECT/DNS proxy; per-session allowlist = target event origin + the source's registered first-party asset domains ONLY (tighter than FR-2.7's origin+KMS — the guest never needs KMS; the broker calls KMS from the vault segment). Pins worker identity: egress IP slot = consistent-hash(tenant, source) from a fixed EIP pool (stable assignment, never rotation — FR-7.6), plus pinned UA/fingerprint template; this tuple is hashed and recorded at cookie capture (P1 graft; browser build hash joins the tuple post-self-host). Any off-allowlist attempt is dropped, kills the session, and emits an audit event (AC-13 behavioral half).
- Session-start egress canary (fail-closed proxy verification): before any credential operation, the driver attempts a canary request to a non-allowlisted host from inside the session; if it is not blocked, the session is killed and the browser-lane incident path fires — converts vendor proxy enforcement from pure attestation into a per-session test.
- Session Driver (ours, Temporal activity workers): Stagehand v3 cached per-source DOM action scripts + Computer-Use vision fallback for the long tail (d02 hybrid); screenshots/DOM come OUT over CDP (claim-checked to S3 per FR-8.5), actions go IN; the driver holds zero decrypt permission and speaks only placeholders.
- Deterministic Action Gate (P3 graft, non-LLM, between Planner and session): enforces the closed action grammar — click(ref), fill(ref, {{placeholder}}), navigate(url ∈ session allowlist + event-URL path pin), detect(), submit(ref), halt_handoff(reason); routes fill_credential slots to the broker (the Planner has no broker channel); rejects submit unless the latest Reader detect returned NOT_PRESENT (FR-5.5 detect-then-submit as a gate, not a convention); holds the screenshot lock between field focus and fill-ack and verifies the target is a masked input before release (P3 graft); runs policy engine + kill-switch + FR-5.10 typed-price==0 guard before any submit.
- CaMeL split (FR-7.4/AC-52): Quarantined Reader LLM (Haiku/Sonnet vision) is the ONLY model that ingests raw DOM/screenshots — tool-less, no broker route, no Temporal access; output is a strictly schema-validated typed observation (page_state enum {LOGIN_FORM|RSVP_OPEN|CONFIRMED|NOT_PRESENT|AMBIGUOUS|CAPTCHA|PAYWALL|OFF_ORIGIN}, opaque field refs bound to selectors in driver code, length-capped pattern-filtered labels, typed numeric price). Privileged Planner LLM (Sonnet, text-only, prompt-cached scaffolding) consumes only typed observations + workflow state; its request schema has NO field capable of carrying raw page text — asserted by a CI schema test; AC-52 fixtures must include label-borne payloads, not just page-body payloads (P1 risk graft). Anthropic injection-classifier opt-out is replaced by this structural control (d02 implication 4).
- RelayInbox OTP claim-check path (P1/P3 graft — fixes P2's FR-2.6 defect): SES inbound → per-tenant KMS-encrypted S3 prefix → deterministic Lambda (per-source sender-domain allowlist, HTML strip, keyword+length extraction, no LLM ever sees the raw email — FR-10.6); Lambda KMS-encrypts the code into the vault ephemeral-secrets table (TTL = provider expiry) and calls signalWorkflow with ONLY {otp_ref, sender, expires_at}; workflow races the signal against a durable timer (FR-8.4); only the broker can redeem the ref, marking it consumed-once. Temporal history carries references, never secrets.
- Pool Governor (ours, NFR-4b): Redis semaphore at 90% of contracted vendor concurrency + a token bucket on the vendor session-CREATION cap (25/min Dev, 50/min Startup, 150/min Scale — d15 confirms creation binds before concurrency in bursts); acquire failure returns SATURATED synchronously and the workflow emits a pre-filled handoff task within NFR-2 targets (p95 ≤ 60 s task, ≤ 120 s notified) — never queues past SLA (FR-6.4/AC-45). Owns the tier tripwire: sustained peak > 70 concurrent opens BOTH tracks (Scale 250+ contract motion AND the gVisor self-host readiness spike).
- Fleet Port (vendor-agnostic session interface): create_session(tenant, event_origin, proxy_config, identity_profile) → CDP endpoint; the driver/broker/proxy topology never names the vendor. Named migration target = Proposal 3's self-hosted gVisor design (Fleet Supervisor + prewarmed credential-free runsc sandboxes + per-session netns, ~65 sessions per 64-vCPU host as a load-test-calibrated assumption, runsc -platform=kvm as the hardening fallback if AC-13's 'kernel' is ruled to mean hardware virtualization).
- Verification harness (NFR-6/AC-6/AC-13): CI drives a full broker-injected RSVP with a canary credential and greps LLM transcripts, tool-arg dumps, Temporal history exports, and logs for zero plaintext; AC-7 redirect-abort fixture proving zero KMS calls on pin failure; AC-5 cross-tenant KMS negative test; in-session egress-block assertion in CI and as a production canary; IAM single-decrypt-principal assertion; anomalous-cookie-use detection (IP/UA/pattern deviation → auto-revoke + needs_reauth, d14 directive 9).
- Launch parameters: Browserbase Developer tier; attempt budget ≤ 3 (FR-5.0); session wall-clock cap 5 min; Governor watermark 90%; tripwire sustained 70 concurrent; OTP ref TTL = provider-documented expiry; cookie-first with password grant only after cookie rejection (AC-12); cost basis model $0.05–0.30 + vendor ~$0.0025/session + rerank cents = $0.15–0.40 ≤ NFR-5's $0.40 at every scale including day one.
- Invariants: (1) exactly one IAM principal can decrypt credentials, CI-asserted; (2) domain-pin executes before KMS Decrypt — pin failure releases nothing; (3) no LLM-bearing process has a channel that can RETURN a secret (the broker types, it never returns plaintext to callers); (4) Temporal history/prompts/tool-args/logs carry only placeholders and opaque refs; (5) one vendor microVM per (user,event), destroyed at activity end, nothing persisted vendor-side; (6) all guest traffic crosses our default-deny proxy, verified per-session by canary; (7) cookie injection only on identity-tuple-hash match; (8) every browser-lane fault, saturation, or vendor outage terminates in exactly one place — a handoff task (FR-6.4, NFR-15); (9) submit only after read-only detect returns NOT_PRESENT; idempotency keys minted once in workflow state (FR-8.3).

## Rejected alternatives

- **Proposal 1 — self-hosted Firecracker on EC2 bare-metal from day one.** Breaches NFR-5 for the entire launch window by its own honest arithmetic (infra-only $1.15–1.91 per browser RSVP at 1k users vs the $0.40 bound; ~$2,978/mo fixed for a ~13-session peak) and buys that breach with a headcount-shaped hypervisor-ops burden (Firecracker/kernel/Chromium CVE treadmill, bare-metal on-call, EIP reputation management) on a pre-PMF team, for a lane the owner explicitly classed best-effort off-SLA. Its decisive claim — that a managed vendor cannot satisfy FR-2.4 identity pinning or egress control — is refuted by Browserbase's per-session proxy config routed through our own sticky-IP egress (d14 directive 7 requires same worker/NETWORK identity, which the tuple satisfies). NFR-4b's letter sanctions Scale 250+ as a co-equal branch; d02 puts self-host breakeven at ~5,000 concurrent, 37× the 100k design point; and its own datacenter EIPs worsen the d02 anti-bot friction that already caps write success at ~56–64%. Its security mechanics (pin-before-decrypt ordering, identity-tuple hash, label-payload AC-52 fixtures) are excellent and are grafted.
- **Proposal 3 — minimal-TCB capability broker on self-hosted gVisor from day one.** The strongest capability discipline of the three (grafted nearly wholesale), but it still pays day-one fleet ownership — gVisor+Chromium hardening spike, fleet ops, datacenter-IP CAPTCHA friction — for a 13-session launch that a $0.0025/session vendor covers, and its two load-bearing specifics don't survive verification: the 500–800-LOC broker claim cites d14 exemplars for which d14 contains no LOC figures (a Rust CDP+Playwright+grant-verify client realistically exceeds it, weakening the 'audit 500 lines' economics the bias rests on), and its AC-52 posture — a vision Computer-Use pilot ingesting raw screenshots inside the action-proposal path — trades the letter of a binding acceptance criterion ('reaches only the quarantined LLM, never the action path') that the Reader/Planner split satisfies without giving up the settled hybrid modality (cached DOM scripts carry the stable Luma flow; the split covers the tail). Retained in full as the NAMED self-host migration design at the NFR-4b threshold, where its cheap standard-EC2 economics genuinely beat Proposal 1's bare metal.
- **Proposal 2 as written (unamended).** Its OTP path is a confirmed FR-2.6 violation: signalWorkflow(user:event, {code}) records the plaintext OTP — a secret per FR-5.8 — in Temporal workflow history via the WorkflowExecutionSignaled payload, and the proposal claims FR-5.7/5.8 satisfied without flagging it. It also leaves FR-2.4 as a convention (proxy-level identity) rather than a deterministic broker check, and lacks the pin-before-decrypt zero-release guarantee phrasing, the single-decrypt-principal CI assertion, the screenshot lock, and the fail-closed per-session proxy canary. All fixed by grafts; the base topology stands.

## Salvaged ideas

- From P1/P3: OTP/magic-link as a KMS-encrypted, TTL'd, consumed-once vault claim-check reference — the Temporal signal carries {otp_ref, expires_at} only, reconciling FR-5.7's durable signal with FR-2.6's history exclusion (fixes P2's defect).
- From P1: pin-BEFORE-decrypt ordering as a stated invariant — the CDP origin check (top frame AND focused frame) precedes the KMS Decrypt call, so a domain-pin failure releases zero secret material, not merely 'aborts typing' (AC-7).
- From P1: deterministic worker-identity tuple hash — (consistent-hash egress-IP slot per (tenant, source), fingerprint template, UA) recorded at cookie capture and re-verified by the broker before any cookie injection; FR-2.4 as a broker check, not a convention. Plus the identity-decay runbook: version the fingerprint template and proactively expire cookies on deliberate change instead of suffering a mid-flight re-auth storm.
- From P3: single-kms:Decrypt-principal CI policy assertion, vault role limited to GenerateDataKey/Encrypt, and the capability framing 'no LLM-bearing process has a channel that can return a secret — the broker types, it never returns'.
- From P3: the deterministic Action Gate as a distinct non-LLM component — detect-then-submit enforced as a gate (submit rejected without a fresh NOT_PRESENT detect), navigation path-pinning to the event-URL prefix, and the screenshot lock during credential fill with masked-field verification.
- From P3: pre-submit typed title/date verification against the CanonicalEvent, bounding a hijacked planner's same-origin wrong-event residual.
- From P1: AC-52 fixtures must exercise label-borne payloads in the typed UI map, not just page-body payloads — the residual CaMeL leak is attacker-authored element labels.
- From P3 (whole design): the self-hosted gVisor fleet (Supervisor, prewarmed credential-free claim-once sandboxes, per-session netns proxy, runsc -platform=kvm fallback) preserved as the named, costed migration target behind the Fleet Port.
- From P1: anomalous-cookie-use auto-revoke (IP/UA/access-pattern deviation → revoke + needs_reauth, d14 directive 9) and the two-layer audit/CI harness shape (canary secret-scan over transcripts/history/logs, AC-7 redirect fixture, AC-13 egress assertion as CI + production canary).

## Edge cases

- Domain-pin mismatch (redirect, hostile iframe, prompt-injected navigation) during fill: broker aborts BEFORE any KMS call — zero secret material released — session destroyed, credential untouched, needs_reauth + handoff + pin-failure audit (AC-7); repeated pin aborts on one source trip the FR-10.3 quarantine breaker.
- Login failure / MFA / CAPTCHA / identity wall: Reader returns a typed page_state enum → orchestrator halts with zero retries, flips credential to needs_reauth, emits handoff with reason code (FR-2.8/AC-8); CAPTCHA is never solved or circumvented (FR-7.6).
- OTP never arrives or expires: durable timer wins the race against the signal → deterministic retry-or-handoff, no hung worker (FR-8.4/AC-57); expired ephemeral-secret rows are unreadable (TTL) and garbage-collected.
- OTP email arrives BEFORE the browser reaches the code screen: the Temporal signal is durably buffered (d16); the ref is redeemed when the workflow reaches its wait — no lost code.
- Duplicate/spoofed confirmation or OTP email: per-source sender-domain allowlist + deterministic extraction drop non-matching senders with an audit event (FR-10.6/AC-75); consumed-once refs + workflowId idempotency prevent a duplicate email double-advancing the lifecycle.
- Stale or DBSC-rejected cookie: no replay retry — broker reports invalid, workflow falls to fresh password+OTP login in the SAME session (identity tuple intact), else handoff; on success the broker captures the fresh cookie via CDP straight into the vault with the current tuple hash (AC-12).
- Identity-tuple decay (EIP reassignment, fingerprint-template version bump): change-management runbook proactively expires affected cookies and schedules re-auth handoffs rather than allowing a silent mass mid-flight failure storm.
- Pool saturation / vendor 429 / vendor full outage: Governor acquire fails synchronously → immediate pre-filled handoff task + notification within NFR-2 (p95 ≤ 60 s / ≤ 120 s — handoff creation is a control-plane write, never touches the fleet); the autonomous Meetup lane shares no resources and cannot be breached (FR-6.4, AC-44/45, NFR-15).
- CDP websocket drop or broker crash mid-fill: broker zeroizes on every exit path (finally); mlock'd MADV_DONTDUMP pages never swap or dump; Temporal retries the activity, which re-enters via the read-only detect — CONFIRMED ⇒ idempotent no-op, so a lost ACK never double-RSVPs (FR-5.5/AC-37, NFR-8).
- Ambiguous post-submit state (layout change, lost ACK, login wall): Reader returns AMBIGUOUS → durable signal to human review; blind re-POST does not exist in the action grammar (FR-5.5).
- Unexpected paywall / donation wall / tiered ticket with paid_allowed=false: Action Gate's typed price==0 check aborts pre-submit, routes to handoff, records the free/paid discrepancy (FR-5.10/AC-41).
- Indirect prompt injection in page content (AC-52): raw bytes reach only the tool-less Reader; schema/enum validation strips imperatives; the Planner's input schema cannot carry raw text (CI-asserted, label-payload fixtures included); a hypothetically hijacked Planner still cannot obtain plaintext (placeholder protocol, broker never returns secrets), navigate off-allowlist (egress proxy + Action Gate), or blind-submit (detect gate) — residual is wasted turns bounded by the 5-min session cap and ≤3 attempt budget.
- Kill-switch engaged mid-workflow: policy re-evaluation before every submit short-circuits the pending RSVP to handoff with no register call (FR-5.9/AC-40, AC-50).
- Vendor security incident: kill-switch freezes the browser lane globally; blast radius is bounded to in-flight session contents — no credentials, cookies, DEKs, or contexts persist on vendor infra; recently-filled cookies are precautionarily revoked (they are ours to revoke, custodied in our vault).
- Session created but proxy config not applied (vendor misconfiguration/regression): mandatory session-start egress canary fails → session killed before any credential operation, incident raised; repeated failures trip the browser-lane kill-switch.
- Erasure request (FR-2.10/FR-10.5/NFR-11): crypto-shred vault ciphertext + DEK including captured cookies and ephemeral OTP refs, revoke upstream tokens, audit tombstone; nothing to purge vendor-side because nothing persists there.

## Open risks

- Vendor coupling: a Browserbase outage, price change, or ToS shift takes the browser lane down; bounded by design (off-SLA lane, 100% degradation to handoff per FR-6.4, Fleet Port swap) but Luma-lane availability at launch is genuinely coupled to a Series-stage vendor.
- Browserbase Scale contract terms are not dossier-verified: exact concurrency/creation commitments, base/minimum pricing (the ~$390/mo figure is overage-rate arithmetic, not a contract quote), ZDR/data-handling posture, contractual per-session isolation, and proxy-enforcement guarantees must be locked before the ~75k-user horizon; a terms regression fires the self-host tripwire early.
- Proxy unbypassability ultimately rests on vendor network enforcement; the per-session fail-closed canary converts it into a test but a sophisticated bypass could race the canary — a discovered bypass trips the browser-lane kill-switch (FR-7.2).
- Fill-time plaintext transits the vendor CDP gateway until self-host migration: a vendor-side gateway compromise could observe in-flight fills; exposure is per-session, mostly short-TTL revocable cookies (cookie-first per AC-12), but it is a real incident class self-hosting would not have.
- DBSC/device-binding adoption by Luma (Chrome 146+ rollout, d14) would reject ALL cookie replay from ephemeral VMs regardless of identity pinning, pushing every session to fresh OTP login — higher cost, latency, and RelayInbox load; monitored via cookie-rejection rate (O-7).
- Gate G3 (do Luma validators accept RelayInbox addresses?) is a precondition for the entire FR-2.13 account-linking and OTP path; if it fails, this topology's login leg stalls regardless of fleet ownership.
- O-4: real Luma per-attempt success at the ~56–64% write ceiling is unmeasured; if the realized browser lane is mostly handoffs, the fleet-ownership question becomes moot and lane economics shift toward the handoff subsystem.
- The Q-LLM→typed-map bottleneck taxes long-tail capability (the Planner never sees pixels); mitigated by cached DOM scripts for Luma's stable flow, but if the measured success rate is unacceptable the only escape is an owner-ratified relaxation of AC-52's boundary, not a silent one.
- Central broker is a single point of failure for all credential fills: run as an HA pair, fail closed to handoff on unavailability (autonomous Meetup lane has no broker dependency and is unaffected).
- Per-session vCPU/memory budgets for the eventual gVisor fleet (~0.9 vCPU/session) are engineering assumptions to calibrate in the pre-migration load-test milestone; a 2× miss roughly doubles migration-fleet cost without threatening NFR-5.

## Owner ratification items

- FR-2.7/AC-13 launch posture: the kernel-separation half of AC-13 is verified by vendor attestation (SOC 2, contractual per-session Firecracker isolation, per-session API evidence) plus behavioral tests (the egress-block half runs fully first-party), NOT by a hypervisor we operate — accepted until the self-host migration, at which point AC-13 becomes fully first-party. This is the decision's one explicit binding-constraint exception and needs an owner sign-off.
- Fill-time plaintext transit: at fill time the secret crosses a TLS CDP websocket through the vendor's gateway into the vendor-hosted browser process (an exposure an in-VM/host-side broker would not have); mitigated by cookie-first (usually a revocable short-TTL cookie), per-fill scoping, immediate zeroization, and no vendor persistence — ratify as the accepted launch trade.
- NFR-4b tripwire parameters: sustained >70 concurrent (≈70% of Startup's 100) opens both the Browserbase Scale 250+ contract motion and the gVisor self-host readiness spike; the final Scale-vs-self-host call is made at the ~100-concurrent threshold with measured per-source success rates, session durations, and vendor terms. Ratify the trigger value and the dual-track spend.
- Named self-host migration target = Proposal 3's gVisor design on standard EC2 (not bare-metal Firecracker); if the owner rules AC-13's 'kernel' to require hardware virtualization per session, the config swaps to runsc -platform=kvm at a density/cost penalty (host count roughly doubles) — rule on the interpretation now so migration sizing is decided consciously.
- Browserbase Scale contract checklist to lock before ~75k users: ≥250 concurrency, 150/min creation, ZDR/data-handling posture, contractual per-session isolation language, proxy-enforcement guarantee, persistence-off guarantee; a regression on any item fires the self-host trigger early.
- Anthropic Computer-Use injection-classifier opt-out (d02): the default classifier inserts human confirmation on flagged injections, which breaks the no-per-action-confirmation scope; opting out and substituting the CaMeL split + deterministic gates is a safety-posture call the owner should ratify explicitly.
- Launch parameter set: attempt budget ≤3 (FR-5.0 owner target), 5-min session wall-clock cap, 90% Governor watermark, cookie TTL/reuse tuning per O-7 — confirm as launch values.

## Proposals (for the record)

### Proposal 1

**Bias:** Self-host security purist: own the entire browser fleet from day one — Firecracker microVMs on our EC2 bare-metal, our egress gateway, our CDP control plane, our host-side injection broker. No third-party browser vendor ever holds a user credential, session cookie, or egress path. The isolation contract (FR-2.7, AC-13, FR-2.4) is enforced by OUR hypervisor boundary and OUR nftables rules — auditable in CI — not by a vendor's ToS attestation. The 100-session Browserbase Startup ceiling (below the binding ~135 peak, NFR-4b) proves vendors cannot follow where this product is going; build once at launch scale (~13 concurrent) and grow linearly.

**Summary:** The browser lane runs as a self-hosted Firecracker fleet on EC2 bare-metal from day one: one snapshot-booted microVM per (user, event) containing only Chromium and a CDP shim — no keys, no model credentials — with a per-session nftables egress allowlist pinned to the target event origin. The injection broker is a per-node HOST daemon (not an in-VM sidecar, not a central service): it is the only process with kms:Decrypt (condition-keyed on tenant encryption context), it domain-pins the guest's live URL over vsock-CDP BEFORE unwrapping the DEK, fills via Playwright/CDP into the guest, and zeroizes mlock'd buffers — so plaintext never crosses a network link and never enters the guest kernel that renders hostile content. The reasoning loop runs outside the VM in Temporal activity workers, structurally split CaMeL-style: a quarantined vision Q-LLM turns screenshots into schema-validated typed UI maps; a privileged text-only P-LLM whose input schema has no raw-page-text field plans actions from a closed grammar with {{placeholder}} credentials; RelayInbox OTPs bypass both LLMs entirely, traveling as vault claim-check references in durable Temporal signals that only the broker can resolve. Worker identity for cookie reuse (FR-2.4) is a deterministic (egress-IP slot, fingerprint template, browser build) tuple hash recorded at capture and re-verified by the broker before any cookie injection. Sizing: 1 c5.metal node at launch (~60-session capacity vs ~13.5 peak at 10k users), 3 nodes at 100k (180 capacity vs 135 peak, 33% headroom), with saturation failing over to the handoff lane per FR-6.4 — which is also why the off-SLA lane tolerates single-node launch. Marginal compute is ~$0.0016/session (cheaper than Browserbase's $0.0025) and the browser lane lands at ~$0.11–0.35 per confirmed RSVP at ≥10k users; the honest trade is fixed-cost amortization below ~10k users and a real hypervisor-ops burden, both accepted as the price of an isolation contract we can actually test (AC-13) rather than sign.

### Proposal 2

**Bias:** managed-vendor pragmatist — launch on Browserbase (Startup → Scale 250+), keep every security-critical primitive (vault, broker, egress policy, CaMeL split, RelayInbox) in OUR infra, and treat self-hosted Firecracker as a data-driven decision at the ~100-concurrent threshold, not a day-one hypervisor project

**Summary:** The browser fleet is Browserbase — whose per-session unit IS a Firecracker microVM operated by the team that runs Firecracker at scale — while every component that touches a plaintext secret stays in our VPC: the siloed KMS-envelope vault, a non-LLM Injection Broker that is the sole holder of kms:Decrypt and reaches into vendor sessions over CDP (domain-pin → fill() → zeroize), and a mandatory egress proxy that ALL vendor-session traffic is routed through via Browserbase's per-session proxy config, enforcing an allowlist of the target event origin only (tighter than FR-2.7's origin+KMS, because the guest never needs KMS — the broker does, from our vault segment). The reasoning loop runs in our infra as Temporal activity workers (Stagehand DOM-skeleton + Computer-Use fallback): screenshots/DOM flow out over CDP to a quarantined no-tools Reader LLM that emits only schema-validated typed observations; a privileged Planner LLM sees only those typed structures plus placeholders and picks from a bounded action vocabulary — untrusted page bytes and RelayInbox OTPs structurally never reach the injection or action-decision path. Worker identity for FR-2.4 cookie reuse is a stable per-user network+fingerprint identity pinned at our egress proxy, with captured short-TTL cookies custodied in OUR vault (vendor contexts never persisted). Sizing: 13.5 peak concurrent at 10k users fits the Developer tier; ~135 at 100k is served by Browserbase Scale 250+ — the exact branch NFR-4b names — with a Pool Governor that fails saturation over to handoff; total managed-browser infra at 100k is ~$390/month, roughly 1–2% of browser-lane cost, making self-hosting a fleet 37× below its ~5,000-concurrent breakeven a distraction from shipping.

### Proposal 3

**Bias:** minimal-TCB capability broker — concentrate every secret-touching capability into one ~500–800-line formally-reviewable broker; make everything else (orchestrator, reasoning loop, page LLM, fleet supervisor) untrusted by construction; gVisor for density and sub-second session starts; self-host the fleet from day one so the trust boundary never crosses a vendor.

**Summary:** The topology is built around one security economics claim: you cannot audit a fleet, a vendor, or an LLM, but you can audit 500 lines. A single Rust host-daemon Injection Broker is the ONLY principal in the entire system holding kms:Decrypt on the credential CMK — verifiable by one IAM policy assertion in CI. Everything that ingests untrusted bytes (the Computer-Use pilot, the quarantined page reader, the browser guest) holds zero secret capability and is physically separated from the broker by process, namespace, and a typed single-purpose socket; everything that holds secret capability (the broker) runs no LLM and makes only deterministic decisions (grant signature, STS tenant pin, CDP origin match, fill, zeroize). Sessions run one ephemeral gVisor runsc sandbox per (user,event) — explicitly permitted by FR-2.7 — giving ~150 ms starts and ~65 sessions per 64-vCPU host, so the d15 ~135-peak-concurrency at 100k users is served by 3–5 autoscaled hosts (~$2.7–4k/mo) that we own end-to-end, instead of a Browserbase Scale contract that would put credential plaintext transit inside a vendor TCB we cannot attest and whose Startup tier (100 sessions, 50 creations/min) the Friday peak already exceeds. OTP/magic-links ride the same capability discipline: RelayInbox extracts deterministically, stores the code as a TTL'd encrypted ref, and the Temporal signal carries only the opaque ref — so no secret ever appears in workflow history, prompts, or logs by construction, and the CI secret-scan verifies an invariant the architecture already guarantees.
