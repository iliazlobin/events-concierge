## 1. Purpose

A production-grade, multi-tenant product that turns a natural-language request ("find me something Friday evening after work and sign me up") into a confirmed calendar entry. For each request the system **discovers** candidate events across many sources (API connectors where a source exposes one, browser automation and a SerpApi cross-source funnel where it does not), **ranks** them against the requesting user's stored taste and hard constraints, autonomously **selects and registers/RSVPs** the best registerable candidate where the source's Terms of Service and technical surface permit, writes the confirmed event to the user's **calendar** with de-duplication behind a conflict gate, and **reconciles** that entry when the organizer cancels/reschedules or the user un-RSVPs.

The product ships the **honest split**: discovery + ranking + calendar (+ reconciliation) are **always autonomous across all sources**; RSVP is **autonomous only where the source permits** (Meetup existing-group events on the reliability SLA; Luma via browser, best-effort, off the SLA); everywhere else (Eventbrite, Partiful, approval/dues/non-member Meetup groups) the product delivers a **pre-filled, one-tap human-handoff** as a first-class feature, not a failure state. This produces **two SLA classes** — an autonomous lane and a handoff lane — a first-class human-handoff subsystem, and deterministic per-source-per-modality routing.

It is deliberately **not**: an autonomous *paid* ticket purchaser (the payment port is a stubbed forward-looking abstraction at launch — decision 4); a single-user personal script (it is a shared multi-tenant service acting on other users' accounts and credentials — decision 1); or a Terms-of-Service-evading scraper (compliance is per-user human-cadence pacing and quarantine-on-ban, never IP rotation or block circumvention — `d10`).

## 2. Confirmed scope (owner decisions, hard)

Settled at kickoff and after research convergence (2026-07-02). HARD — do not re-litigate.

1. **Multi-tenant product.** Authentication, per-user profiles + preferences + **stored third-party credentials**, tenant isolation, and product-grade SLAs are first-class — not afterthoughts.
2. **Hybrid discovery.** API/connector retrieval where a source has an API, plus browser-driven retrieval (programmatic Computer Use API + DOM adapters) for API-less / JS-heavy sites, plus a SerpApi `google_events` cross-source funnel.
3. **Fully autonomous within the permitted surface.** No per-action confirmation prompt. Safety lives in configured **policy** — per-user limits, idempotency, auditability, kill-switch — not interactive gates.
4. **Launch = FREE RSVP only; paid purchase DEFERRED.** The payment port stays a forward-looking abstraction behind a `paid_allowed` flag; no BOTS-Act / SCA / chargeback machinery is built at launch (`d04`, addendum).
5. **Source posture = API-FIRST, browser BEST-EFFORT.** Browser automation is off the reliability-SLA critical path, with human-handoff on failure.
6. **Post-booking lifecycle IN v1.** Detect organizer cancel/reschedule (schema.org `eventStatus` via webhook/poll) and reconcile the calendar entry; support user-initiated un-RSVP (free ⇒ no refund complexity).
7. **v1 framing = "ship the honest split."** Always-autonomous discovery + ranking + calendar (+ reconciliation) across all sources; autonomous RSVP where the source permits; pre-filled one-tap human-handoff everywhere else. Implication: two SLA classes, a first-class human-handoff subsystem, per-source-per-modality routing.

## 3. Definitions

| Term | Meaning |
|---|---|
| **Tenant / User** | A registered account. Tenancy is per-user; `tenant_id` is a signed OIDC claim resolved at the request edge and threaded into every store access (`d05`). |
| **EventRequest** | One natural-language ask from a user ("something Friday evening after work") with parsed constraints (time window, geo, category, budget, hard filters) and an intent embedding, received through the request-intake channel (FR-6.8). |
| **CandidateEvent** | One source's raw advertisement of a real-world event, as retrieved by a `SourcePort.discover()` before normalization. |
| **CanonicalEvent** | The de-duplicated, ACL-normalized schema.org/`Event` record for one real-world event, retaining **all** per-source registration URLs and provenance (`d07`, `d08`). Ranking, registration selection, and the calendar idempotency key all operate on the CanonicalEvent. |
| **Source** | An external event surface (Meetup, Ticketmaster, Luma, Eventbrite, Partiful, SerpApi funnel, …). Each carries a per-modality policy record `automation_allowed = {api, browser}` and `paid_allowed` (`d10`). |
| **SourcePort / modality** | The single port `discover()` + `register()` per source, implemented by up to two **adapters** — an **API adapter** (preferred) and a **browser adapter** (fallback). Adapter selection is a deterministic capability-flag decision, never a model choice (`d08`). A **modality** is `api` or `browser`. |
| **Registration** | The act of securing the user a place at an event on the source's own surface (an RSVP for free events; paid purchase is out of scope at launch). |
| **RSVP lane** | The routing class for a `(source, modality, group-condition)` triple: **autonomous-on-SLA** (Meetup API for groups the user is already in), **browser-best-effort** (Luma browser, off SLA), or **human-handoff** (Eventbrite, Partiful, approval/dues/non-member Meetup groups) (`d10`, `d11`, `d17`). |
| **Credential** | A stored per-user third-party secret or token: an OAuth refresh token (preferred, e.g. Meetup, Google) or, for browser-only passwordless sources, a session cookie / password held under KMS-envelope encryption (`d05`, `d14`). |
| **RelayInbox** | A per-user concierge **email** address (`alice@u.<domain>`) the user signs up email-magic-link/OTP sources with, so login codes arrive on a channel the system controls — never the user's Gmail (`d16`). Partiful's SMS-only login is **not** served by the RelayInbox (FR-2.4). |
| **Consent record** | A first-class per-source, per-user, per-scope, timestamped artifact evidencing the user's delegation, satisfying Meetup OAuth, Eventbrite §4.2, and GDPR/CCPA lawful-basis in one object (`d10`, `d14`). |
| **Saga** | The durable workflow per `(user_id, canonical_event_id)`: `discover → rank → select → resolve_membership → register_or_rsvp → await_confirmation → dedupe_calendar → write_to_calendar`, each side-effecting step a journaled Activity with compensation (`d13`). |
| **Lifecycle** | The per-`(user, event)` state progression `found → registered → scheduled → reconciled`, plus the `handoff` and `un-RSVP` branches and the **terminal states** `completed`, `cancelled`, `expired` (handoff/confirmation TTL elapsed), and `failed_no_candidate` (FR-5.0). Every workflow ends in exactly one terminal state, which closes its durable workflow and releases resources. |
| **Handoff task** | A pre-filled, one-tap unit of work surfaced to the user when a source/modality cannot be completed autonomously (browser failure, CAPTCHA/identity wall, approval/dues gate, deferred-register source, saturation, unexpected paywall). Carries a policy TTL after which it transitions to `expired`. |
| **Policy engine** | The externalized declarative authorization layer evaluated at the money-/action-moving boundary: per-user limits, `automation_allowed`/`paid_allowed`, dry-run mode, kill-switch (`d04`). |
| **Kill-switch** | A data-plane control (per-user and global) that, when **engaged**, freezes all registration/RSVP actions without a deploy; **disengaging** it resumes normal policy evaluation (`d04`). |
| **Injection broker** | A non-LLM component that decrypts a KMS-enveloped credential in-memory, domain-pins the live URL via CDP, types it via Playwright `fill()`, and zeroizes — the secret is structurally excluded from prompts, tool-args, workflow history, and logs (`d14`). |

## 4. Functional requirements

### FR-1 Identity, tenancy & authentication

- **FR-1.1** The system shall authenticate users via **OIDC with a Backend-for-Frontend**: the browser holds only an httpOnly/Secure/SameSite session cookie, third-party tokens stay server-side, and `tenant_id` is a signed claim resolved once at the request edge (`d05`).
- **FR-1.2** The system shall isolate tenant data under a **bridge topology**: pooled user/profile/preference/lifecycle data behind Postgres Row-Level Security, with the third-party-credential vault **siloed** (own store, KMS key hierarchy, network segment) (`d05`).
- **FR-1.3** While serving any tenant-scoped request, the system shall enforce RLS with `FORCE ROW LEVEL SECURITY`, connect as a non-owner role without `BYPASSRLS`, set the tenant context with `SET LOCAL` inside the transaction (pgBouncer transaction-mode safe), and index `tenant_id` as the leading column (`d05`).
- **FR-1.4** If a query executes without an established tenant context, then the system shall return zero rows and record a policy-violation audit event rather than fall back to owner scope.
- **FR-1.5** The system shall provision each user a **RelayInbox** email address at onboarding and bind it to the tenant (`d16`).

*Acceptance:*
AC-1 a request authenticated as tenant A that attempts to read tenant B's profile, preferences, or credential rows returns zero B-rows, proven against a two-tenant fixture with RLS forced (FR-1.1/1.2/1.3).
AC-2 a session cookie replayed without a valid OIDC session is rejected and no third-party token is exposed to the browser (BFF token-custody check) (FR-1.1).
AC-3 a query issued with no `SET LOCAL` tenant context returns zero rows and emits a policy-violation audit event (FR-1.4).
AC-4 onboarding a new user provisions exactly one RelayInbox address bound to that `tenant_id` (FR-1.5).

### FR-2 Profiles, preferences & third-party credential vault

- **FR-2.1** The system shall store per-user profile attributes and taste preferences (onboarding attribute-preferences, explicit affinities, and implicit attended/declined signals) as ranking inputs under RLS (`d07`).
- **FR-2.2** The system shall store every third-party credential under **KMS envelope encryption** with a pooled CMK, a **per-tenant DEK**, and `tenant_id` + `credential_type` passed as **KMS encryption context**, so a decrypt scoped to tenant A cannot read tenant B (`d05`).
- **FR-2.3** Where a source offers OAuth (Meetup, Google), the system shall store an OAuth refresh token and shall **not** store a raw third-party password; it shall persist **exactly one refresh token per user per client ID** and never re-run consent for an already-connected user (`d05`, `d12`, `d17`).
- **FR-2.4** Where a source is browser-only and passwordless via **email magic-link/OTP** (Luma), the system shall prefer a **short-TTL session cookie** over a stored password, reuse a captured cookie only from the same worker identity, and store a password only as a re-auth fallback (`d14`). Partiful's login is **SMS-only** (`d16`: Twilio SMS ingestion or human-handoff, on the identical coordination as the RelayInbox); because Partiful is disabled by default (FR-5.6), no SMS-ingestion path is built at launch.
- **FR-2.5** When a browser worker must supply a credential, the system shall use a **non-LLM injection broker**: the reasoning loop emits `{{username}}`/`{{password}}` placeholders; the broker unwraps the per-tenant DEK, decrypts into a locked (`mlock`, `MADV_DONTDUMP`) buffer, verifies the live URL by **CDP domain-pinning** against the credential's bound origin, types via Playwright `fill()`, and zeroizes the buffer and DEK immediately after typing (`d14`).
- **FR-2.6** The system shall structurally exclude every plaintext secret from LLM prompts, tool arguments, Temporal activity inputs/history, and logs (`d05`, `d14`).
- **FR-2.7** The system shall run each browser login/RSVP session in **one ephemeral Firecracker (or gVisor) microVM per `(user, event)`** with no cross-tenant coresidency, fronted by a **mandatory egress proxy** whose per-session allowlist is the **target event origin plus the source's registered first-party asset domains only** — the guest session never reaches the KMS endpoint, since the non-LLM injection broker performs every KMS call from the siloed vault network segment, not from inside the session (`d14`; corrected v0.3 to match ADR-006).
- **FR-2.8** If a login attempt fails, or MFA/CAPTCHA is encountered, then the system shall mark the credential `needs_reauth`, halt autonomous retries, and emit a human-handoff task (`d14`).
- **FR-2.9** The system shall record a first-class **consent record** (per-source, per-user, per-scope, timestamped) before acting on a user's behalf against any source (`d10`, `d14`).
- **FR-2.10** When a user requests credential deletion, the system shall delete the ciphertext and DEK and revoke stored OAuth tokens within the erasure SLA (NFR-11), leaving a tombstone in the audit log (`d05`).
- **FR-2.11** When a user disconnects a **single** connected source (distinct from account erasure), the system shall revoke that source's stored token/cookie, halt autonomous action for that source only, and leave the account and all other connected sources intact.
- **FR-2.12** The system shall detect **upstream-invalidated credentials** — OAuth revocation, Google `invalid_grant`, an expired/rejected session cookie — proactively on a refresh failure or a periodic health probe, mark the credential `needs_reauth`, and emit a re-consent handoff independent of any in-flight registration; for the password-fallback case it shall treat a rejected password as `needs_reauth` and require re-capture (FR-2.13) rather than silent reuse (`d14`).
- **FR-2.13** When a user connects a **browser-only, non-OAuth source** (e.g. Luma), the system shall capture the initial credential (session cookie captured via a first-login human-handoff, or a stored-password fallback) through the account-linking flow, create the consent record (FR-2.9) at that moment, and encrypt the credential into the siloed vault (FR-2.2) before any autonomous use; this path is gated on RelayInbox acceptance (G3) since sign-up-with-relay-inbox is its precondition (`d14`, `d16`).

*Acceptance:*
AC-5 a credential-decrypt call presenting tenant A's `tenant_id`/`credential_type` context cannot decrypt tenant B's ciphertext (KMS encryption-context negative test) (FR-2.2).
AC-6 a browser-login fixture drives a full RSVP with the credential injected by the broker while a captured LLM transcript, tool-arg dump, Temporal history export, and application log contain zero occurrences of the plaintext secret (FR-2.5/2.6).
AC-7 a domain-pinning fixture that redirects the login page to a non-bound origin aborts injection and raises human-handoff with no secret released (FR-2.5).
AC-8 a failed-login fixture flips the credential to `needs_reauth`, issues no further autonomous attempt, and emits a handoff task (FR-2.8).
AC-9 an OAuth source connected twice for one user yields exactly one stored refresh token; a re-consent path is exercised only on `invalid_grant` (FR-2.3).
AC-10 a credential-deletion request removes ciphertext + DEK, revokes tokens, and leaves an audit tombstone within the SLA (FR-2.10).
AC-11 a fixture user whose onboarding preferences favor a category receives a ranked list whose retrieval/scoring inputs demonstrably reflect those stored preferences (FR-2.1).
AC-12 a Luma link fixture prefers the captured short-TTL cookie for injection and falls back to the stored password only after the cookie is rejected, never storing a password when a cookie is available (FR-2.4).
AC-13 a two-tenant browser-session fixture proves no two `(user, event)` sessions share a microVM/kernel, and an egress attempt to a non-allowlisted host from within a session is blocked (FR-2.7).
AC-14 a user disconnecting Meetup revokes only the Meetup token, halts autonomous Meetup action, and leaves the account plus other sources fully usable (FR-2.11).
AC-15 a periodic health probe against an out-of-band-revoked OAuth token (no in-flight workflow) flips the credential to `needs_reauth` and emits a re-consent handoff (FR-2.12).
AC-16 connecting a Luma account end-to-end captures the initial cookie via first-login handoff, writes a consent record at capture time, and lands the credential encrypted in the vault before any autonomous RSVP (FR-2.13).

### FR-3 Event discovery

- **FR-3.1** The system shall expose one `SourcePort.discover()` per source and shall **deterministically select the adapter** (API preferred, browser fallback) from the source's `automation_allowed` capability flags — never by model choice (`d08`, `d10`).
- **FR-3.2** The `SourcePort` selector shall **refuse the browser adapter** for a source whose browser modality is not ToS-sanctioned: for the credentialed **Meetup action lane**, because browser RSVP is prohibited and autonomous RSVP belongs only to the API path; for **Eventbrite**, because the consumer **ToS §13.1 bans browser automation** and Eventbrite exposes no usable API modality (public search API killed 2019, no free-order endpoint), so Eventbrite discovery routes through the SerpApi cross-source funnel (FR-3.6), not an Eventbrite API (`d10`, `d11`, addendum). The exact anonymous public-page catalog read in FR-3.10 is not a credentialed browser RSVP adapter.
- **FR-3.3** The system shall run a scheduled, geo/category-sharded **read-through catalog crawl** of shared-app-key API sources (Ticketmaster, and SeatGeek when enabled) into the local schema.org/`Event` store, and shall serve all tenant discovery reads from that cache rather than fanning out N×M user requests to N×M source calls (`d15`).
- **FR-3.4** While crawling Ticketmaster, the system shall respect `5 rps`, the `5,000 calls/day` app-key budget, and the `size × page < 1000` deep-paging cap, partitioning by facets rather than deep-paging (`d11`, `d15`).
- **FR-3.5** The system shall route credentialed per-user-specific discovery (Meetup, Luma) against **each user's own stored OAuth/session credential**, never a shared token, and shall not promote the resulting rows into the tenant-neutral catalog (`d15`).
- **FR-3.6** The system shall run a SerpApi `google_events` sweep as a **cross-source top-of-funnel**, de-duplicating results across providers before per-source enrichment (`d03`, `d11`).
- **FR-3.7** The system shall normalize every retrieved CandidateEvent through an **Anti-Corruption Layer** onto canonical schema.org/`Event`, preferring a page's existing JSON-LD `Event` block over DOM scraping (`d08`).
- **FR-3.8** The system shall **de-duplicate CandidateEvents into CanonicalEvents before ranking** — blocking by city/date, matching on fuzzy title + description-embedding cosine + time/geo delta — assigning each a stable `canonical_event_id`, and shall retain **all** per-source registration URLs on the merged CanonicalEvent (`d07`).
- **FR-3.9** While a source's `automation_allowed` for a modality is disabled (ToS change, ban wave), the system shall exclude that source-modality from discovery and register routing without a code deploy (`d10`).

### FR-4 Ranking, personalization & conflict gate

- **FR-4.1** The system shall retrieve candidates with **hybrid retrieval** — pgvector dense ANN plus Postgres `tsvector`/BM25 — fused by **Reciprocal Rank Fusion (k ≈ 60)** to ~100–200 candidates (`d07`).
- **FR-4.2** The system shall re-rank the fused set with a **cross-encoder** (Cohere Rerank v3.5) behind a swappable `Ranker` port, and shall use an LLM listwise pass only as a final **top-10** diversity/clash tie-break, not as the primary ranker (`d07`).
- **FR-4.3** The system shall apply a per-user feature-based **re-scoring layer** (LightGBM/LambdaMART) over user↔event embedding cosine + explicit affinities + implicit signals (`d07`).
- **FR-4.4** When a user has insufficient history, the system shall **cold-start** ranking from onboarding attribute-preferences + content-based metadata + LLM test-time intent inference from the EventRequest (`d07`).
- **FR-4.5** Before any registration/RSVP, the system shall call **`freeBusy`** over the candidate window across all the user's connected calendars and shall, when a candidate **hard-overlaps** a busy block, **BLOCK** that candidate — it shall never attempt an RSVP for a hard-overlapping candidate (the **mandatory pre-registration conflict gate**); deprioritization is used only as a soft ranking preference for near-adjacent / tentative / transparent conflicts, not as the hard gate (`d06`).
- **FR-4.6** The system shall evaluate ranking against the EventRequest's parsed hard constraints (time window, geo, budget=free at launch, explicit filters) and shall never return a CanonicalEvent that violates a hard constraint.

### FR-5 Registration selection, RSVP execution & honest-split routing

- **FR-5.0** When an EventRequest yields a ranked candidate set, the system shall **autonomously select the single highest-ranked CanonicalEvent** that passes the conflict gate (FR-4.5) and hard constraints (FR-4.6) for registration, and shall **fall through to the next-ranked candidate** on registration failure/conflict up to a policy-bounded attempt budget **[owner target: ≤ 3 attempts]**. When a selected CanonicalEvent is registerable through more than one `(source, modality)` (FR-3.8 retains all per-source URLs), the system shall deterministically **prefer the autonomous-on-SLA lane, then browser-best-effort, then human-handoff**, honoring per-source `automation_allowed`. When no candidate is registerable within the attempt budget, the workflow shall reach a terminal state — a human-handoff task if any candidate is handoff-eligible, otherwise `failed_no_candidate` with a no-result notification (FR-6.6) (decision 7; `d10`, `d17`).
- **FR-5.1** The system shall route each `(user, CanonicalEvent, chosen source)` to exactly one **RSVP lane** by a deterministic decision over `(source, modality, group-condition)`: autonomous-on-SLA, browser-best-effort, or human-handoff (`d10`, `d11`, `d17`).
- **FR-5.2** For **Meetup**, the system shall RSVP via the API `createEventRsvp` under the user's own OAuth token with `member_id` omitted, and shall attempt it **only when the user is already a member** of the group; approval-gated, screening-question, or dues-required groups, and non-member groups absent a positive G2 spike result, shall route to human-handoff (`d11`, `d17`).
- **FR-5.3** Before a Meetup RSVP mutation, the system shall **read the RSVP/membership state** (read-before-mutate guard) and shall treat a `CONFIRMED` state as an idempotent no-op (`d17`, addendum G2 contingency).
- **FR-5.4** For **Luma**, the system shall register via the browser adapter (Computer Use + DOM) as **best-effort, off the SLA**, with human-handoff on failure (`d11`).
- **FR-5.5** For any browser RSVP, the system shall apply the **detect-then-submit** rule: on every attempt re-run a read-only detect of the "You're going" / RSVP marker — `CONFIRMED` ⇒ idempotent no-op, `NOT_PRESENT` ⇒ submit, `AMBIGUOUS` ⇒ durable signal to human review — and shall **never blind-re-POST** (`d13`).
- **FR-5.6** For **Eventbrite** and **Partiful**, the system shall not attempt an autonomous register: Eventbrite is discovery-only with register routed to human-handoff, and Partiful is disabled by default (ToS bans robots; SMS-only login) (`d10`, `d11`).
- **FR-5.7** When a source requires an email OTP or magic-link to log in or confirm, the system shall ingest it via the **RelayInbox** (`EmailIngestionPort`): sender-domain allowlisted, OTP/magic-link **deterministically extracted** without forwarding raw HTML to any LLM, and delivered as a durable workflow signal (`d16`).
- **FR-5.8** The system shall treat a magic-link/OTP as a short-TTL secret: never logged, never placed in an LLM prompt/tool-arg, expired after use (`d16`).
- **FR-5.9** Before executing any register/RSVP activity, the system shall evaluate the **policy engine** (`automation_allowed` for the chosen modality, per-user limits, kill-switch) and shall short-circuit an in-flight `(user, event)` workflow to human-handoff if the action is no longer permitted (`d04`, `d10`).
- **FR-5.10** When a register/RSVP flow encounters a **payment/price surface** while `paid_allowed=false` (mis-tagged free metadata, tiered free/paid ticket, donation wall), the activity shall **abort without submitting**, route to human-handoff, and record the free/paid discrepancy — an execution-time free-only guard distinct from the ranking-time budget filter (FR-4.6) (decision 4; `d04`).

### FR-6 Human-handoff, notification & inbound interface (first-class)

### FR-11 Attendance loop & cancel hygiene (D1 — extends FR-8 lifecycle)

- **FR-11.1** For every `(user, event)` in `scheduled` state, the system shall send an **attendance-confirmation nudge** at **[owner target: T-24h]** over the notification channel (FR-6.6) and shall treat the event as unconfirmed after a **[owner target] non-response window** (`d24`, `d25`).
- **FR-11.2** When a user declines the nudge, does not respond within the window, or a **post-registration user-side hard calendar conflict is detected (FR-11.7)**, the system shall trigger the **withdrawal path (FR-8.8)** — un-RSVP where the source permits, else a withdrawal handoff — and remove the calendar entry, recording the reason.
- **FR-11.3** The system shall enforce a **per-user concurrent-open-RSVP cap** at **[owner target]** count as a policy limit (FR-7.1); an autonomous RSVP that would exceed it shall route to handoff or be declined per policy, never silently breach the cap.
- **FR-11.4** The system shall maintain a **per-user attendance score** derived from the attendance-outcome signal (FR-11.6) and shall use it to **throttle autonomy** — a score below a **[owner target] demotion threshold** demotes that user's lanes **toward human-handoff** (a soft, policy-driven governor, never a hard ban). The score and its inputs are behavioral PII, **erasable under FR-10.5** and audit-tombstoned under its crypto-shred reconciliation.
- **FR-11.5** All attendance-loop actions (nudge, auto-un-RSVP, score-driven demotion) shall be **policy-gated (FR-5.9), kill-switch-honoring (FR-7.2), and audit-logged (FR-7.3)** exactly as first-party registrations are.
- **FR-11.6** The system shall derive the attendance outcome (`attended` / `no_showed` / `late_cancelled`) from a defined signal — a **post-event attended/no-show confirmation over the notification channel (FR-6.6)** and/or an organizer/source no-show signal where exposed — never from the T-24h intent nudge alone (which confirms intent, not attendance).
- **FR-11.7** For every `(user, event)` in `registered`/`scheduled` state, a **user-side calendar change ingested via FR-9.4** shall re-run the **FR-4.5 `freeBusy` conflict check** against the scheduled concierge event, and on a new hard overlap shall fire the FR-11.2 withdrawal/notification path — closing the gap where FR-8.7a detects only organizer-side changes.
- **FR-11.8** The system shall accept, over the channel-independent inbound contract (a reply to the nudge/notification or an authenticated consumer-web command where exposed, on the FR-6.7 mechanism), a **nudge confirm/decline** and a **post-event attended/no-show self-report**, feeding the withdrawal path (FR-11.2) and the attendance-outcome signal (FR-11.6) respectively (NFR-16).

*Acceptance:*
AC-76 a scheduled event at the nudge horizon triggers exactly one confirmation nudge over the notification channel; a non-response past the window, and equally a user reply DECLINING the nudge over the FR-11.8 inbound channel, triggers the withdrawal path and calendar removal (FR-11.1/11.2/11.8).

## 5. Non-functional requirements

Each NFR names its ISO/IEC 25010:2023 characteristic, a measured target, and a measurement basis. Provisional product goals are **[owner target]**; evidence-backed numbers cite their dossier.

- **NFR-1 Discovery freshness & latency (Performance efficiency — time behaviour).** For catalog-cache-backed sources, a newly-published event shall be discoverable within **[owner target: ≤ 6 h]** of the scheduled crawl cadence; an interactive EventRequest shall return a ranked list within **[owner target: p95 ≤ 5 s]** when served from the cache and pgvector index. Measurement: crawl-to-index timestamp delta per source; end-to-end request latency histogram over a synthetic request corpus. The catalog crawl is launch architecture, not optimization (`d15`).

- **NFR-2 Two SLA classes (Reliability — availability + Performance efficiency).** The system operates two distinct SLA classes: **(a) autonomous lane** (Meetup member-group API RSVP) with an RSVP success-rate and completion-latency target that is **DEFERRED pending gates G1 and G2** (§8) and shall not be fixed until the realized request-mix and Meetup quota scoping are measured; **(b) handoff lane** with a **time-to-handoff-task-available** target of **[owner target: p95 ≤ 60 s]** from routing decision **and a time-to-user-notified** target of **[owner target: p95 ≤ 120 s]** from routing decision (delivery, not just enqueue). Browser-best-effort registrations are explicitly **off the reliability SLA** (`d10`, `d17`). Measurement: per-lane success/latency dashboards partitioned by lane; handoff-task creation latency; notification-delivery latency from the delivery channel (FR-6.6).

- **NFR-3 Availability (Reliability — availability).** Product control plane and discovery/ranking API shall meet **[owner target: 99.9% monthly]** availability; the durable-execution engine's guarantees back lifecycle continuity across worker restarts. Measurement: **synthetic canary probes at [owner target: 1-min cadence]**; a minute counts as **down** if **[owner target: > 50%]** of that minute's probes fail (error or latency > **[owner target: p99 SLO]**); availability = up-minutes ÷ total-minutes over a calendar month, alerting on burn against the monthly error budget.

- **NFR-4 Anthropic-model capacity (Performance efficiency — capacity; Flexibility — scalability).** At **[owner target: 100k users]** the system shall provision Anthropic on **Scale (10k RPM / 10M ITPM / 2M OTPM per model class)**, treating **ITPM/OTPM — not RPM — as the binding constraint**, with cache-read tokens excluded from ITPM, and a **Batch API pool** (separate from interactive) for ranking + post-RSVP summarization; the derived Sonnet load fits Scale with headroom at 100k, mitigated by caching + Batch + workspace sharding, then Custom for the next order of magnitude (`d15`; the precise ITPM-per-user derivation and the exact binding user-count are confirmed at design). Measurement: load simulation asserting interactive ITPM stays under the Scale ceiling with cache-reads excluded and Batch traffic off the interactive pool.

- **NFR-4a Source-quota capacity (Performance efficiency — capacity).** Ticketmaster's single global **5,000-calls/day** app-key shall be absorbed by the central read-through cache so it does not bind before ~4–5k users on a naive path (`d15`); per-user OAuth sources (Meetup, Luma) shall fan out against each user's own token so their quota is per-tenant. Measurement: load simulation proving added tenants add zero live TM calls (cache-served) and per-user-source calls scale with the requesting user's own token, not a shared one.

- **NFR-4b Browser-concurrency capacity (Performance efficiency — capacity; Safety — fail-safe).** The browser (Computer-Use) concurrency pool is a **first-class, independently-scaled resource kept OFF the SLA**. It shall be **provisioned to the `d15`-derived peak concurrency (~135 concurrent at 100k users**, Friday-peak derivation, `d15` line 53) — **not** to a steady-state average — because peak is the sizing basis for a saturation-fail-safe pool. This peak **exceeds the Browserbase Startup 100-session ceiling**, so the pool shall move to **Scale 250+ or a self-hosted Chromium fleet at the ~100-concurrent self-host threshold** (`d15` design implication 7); on saturation, new browser RSVPs fail over to human-handoff (FR-6.4), never breaching the autonomous-lane SLA. Measurement: load simulation ramping to peak concurrency, asserting the pool is sized to ~135 (not ~40/steady-state), that crossing ~100 concurrent triggers the self-host/Scale-250 path, and that saturation routes to handoff.

- **NFR-5 Cost envelope (Performance efficiency — resource utilization).** Cost-per-confirmed-RSVP is a first-class tracked SLO, stated as **per-lane bounds** (a single blended range is avoided because the browser sub-range exceeds any blended ceiling): **API-lane ≤ $0.12 per confirmed RSVP**, **browser-lane ≤ $0.40 per confirmed RSVP**, **blended ≤ $0.20** (`d15` line 55: API ~$0.05–0.12, browser ~$0.15–0.40, blended ~$0.10–0.20). Alert when any lane's rolled-up per-RSVP cost breaches its bound. Reduce via Batch + prompt caching; model tiering routes Haiku to parse/extract/dedup, Sonnet to default register reasoning, Opus only to hard/failed cases (`d09`, `d15`). Measurement: per-RSVP token+infra accounting rolled up per lane, each checked against its numeric bound.

- **NFR-6 Credential & injection security (Security — confidentiality, resistance).** No plaintext secret shall appear in any prompt, tool-arg, workflow history, or log; every credential shall be KMS-envelope-encrypted with a per-tenant DEK and `tenant_id`+`credential_type` encryption context; browser sessions shall run one ephemeral microVM per `(user, event)` with egress allowlisted to **the target event origin plus the source's registered first-party asset domains only** — the guest session never reaches the KMS endpoint, which the non-LLM injection broker calls from the siloed vault segment (corrected v0.3 to match FR-2.7/ADR-006); plaintext shall be zeroized immediately after injection (`d05`, `d14`). Measurement: automated secret-scan of transcripts/logs/histories in CI; KMS encryption-context negative tests; egress-allowlist assertion (including a negative assertion that the KMS endpoint is NOT reachable from within a session); two-tenant coresidency isolation test (AC-13).

- **NFR-7 Tenant isolation (Security — confidentiality; Safety — fail-safe).** There shall be **zero cross-tenant data leakage**: RLS forced with a non-owner non-`BYPASSRLS` role, `SET LOCAL` per transaction, `tenant_id` leading-indexed; a missing tenant context fails closed to zero rows (`d05`). Measurement: adversarial two-tenant test suite; query-plan audit for the leading `tenant_id` index.

- **NFR-8 Durability & idempotency (Reliability — recoverability; Maintainability).** No lifecycle event shall be lost and no side effect executed twice: at-least-once activities + idempotent upserts keyed by workflow-minted keys, transactional outbox as system of record, engine-level `workflowId` idempotency, browser detect-then-submit, API read-before-mutate (`d13`, `d08`). Measurement: crash-injection tests asserting exactly-once effects; outbox redelivery convergence test.

- **NFR-9 Extensibility (Maintainability — modularity, reusability; Flexibility — replaceability).** Adding a new source shall be **one new adapter module + one capability-registration entry**, with zero orchestrator edits; storage and calendar providers sit behind ports (Postgres/pgvector, CalendarPort, EmailIngestionPort) so a provider swap is an adapter change, not a domain rewrite (`d08`). Measurement: add-a-source integration fixture + code review; port contract tests against recorded fixtures.

- **NFR-10 Auditability & non-repudiation (Security — accountability, non-repudiation).** Every registration/RSVP, policy decision, credential access, and lifecycle transition shall be traceable to an immutable audit entry carrying consent ref, idempotency key, workflow ID, and OTel `tenant_id`-tagged span; erasure is reconciled with immutability by crypto-shredding PII fields while retaining non-PII operational fields (FR-10.5) (`d04`, `d08`). Measurement: audit-completeness assertion over an end-to-end fixture (every action has exactly one immutable entry); post-erasure assertion that operational fields survive and PII fields are shredded.

- **NFR-11 Privacy & GDPR/CCPA (Security — confidentiality; Safety — operational constraint).** Credential deletion and data-subject erasure (credentials, PII, RelayInbox contents, stored OAuth tokens, lifecycle/event history, concierge-written calendar entries, audit PII fields, and the FR-10.5 behavioral-PII categories — attendance score/history, standing watches, notification preferences, imported affinity signals) shall complete within **[owner target: ≤ 72 h]**, propagate to a tombstone in the audit log, and revoke tokens; KMS-separate-from-ciphertext yields breach-notification safe harbor (`d05`). Measurement: erasure fixture verifying purge + revocation + propagation within SLA.

- **NFR-12 Google sensitive-scope verification gate (Compatibility — interoperability; Safety — risk identification).** The product shall be published to **Production** (never shipped on Testing, where calendar refresh tokens expire in 7 days) and shall pass **sensitive-scope app verification** — a pre-launch critical-path gate, brand/consent (~2–3 business days) then sensitive-scope review (nominal "up to 10 days", **plan 3–6 weeks wall-clock**) (`d12`). Measurement: verification submitted and approved before public launch; milestone tracked on the launch plan.

- **NFR-13 Disaster recovery (Reliability — recoverability).** RPO **[owner target: ≤ 60 s of committed workflow/audit/vault state; zero committed-and-acknowledged transactions lost]** for lifecycle/audit/credential-vault stores, guaranteed by a backup/checkpoint cadence no coarser than the RPO bound; restore-to-serving within RTO **[owner target: ≤ 24 h]**; projections and product API rebuildable from restored durable-engine history + outbox + relational stores. Distinct from deferred multi-region HA (§6), which does **not** exempt this objective. Measurement: restore drill from backups asserting the seconds-bounded RPO, the RTO, and rebuildability.

- **NFR-14 Compatibility & interoperability (Compatibility — co-existence, interoperability).** All events shall be normalized to canonical schema.org/`Event` through the ACL; calendar writes shall interoperate on the **Google adapter at launch** with correct IANA time zones, and the Microsoft Graph and Apple CalDAV adapters shall satisfy the CalendarPort **port contract** (feature-flagged, post-launch) (`d06`, `d08`; §6). Measurement: round-trip ACL conformance tests; Google cross-write fixture at launch; Graph/CalDAV port-contract fixtures.

- **NFR-15 Safety — action fail-safe (Safety — fail-safe, hazard warning).** A source ban, credential revocation, injection-detection, unexpected paywall, or browser-pool saturation shall **fail safe** to human-handoff and shall never cascade to an autonomous-lane SLA breach or a ToS-violating action; the kill-switch freezes actions without a deploy (`d10`, `d14`, `d15`, `d17`). Measurement: fault-injection suite (ban, revocation, saturation, injection, paywall) asserting handoff fallback and no prohibited action.

- **NFR-16 Interaction capability — bounded consumer-web floor (Interaction capability — operability + user-error protection).** The local consumer-web MVP shall provide logical keyboard navigation and focus restoration, visible high-contrast focus, programmatic status/error announcements, reduced-motion support, truthful preview/durable/lifecycle language, and layouts without horizontal overflow at the supported desktop and 390 px mobile viewports. Measurement: static DOM/ARIA and asset checks plus the committed Playwright CI gate at the supported viewports. This evidence is **not** a claim of complete WCAG conformance or production identity safety; the deployment-level real-IdP/Redis/edge canary for the built-in BFF/CSRF path in AC-101 remains required before public launch.

- **NFR-17 Organizer-change detection freshness (Reliability — availability; Performance efficiency — time behaviour).** For every `(user, event)` in `registered`/`scheduled` state, an organizer cancel/reschedule shall be reflected into a reconcile within **[owner target: ≤ 6 h]** on the poll path and near-real-time where a source webhook exists (FR-8.7a). Measurement: inject a source-side reschedule/cancel and assert the reconcile fires within the cadence for each launch source's declared detection modality.

- **NFR-18 Supply resilience & source concentration (v0.3, D8) (Reliability — availability; Performance efficiency — capacity).** The per-source per-metro concentration cap **[owner target: ≤ 40%]** of a metro's served candidate supply is a **soft alerting threshold** (FR-18.2): breaching it raises a supply-risk flag, never a candidate drop. A single source's degradation or quarantine (FR-10.3) shall not drop that metro's coverage below a **[owner target] coverage floor** — a minimum served on-taste-candidates-per-standard-request (or a per-metro coverage index) — the scrape-war failure mode (`d23`). Measurement: per-source per-metro supply-share monitoring with a cap alert (assert no candidate is dropped to enforce the cap); a source-quarantine fault-injection asserting metro coverage stays above the floor via the remaining sources.

## 6. Out of scope (v1)

Explicit non-goals. Some deferrals do **not** exempt related obligations — noted inline.

- **Autonomous paid ticket purchase.** The payment port ships as a stubbed forward-looking abstraction behind `paid_allowed` (default off). No SCA/3DS, chargeback, or BOTS-Act machinery is built (decision 4; `d04`).
- **Partiful autonomous register** (ToS bans robots; SMS-only login; disabled by default — no SMS-ingestion path built at launch) and **Eventbrite autonomous register** (no free-order endpoint + browser ToS §13.1 ban ⇒ discovery-only via SerpApi, register-handoff) (`d10`, `d11`).
- **Meetup non-member / approval / screening / dues-group auto-join** (no `joinGroup` API surface; each a human/payment gate) (`d17`).
- **Native mobile applications and public production web launch.** P46–P48 include the local same-origin consumer-web MVP, repository-owned OIDC BFF/CSRF path, and browser gate specified by FR-19/NFR-16; public web launch remains gated on real IdP/Redis/HTTPS-edge configuration and canary evidence for that built-in path, real providers and credentials, and the external evidence in the production runbook.
- **Microsoft Graph and Apple/iCloud CalDAV calendar adapters as shippable launch surfaces.** The CalendarPort abstraction and the **Google adapter** are the launch floor; Graph (needs Publisher Verification) and CalDAV (app-specific-password, off SLA) are **feature-flagged, validated only as port-contract fixtures** at launch (FR-9.5, NFR-14).
- **Multi-region high availability.** Does **not** exempt NFR-13 backup/restore (RPO/RTO).
- **SeatGeek / Songkick partner-gated licenses** — feature-flagged, not a launch floor (`d11`).
- **Advanced learning-to-rank personalization** beyond the baseline LightGBM re-scoring layer — design-phase tuning (`d07`).

## 7. Settled since research (evidence outcomes that pin requirements)

- **Per-source launch matrix is definitive (`d10`, `d11`, `d17`).** Meetup register = API-only `createEventRsvp`, per-user OAuth, **member-scoped, on SLA**; Ticketmaster = discovery-only; SerpApi = cross-source funnel; Luma = browser best-effort off SLA; Eventbrite = discovery-only (via SerpApi) / register-handoff; Partiful = disabled by default (SMS-only login). `automation_allowed` is per-source, per-modality.
- **Meetup RSVP is membership-gated with no `joinGroup` mutation (`d17`).** The on-SLA autonomous-register surface shrinks to "groups the user is already in"; approval/screening/dues/non-member ⇒ human-handoff. The single Pro-gated OAuth consumer is a revocable, commercial-use-restricted single point of failure that must degrade to handoff, never cascade to an SLA breach.
- **Durable spine = Temporal Cloud primary, DBOS documented fallback (`d13`).** One workflow per `(user, canonical_event_id)`, `workflowId` idempotency, claim-check for the 2 MB payload cap, saga with compensation, durable-timer+signal confirmation waits, browser **detect-then-submit** and API **read-before-mutate** to bound double-RSVP. Engine choice is treated as settled; O-6 now confirms sizing/limits, not the vendor.
- **Calendar-only Google scopes are sensitive, not restricted (`d12`)** — dodging CASA Tier 2 (corrects wave 1), but still requiring **sensitive-scope app verification** (~3–6 weeks wall-clock, pre-launch), Production publishing (Testing's 7-day refresh-token expiry is disqualifying), one refresh token per user, and a permanent no-Gmail-scope rule.
- **Credentials = BUILD a non-LLM KMS-envelope injection broker (`d14`)** with CDP domain-pinning, one ephemeral Firecracker/gVisor microVM per session (~125 ms boot, <5 MiB overhead), egress allowlist, CaMeL dual-LLM boundary, and post-injection zeroization; OAuth wherever offered so no password is stored (1Password Agentic Autofill rejected for the unattended path).
- **Login-code ingestion = per-user RelayInbox (`d16`)** (SES→S3→Lambda / Cloudflare Email Routing), deterministic OTP/magic-link extraction, Temporal signal — sidestepping Gmail restricted scopes; magic-link treated as a short-TTL secret; email is an untrusted injection vector. Partiful's SMS-only login is not covered by the RelayInbox and needs no path at launch (disabled by default).
- **Capacity: TM central catalog cache is launch architecture (`d15`).** Ticketmaster's shared 5,000/day binds first (~4–5k users) on a naive path; per-user OAuth sources fan out per token; Anthropic Scale sizing with ITPM/OTPM binding and cache-read exclusion; browser concurrency (~75–100k users) is the real operational ceiling, kept off SLA and **provisioned to the ~135-concurrent Friday peak at 100k** (not a steady-state average). Blended **~$0.10–0.20/confirmed RSVP** (API ~$0.05–0.12; browser ~$0.15–0.40).
- **Legal risk is contract + trespass + account/IP ban, not CFAA (Van Buren; hiQ $500k non-CFAA judgment) (`d10`).** Enforcement is per-user human-cadence pacing + quarantine-on-ban; never IP rotation/block circumvention.
- **Ranking = pgvector hybrid RRF (k≈60) + Cohere cross-encoder + LightGBM re-scoring (`d07`)**, dedup-before-ranking retaining all per-source URLs, mandatory `freeBusy` conflict gate as a hard block (`d06`).
