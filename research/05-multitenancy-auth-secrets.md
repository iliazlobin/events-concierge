# Multi-Tenancy, Authentication & Custody of Users' Third-Party Credentials

> The Events Concierge acts autonomously on behalf of many users using their own third-party logins and calendars; how tenants are isolated and how their credentials are stored is the single largest determinant of blast radius, regulatory exposure, and whether the product can ship at all (Google CASA gate).

## Verified findings

### Isolation topology — bridge model

- **Adopt a bridge isolation posture: pool the application plane behind row-level tenant isolation, but SILO the credential vault.** [confirmed] AWS's SaaS Tenant Isolation Strategies whitepaper frames three models — POOL (shared resources, isolation enforced logically at the row/item level; most efficient and scalable, but isolation depends on a correctly-enforced runtime control, not a physical boundary), SILO (dedicated resources per tenant; maximum isolation, highest cost, for highly-regulated data), and BRIDGE (mix per resource — "the values and tenets of silo isolation still apply" to the siloed pieces while the rest is pooled, verbatim from the bridge page). The pool page explicitly warns you "can't lean on the typical networking and IAM constructs to create boundaries between tenants" and must be "especially diligent about ensuring that resources are isolated." For an agent product the natural split is: pool user profiles/preferences/event-lifecycle rows behind Postgres RLS, but treat the third-party-credential store as a silo-grade component (its own DB/tablespace, its own KMS key hierarchy, its own network + IAM boundary) because it is the highest-value blast target.
- **One shared control plane regardless of how the application plane is siloed/pooled.** [confirmed] AWS's current SaaS Architecture Fundamentals whitepaper: control-plane services are "global to all of the tenants... shared by all tenants... foundational to SaaS."
- Two caveats that do not change the guidance but belong in the design doc: (1) the tenant-isolation-strategies whitepaper now carries an AWS "historical reference only" banner, though the silo/pool/bridge vocabulary and the control-plane/application-plane split persist unchanged in current AWS guidance (SaaS Architecture Fundamentals, SaaS Lens); (2) AWS's actual language is descriptive, not prescriptive — real decomposed systems "will often" end up as a mix; bridge is not a mandate. The specific split (silo the credential vault; pool everything else) is our idiomatic application of the principle, not an AWS prescription.

### Postgres Row-Level Security for the pooled plane

- **Use RLS with a PER-TRANSACTION tenant context; the mechanics are load-bearing.** [adjusted] Canonical policy: `ALTER TABLE t ENABLE ROW LEVEL SECURITY; CREATE POLICY tenant_isolation ON t USING (tenant_id = current_setting('app.current_tenant')::uuid);`. The four non-negotiables:
  1. **`SET LOCAL` (or `set_config(..., is_local => true)`), NOT plain `SET`.** Plain `SET` is session-scoped and persists on a pooled backend, leaking the previous tenant's context to the next request. `SET LOCAL` is transaction-scoped and resets at commit/rollback. Pin it inside the same transaction as the query — this matters especially under transaction-mode poolers; AWS notes "session variables may be incompatible with server-side connection pooling such as pgBouncer." (Attribute the `SET LOCAL` prescription to Postgres semantics + the Fritzsche piece, not to the AWS blog, which does not distinguish `SET` from `SET LOCAL`.)
  2. **`ALTER TABLE t FORCE ROW LEVEL SECURITY`.** The PostgreSQL docs state table owners bypass RLS by default unless FORCE is set.
  3. **Connect the app as a NON-owner role that lacks BYPASSRLS.** Superusers and BYPASSRLS roles always bypass RLS; reserve BYPASSRLS strictly for migration roles, never for the app or admin.
  4. **Index `tenant_id` as the leading column of a composite index.** RLS injects the tenant predicate as an implicit `WHERE`, so a missing index forces sequential scans.
  Skipping (1)–(3) risks silent cross-tenant leakage.
- **REFUTED (embellished metrics):** the figures "~100x / 2-orders-of-magnitude slowdown" and "no measurable degradation at 500 concurrent connections" are not substantiated by either cited source and should be treated as illustrative, not benchmarked. The Fritzsche article only characterizes the overhead as "negligible" with proper indexing; AWS gives no benchmarks. Note the mechanism: RLS performance is essentially that of the equivalent `tenant_id` filter, so a missing index hurts because of seq scans generally, not because of RLS per se.

### Credential-at-rest encryption — envelope + KMS

- **Store every third-party secret with envelope encryption: a KMS-wrapped per-tenant Data Encryption Key, with `tenant_id` passed as KMS encryption context.** [adjusted] Mechanics: call KMS `GenerateDataKey` (returns plaintext DEK + encrypted DEK), encrypt the secret locally with AES-256-GCM, zeroize the plaintext DEK, store `{ciphertext, encrypted-DEK}` together; the CMK never leaves KMS. Encryption context is non-secret AAD that must be re-supplied identically on `Decrypt` or the call fails, binding each ciphertext to a tenant.
- **CORRECTION — encryption context alone is NOT a cryptographic isolation boundary on a pooled/shared CMK.** [adjusted] Because the context is non-secret, anyone holding `kms:Decrypt` on the shared CMK can supply any `tenant_id`. The per-tenant blast-radius container is only real when IAM/session policy constrains each caller to its own context via the `kms:EncryptionContext:tenant_id` condition key (or, in the per-CMK model, via key-scoped IAM). State this IAM enforcement as load-bearing; do not imply the boundary comes from encryption context by itself.
- **CORRECTION — attribution.** [adjusted] The cited AWS "cost-conscious KMS key strategy" blog actually recommends ONE customer-managed key PER TENANT (consolidated across services via cross-account IAM role delegation) as its headline strategy, mentioning encryption context only as an optional per-service add-on. The pooled-CMK-+-encryption-context pattern is legitimate AWS guidance but comes from the AWS SaaS Lens / multi-tenant SaaS storage guidance, not from that blog.
- **Two granularity strategies:** (a) one CMK per tenant — strongest isolation, ~$1/key/month baseline up to ~$3 with two or more rotations (the blog states "$1 monthly, increasing to a maximum of $3 per month with two or more key rotations" — still current), prohibitive at millions of tenants; (b) pooled CMK + per-tenant DEKs isolated by encryption context PLUS IAM condition-key enforcement — the cheaper at-scale pattern. [confirmed pricing] **Recommendation for this product:** pooled CMK + per-tenant DEK + encryption-context `{tenant_id, credential_type}` + IAM condition-key scoping, with brief data-key caching (AWS Encryption SDK) to bound KMS call volume/latency.
- **HashiCorp Vault Transit is the multi-cloud equivalent** [confirmed] — encryption-as-a-service, keys never leave Vault, DEK/EDK client-side envelope pattern, and convergent+derived keys for context binding.

### The riskiest data — passwords/cookies for API-less sites

- **Passwords and session cookies for API-less sites (Luma, Partiful) that the browser agent must log into autonomously are the highest-risk data; prefer OAuth/token vaulting (Plaid model — never store the raw password).** [confirmed]
- **A server-side autonomous agent cannot be true zero-knowledge**, because it must decrypt the credential to type it into the target site — the server necessarily holds plaintext at use time. If you must store passwords/cookies they must be siloed, HSM/KMS-backed, short-TTL, and treated as breach-critical. [confirmed]
- **Plaid is the cautionary tale.** [confirmed] Plaid's defensible model is credential-token exchange (hands the app a token, not the raw banking password); its screen-scraping mode, which DID capture/store raw credentials, is exactly what drew a $58M class-action settlement. Plaid Core Exchange remains token-based.
- **Do not over-trust the vault primitive.** [confirmed] ETH Zurich / USI research (Feb 2026) demonstrated 12 attacks on Bitwarden, 7 on LastPass, 6 on Dashlane (three managers serving ~60M users), directly challenging "zero-knowledge encryption" claims, with the majority allowing full password recovery. Precision note: the threat model is a MALICIOUS/COMPROMISED SERVER that deviates from expected behavior during client interaction, not passive theft of at-rest vault ciphertext, and several findings are integrity/password-change violations rather than pure plaintext recovery. The design directive ("don't over-trust the primitive") stands.
- Supporting color (well-established, not independently drilled): browser-stored credentials + session cookies are the #1 infostealer target; MITRE ATLAS 2025 flags session-cookie replay across federated IdPs and compound/non-human-identity credential sprawl as agent-specific risks. (researcher confidence: high)
- **Design directives:** (1) never store a raw third-party password when OAuth exists; (2) for password/cookie sites, store in the siloed KMS-envelope vault, decrypt only in-memory inside the browser-automation worker, never log, zeroize after use; (3) prefer capturing and reusing a scoped SESSION COOKIE with short TTL over the long-lived password, re-auth on expiry; (4) expect bot-detection friction — servers now emit cookie indicators marking autonomous clients.

### Google CASA gate for Calendar/Gmail scopes

- **Requesting `calendar.events` and any Gmail scope forces the app through Google's CASA Tier 2 assessment — a third-party DAST scan re-required every 12 months.** (researcher confidence: high) Google routes sensitive/restricted OAuth scopes (Gmail, Drive, Calendar, Contacts) through the App Defense Alliance CASA framework. `calendar.events` and `gmail.modify` trigger CASA Tier 2, requiring a third-party Dynamic Application Security Testing scan by an authorized lab plus OAuth-consent-screen verification, and re-verification/re-assessment at least every 12 months after the Letter of Assessment approval date. This is a hard product gate that shapes architecture, timeline, and cost.
- **Operational OAuth facts to design around:** Google enforces ~100 refresh tokens per (Google account + OAuth client ID) — exceeding it silently invalidates the OLDEST token; OAuth clients inactive 6 months are auto-deleted; a refresh token unused 6 months expires; changing the user's Google password invalidates refresh tokens carrying Gmail scopes. **Directive:** request the minimum scope set, store exactly ONE refresh token per user per client (don't churn them), and build refresh-failure / re-consent handling as a first-class lifecycle path.

### Product's own auth — OIDC + BFF

- **Product auth = OIDC (authentication) + OAuth 2.1 (delegated authz) with a Backend-for-Frontend.** (researcher confidence: high; non-load-bearing) The BFF is a confidential OAuth client: it receives the auth code, exchanges it for tokens, stores them server-side (encrypted session store / Redis), and issues the browser only an httpOnly + Secure + SameSite session cookie. Never put access/refresh tokens in localStorage (XSS liability, OWASP Top 10). The session/JWT carries tenant scope explicitly (`sub`, `tenant_id`, tenant-scoped `role_ids`); resolve tenant exactly once at the request edge and use that same `tenant_id` to drive the RLS `SET LOCAL app.current_tenant` and every cache key. For service-to-service (discovery worker → vault) use OAuth2 client-credentials bearer tokens, scoped per tenant. Keep the JWT SIGNING key separate from the data-at-rest ENCRYPTION key and rotate both on schedule and immediately on suspected leak.

### GDPR / CCPA duties on credential data

- **Encryption buys breach-notification safe harbor; erasure must hard-delete + upstream-revoke; California 2026 adds a mandatory pre-processing risk assessment.** (researcher confidence: high; non-load-bearing)
  - GDPR Art. 33/34: notify the supervisory authority within 72 hours; Art. 34 lets you avoid notifying data subjects if the breached data was encrypted "unintelligible to any person unauthorised to access it" — envelope encryption with KMS-held keys is a direct legal safe harbor, PROVIDED keys were not obtained with the data. California AB 1130 says the same. Strong argument for the KMS/HSM key boundary being physically/administratively separate from the ciphertext store.
  - Right to erasure: account deletion must HARD-delete stored credentials, OAuth refresh tokens, and cookies AND proactively REVOKE those tokens upstream (Google revoke endpoint), not soft-delete rows.
  - From 2026, California (CPRA regs) requires a documented risk assessment before processing that presents significant privacy risk — explicitly including sensitive personal information and automated decision-making for significant decisions. This product's autonomous paid registration on stored credentials squarely qualifies.
  - EU-US Data Privacy Framework remains legally fragile (Safe Harbor and Privacy Shield were both struck down); keep SCCs as a contingency transfer mechanism.

### "What never to store" and blast-radius plan

- **Define a strict "never store" list and a key-rotation/blast-radius plan up front.** (researcher confidence: medium; non-load-bearing) Key hierarchy: Root = KMS CMK (in KMS/HSM, never exported, rotated annually or on incident) → per-tenant DEK (envelope, encryption-context `{tenant_id, credential_type}`) → individual credential encrypted with the DEK via AES-256-GCM. Rotation: rotate CMK on schedule and immediately on suspected compromise; DEK rotation = re-wrap under a new CMK version (KMS automatic rotation re-wraps without re-encrypting data). Blast-radius layers: (1) `tenant_id` encryption context + IAM condition-key scoping so a leaked decrypt capability for one tenant cannot read another's ciphertext; (2) siloed vault DB/network/IAM boundary; (3) short-TTL in-memory decryption in the browser worker. Agent-specific "never store": given ~28.65M hardcoded secrets leaked to GitHub in 2025 and AI-assisted code roughly doubling secret-leak rates, secrets must never enter the LLM prompt/context, logged tool arguments, or agent transcripts — inject them only at the browser-automation boundary. Consider DPoP sender-constrained refresh tokens so a stolen bearer token is unusable without the client key.

## Design implications

1. **Bridge topology.** Pool user/profile/preference/event-lifecycle data behind Postgres RLS in a shared DB; place the third-party-credential vault in a physically/logically SILOED component with its own DB, KMS key hierarchy, network segment, and IAM boundary. It is the system's highest-value blast target.
2. **Credential vault as a dedicated port/adapter** with a narrow interface (`put`/`get`/`revoke` by `{tenant_id, source}`). Plaintext secrets are decrypted only in-memory inside the browser-automation worker and zeroized after use — never persisted decrypted, never logged, never placed in an LLM prompt / tool-arg / transcript.
3. **KMS envelope with a POOLED CMK + per-tenant DEK**, passing `{tenant_id, credential_type}` as encryption context, AND enforcing per-tenant isolation with IAM `kms:EncryptionContext:tenant_id` condition keys (encryption context alone is not a boundary). Use short-lived data-key caching to bound KMS cost/latency. This buys GDPR Art. 34 / CA AB 1130 breach-notification safe harbor as long as keys live in KMS separate from the ciphertext.
4. **RLS correctly or not at all.** `FORCE ROW LEVEL SECURITY`; connect as a non-owner role without BYPASSRLS; set tenant context with `SET LOCAL` inside each transaction (transaction-mode pooler safe); composite indexes with `tenant_id` leading. Reserve BYPASSRLS for migrations only. Do not rely on the fabricated "100x" / "500-conn" figures for capacity planning — benchmark your own workload.
5. **Ports-and-adapters for auth sources.** One Port per third-party source; OAuth adapter for Google Calendar / Meetup / Eventbrite, browser/password adapter for Luma / Partiful. The storage strategy differs per adapter (refresh-token record vs siloed password/cookie), so make `credential_type` an explicit dimension of the vault schema.
6. **Treat Google CASA Tier 2 as a hard external gate.** Request minimum scopes; store exactly one refresh token per user per client (avoid re-consent churn that silently invalidates the oldest of ~100 tokens); build first-class refresh-failure / re-consent lifecycle handling; budget for an annually-renewed third-party DAST assessment.
7. **Product auth = OIDC + BFF.** Browser gets only an httpOnly/Secure/SameSite session cookie; tokens stay server-side; `tenant_id` is a signed claim resolved once at the request edge and used uniformly for RLS context and cache keys. Keep JWT signing keys separate from at-rest encryption keys; rotate both.
8. **Bake compliance into the data model.** Account deletion hard-deletes credentials + tokens + cookies AND calls upstream revoke endpoints (Google revoke, etc.); maintain a documented CPRA risk assessment for the automated/paid-action processing; keep SCCs as a fallback to the fragile EU-US DPF; specify a concrete key-rotation + incident blast-radius runbook.
