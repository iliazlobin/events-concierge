# Autonomy, Authorization, Payments & Safety for Money-Moving Agent Actions

> The Events Concierge takes irreversible, money-moving actions (paid ticket purchase, registration) with no human in the loop at execution time; this dimension defines the token scoping, consent model, idempotency contract, policy guardrails, and audit trail that keep autonomy bounded, exactly-once, and legally defensible.

## Verified findings

### Payment tokenization — the ACP delegate_payment blueprint

- **[confirmed] ACP's `delegate_payment` endpoint is a directly reusable blueprint for a scoped, single-use payment token bounded by an explicit `Allowance` object.** Verified against the raw ACP OpenAPI spec (`spec/2026-04-17/openapi/openapi.delegate_payment.yaml`, Apache-2.0). `POST /agentic_commerce/delegate_payment` returns a vault token (id prefix `vt_`) governed by a required `allowance` object with fields: `reason` (enum, currently only `one_time`), `max_amount` (integer, minor units), `currency` (ISO-4217 lowercase), `checkout_session_id`, `merchant_id` (maxLength 256 — the ONLY merchant authorized to use the token), and `expires_at` (RFC-3339). The card is passed as `payment_method` with `card_number_type` enum `fpan | network_token`, plus optional `cryptogram` and `eci_value` (maxLength 2) for 3DS-authenticated tokens, and a required `risk_signals` array whose `action` enum is `blocked | manual_review | authorized`. This is exactly the "scoped virtual card per purchase" pattern: mint a fresh token bound to one merchant, one amount cap, one short expiry — never a reusable stored PAN.
  - **Integration caveat (not a refutation):** direct integration against `delegate_payment` is intended for PSPs or PCI-DSS Level 1 merchants running their own vault. A typical application consumes this via Stripe's **Shared Payment Token** rather than re-implementing tokenization. Design against the contract shape; delegate the actual vaulting to the PSP.

- **[confirmed] ACP mandates an `Idempotency-Key` on money-moving POSTs and specifies exact conflict/replay/in-flight semantics to mirror.** Verified verbatim against the primary YAML (latest released version 2026-04-17, confirmed via the GitHub contents API — not stale). The `Idempotency-Key` header is `required: true`, opaque string minLength 1 / maxLength 255, UUIDv4 recommended, and explicitly **"Scoped to authenticated identity + endpoint."** A successful replay returns header `Idempotent-Replayed: true` ("cached replay of a previous request with the same Idempotency-Key"). Error contract: `400 idempotency_key_required` (missing), `409 idempotency_in_flight` (still processing) with a **required** integer `Retry-After` header in seconds, `422 idempotency_conflict` (same key, different request body). Every response also echoes a `Request-Id` correlation header. Scope nuance: this file defines a single POST endpoint, so "every money-moving POST" is an accurate generalization of ACP's convention but is substantiated here only for `delegate_payment`. The contract is directly implementable for exactly-once registration and ticket purchase: derive the key deterministically from `(user_id, event_id, action)`, store the first response, enforce body-hash equality on replay.

- **[confirmed, non-load-bearing] ACP separates delegate-authentication (OAuth 2.0, act-on-behalf) from delegate-payment (token vault), and its auth flow is 3DS-shaped.** The `delegate_authentication` OpenAPI is a 3-D-Secure-style session API: create session, submit fingerprint, branch into frictionless-success vs challenge-required vs card-not-enrolled vs authentication-failed. This validates a ports-and-adapters split: an Authorization/consent port (what the user delegated, OAuth-scoped per third-party account) is architecturally distinct from a Payment-tokenization port (how a specific charge is funded and capped). The "challenge required" branch is exactly where full autonomy stalls and must fall back to a pre-authenticated token or a queued human step.

### The 3DS/SCA autonomy gap

- **[adjusted] SCA/EMV 3-D Secure can only run a step-up challenge when the cardholder is present, so it blocks fully-autonomous, cardholder-absent charges — but this is a PSD2/EEA legal mandate, not universal.** Corrected framing: under PSD2/EEA rules an autonomous, human-not-present charge is blocked unless it uses a recognized exemption (MIT/MOTO) or an agent-scoped **network token** carrying a pre-supplied cryptogram + ECI (3DS authentication status). **In non-PSD2 markets like the US** — where most current ACP/Instant Checkout volume sits — SCA is not legally required, so a raw-FPAN or stored-credential MIT charge *can* clear without a challenge, but it carries higher decline and fraud-liability risk. That risk, not a hard legal block, is the real reason to prefer network tokens in the US. Card networks are productizing agent-scoped tokens:
  - **Mastercard Agent Pay** (announced Apr 29 2025) issues MDES-based **Agentic Tokens** binding a tokenized credential to a specific agent + merchant scope + consent policy; a US issuer pilot (Citi, US Bank) ran in **September 2025**, expanding to all US cardholders by November 2025. (The specific "first live transaction Sep 29 2025" date is *not* corroborated by primary sources — softened to "September 2025 pilot.")
  - **Visa Intelligent Commerce** (announced Apr 30 2025) exposes tokenization/authentication and spending-control APIs for agent-added cards, plus an MCP server.
  - ACP's `network_token` path (cryptogram + `eci_value`) is the corresponding pre-authenticated escape hatch.
  - **Design consequence:** full autonomy on paid tickets is reliable only through network-tokenized/agent-token rails or merchant-stored-credential reuse — never by replaying a raw stored PAN.

### Delegated consent — Google AP2 mandates

- **[adjusted] AP2 (v0.2.0, April 2026) formalizes delegated consent as cryptographically-signed Mandates with distinct human-present vs autonomous signing.** Confirmed verbatim: AP2 represents a purchase as signed Mandates (verifiable credentials). In **Human-Present** mode the user signs the closed Checkout and Payment Mandates directly via a "Trusted Surface." In **Autonomous (Human-Not-Present)** mode the user signs *open* mandates carrying bounded constraints (price limits, timing) **plus the agent's public key (via a `cnf` claim)**; the agent then signs the *closed* mandates with its own Agent Key without further user interaction. The signed chain — **Intent Mandate → Cart/Checkout Mandate → Payment Mandate** — is the non-repudiable audit trail. Two corrections:
  - Mandates are implemented as **SD-JWTs (SD-JWT VC)**, not the W3C VC Data Model — "W3C Verifiable Credentials" overstates it.
  - The "budget ≤ $150, vendor class ticketing, 24h window" example is the researcher's illustration, not AP2's canonical example (AP2's own example is retail shoes). The constraint mechanism genuinely supports such a budget/vendor-class/time-window authorization, but do not attribute it to the spec as canonical.
  - Reference implementations exist in Python + TS/Kotlin/Go.

### Liability & chargebacks

- **[adjusted / confidence: medium — load-bearing] Chargeback liability for autonomous agent purchases is unresolved in 2026; under existing network rules the merchant is liable by default, and the agent's signed mandate + immutable action log is the emerging dispute-evidence layer.** Primary industry sources agree there is no settled liability regime — networks, issuers, and platform operators are still working through who absorbs the loss when an agent buys the wrong thing, but disputes do not wait for consensus. Under current rules a charge the cardholder never reviewed still lands on the merchant unless authorization can be proven, so "agent authorization logs, delegation records, and purchase-context data are becoming the new evidence layer." Consumer chargeback recourse is NOT extinguished by an agent mandate. **Unconfirmed:** specific case names / regulatory advisories surfaced only in secondary summaries could not be verified against primary sources — treat as unconfirmed. The load-bearing implication holds: our immutable audit log (signed user consent + exact event/price/time the agent registered) is the primary chargeback-dispute defense and must be tamper-evident and per-action.

### Orchestration & guardrails

- **[confidence: high — non-load-bearing] The idempotent-saga + transactional-outbox pattern makes the multi-step register→pay→calendar flow exactly-once with deterministic compensation.** Give every user intent one idempotency key; run the workflow as a saga of forward steps, each with a compensating action; persist saga state; use a transactional outbox/inbox so a state change and its outgoing event commit in ONE local DB transaction (relay adds ~tens of ms latency). Compensations are semantic reversals ("undo"), not true rollbacks, and MUST themselves be idempotent because they get retried. For `found → registered → scheduled_to_calendar`: if calendar insert fails after a paid registration, the compensation is a cancel/refund attempt against the registration. Paid-ticket refunds are frequently **not** fully reversible — a **saga pivot** point requiring forward-recovery / manual review rather than blind rollback. Money-moving steps and their compensations both key off the same idempotency key to guarantee at-most-once charge and at-most-once refund.

- **[confidence: medium — non-load-bearing] Express guardrails as externalized declarative policy (OPA/Rego or Cedar) evaluated before every tool call.** OPA (Rego) and AWS Cedar are the two dominant policy engines for gating agent tool calls — which tools, with what parameters, under what constraints — decoupled from the agent loop. Concrete kill-switch mechanic from OPA's Data API: `PUT /v1/data/maintenance {"enabled": true}` instantly blocks all non-admin actions fleet-wide; `DELETE /v1/data/maintenance` reverses it — a panic button / per-tenant freeze with no deploy. Rego policies are unit-testable, so spending-limit and merchant-allowlist rules ship through the same CI as code and can run in dry-run/monitor mode before enforcement. Put per-user spending limits, category/vendor allowlists, per-event and daily/monthly caps, and the kill-switch in a policy engine queried by a PolicyDecisionPoint at the money-moving boundary — autonomy bounded by configured POLICY, not interactive prompts.

### Ecosystem maturity

- **[confidence: high — non-load-bearing] ACP is live in production, lowering the risk of standardizing our payment port on it; AP2 and card-network agent tokens give a migration path.** As of early 2026 ACP is in beta but processing live transactions (Etsy live; expanding to 1M+ Shopify merchants, Walmart). The spec ships iterative dated releases (2025-09-29 initial → 2026-04-17 adding cart/feed/orders/authentication + explicit MCP integration). AP2 shipped v0.2.0 (April 2026) with Python/TS/Kotlin/Go reference impls. Four agentic-commerce frameworks landed Apr–Oct 2025 across stack layers: Mastercard + Visa (card-network), Google/AP2 (open protocol), Stripe/OpenAI/ACP (processor/tooling). Model the payment adapter against ACP's delegate-payment contract now (implementable today, MCP-native), keeping the Allowance/mandate abstraction generic enough to swap in AP2 mandates or Visa/Mastercard agent tokens without touching the domain layer.

## Design implications

1. **Scoped single-use token per purchase.** Model the payment token on ACP's `Allowance`: mint one vault token bound to one `merchant_id`, one `max_amount` cap (minor units), a `currency`, and a short `expires_at`. Never store or replay a raw reusable PAN. Store user cards only in a PCI-scoped vault (or delegate to the PSP via Shared Payment Token). Prefer network tokens over FPAN.

2. **`PaymentPort` seam mirroring ACP.** Define `delegate_payment(allowance, payment_method, risk_signals) -> vault_token`. Keep an adapter seam so AP2 mandates or Visa/Mastercard agent tokens can be swapped in later without changing register/purchase domain logic.

3. **Idempotency discipline on every money-moving action.** Required, deterministically-derived `Idempotency-Key` scoped to `(user_id, action, endpoint)`. Persist first-response; enforce body-hash equality (return `422`-style conflict on mismatch); surface an idempotent-replayed flag; handle in-flight duplicates with a `Retry-After` backoff. Apply the SAME key discipline to refunds/compensations.

4. **Idempotent saga + transactional outbox** for `register → pay → calendar`. Commit each state transition and its outbound event atomically. Define an explicit compensation per forward step. Treat paid-ticket refunds as a **saga pivot** (may be non-reversible) that routes to forward-recovery / manual review rather than assuming clean rollback.

5. **Externalized policy at the money-moving boundary.** Encode guardrails as OPA/Rego or Cedar: per-user spending limits (per-event, daily, monthly), vendor/category allowlists, currency limits, dry-run/monitor mode — with a data-plane kill-switch (per-user and global) that freezes all money-moving tool calls instantly without a deploy.

6. **Signed, bounded consent artifact (AP2-style Intent Mandate):** budget cap + vendor class + time window, signed once by the user; in autonomous mode the agent signs the concrete purchase mandate against those pre-approved constraints. Keep this Authorization/consent port architecturally separate from the Payment-tokenization port.

7. **Immutable, tamper-evident, per-action audit log as a liability-defense asset,** not just observability. Record: signed user consent, exact event/price/time the agent selected, the policy decision, the idempotency key, and the resulting vault-token/charge. Under 2026 rules the merchant/operator is liable by default; this log is the primary chargeback-dispute evidence.

8. **Design for the 3DS/SCA autonomy gap explicitly.** An autonomous charge cannot answer a step-up challenge. Route paid tickets through pre-authenticated network tokens (cryptogram/ECI) or the event site's stored payment. On a "challenge required" outcome, degrade gracefully to a queued human-authentication step rather than failing the saga silently. (Note the PSD2/EEA vs US distinction: outside PSD2, SCA is not legally mandated but network tokens still reduce decline/fraud-liability risk.)

9. **Defense in depth on limits.** Enforce per-user spending limits and merchant allowlists BEFORE token minting AND AGAIN at charge time. Set the vault token's `max_amount` equal to the specific expected ticket price, so an agent that picks the wrong item cannot overspend the delegated cap.
