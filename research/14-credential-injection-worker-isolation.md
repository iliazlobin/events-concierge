# Credential Injection: Build-vs-Buy, Browser-Worker Compromise Threat Model, and Credential Lifecycle

> Closes the post-wave-1 gap on how the autonomous RSVP path stores, injects, and isolates end-users' third-party source credentials — establishing that the injection worker must be BUILT (not bought), how a compromised browser worker is contained, and the full credential lifecycle from capture to zeroization to revocation.

## Verified findings

### Build-vs-buy: 1Password cannot back the unattended path

- **1Password Secure Agentic Autofill is human-in-the-loop by architecture; it has no unattended, policy-scoped auto-approval as of mid-2026, so it cannot back autonomous free RSVP.** [confirmed] Every login triggers "an approval prompt from your 1Password desktop app for each autofill request," authorized "in the same way you unlock your 1Password account, like with Touch ID." The Business policy "Allow AI Agents to autofill for users" only ENABLES the feature — it grants no unattended mode. Early Access constraints compound this: exactly one paired approving device at a time (a second device de-authorizes the first), and the integration is validated/pinned to Browserbase Director.ai only ("1Password validates its pairing partner is director.ai and rejects any untrusted party"). Communication uses forward-rotating key material over the Noise framework, and the extension injects the credential directly into the form so it never reaches the LLM — but a live human biometric tap gates every single login. Confirmed against the primary doc at 1password.dev/agentic-autofill (developer.1password.com 301-redirects there).

- **The March 2026 "1Password Unified Access" launch does not deliver unattended agent auto-approval; runtime scoped-credential issuance to agent/machine workloads is future-tense ("later this year") and remains consent-gated.** [adjusted] The release describes Discover/Secure/Audit for "human, agent, and machine credentials in a unified vault" and states 1Password "will expand Unified Access to issue scoped credentials to agent and machine workloads at runtime" — future tense, unspecified approval semantics, credentials elsewhere filled "with a user's consent." Currency check as of July 2026: no shipped headless policy-auto-approval capability exists to buy. Betting the RSVP critical path on a not-yet-shipped vendor feature would violate the API-first/SLA posture. (Verifier note: Unified Access is an access-governance product layered with partner integrations — Anthropic, OpenAI, Vercel — and does NOT introduce an unattended auto-approve path for Secure Agentic Autofill; the per-request biometric gate remains architectural.)

- **The only unattended Browserbase+1Password path is a 1Password Service Account SDK token, which re-exposes the secret to the agent process and concentrates tenants behind a single credential — no advantage over self-hosting for a multi-tenant product.** [adjusted] The Browserbase quickstart runs headless via `OP_SERVICE_ACCOUNT_TOKEN`: the client initialized with the token calls `client.secrets.resolve()` on `op://` references, returning plaintext that Stagehand then types into the form. This is the traditional secrets-manager model, NOT the "secret never seen" Agentic Autofill model — plaintext flows through the agent runtime. Storing end-users' third-party (Meetup/Eventbrite/Luma) passwords behind one service-account token collapses per-tenant isolation into a single blast radius. **Correction from verifier:** a single service account can be granted access to MULTIPLE vaults, so "one vault" is imprecise — you could partition per-tenant vaults. But the blast-radius point stands: one service-account token (and the process holding it) can resolve secrets across every vault it is granted, and the in-process plaintext exposure is identical to what self-hosting would require us to defend anyway. Buying this buys vendor lock-in and shared-credential concentration with no isolation gain.

### The build pattern: placeholder/reference broker

- **Build the injection worker as a non-LLM placeholder/reference broker: the LLM emits `{{username}}`/`{{password}}` tokens; a broker decrypts the per-tenant KMS-envelope credential and types it via Playwright `fill()`/CDP, with domain-pinning verifying the live URL before injection.** [confirmed] The pattern is real and, in several cases, shipping. Cerberus KeyRouter: "The AI writes the logic using placeholders. Real credentials are substituted locally and injected directly into the browser," where the broker "reads the browser's actual URL via CDP and matches it against the vault entry's URI. Phishing sites get rejected." OpenClaw issue #18245 confirms slot-based fill plus domain-pinning (`new URL(browser.currentURL).hostname` against `pinned_domains`), with "the LLM context window never contain[ing] the credential." Independent corroboration: Vercel Labs agent-browser ("Passwords stored in the auth vault are never included in LLM context," credentials bound to a `--url` domain, provider plugins run out-of-process) and 1Password's own shipping product ("the AI agent and underlying LLM never need to see nor handle the credentials"). Injection uses `fill()` (sets value + dispatches events) or character-by-character `type()` for stubborn forms. **Caveat (verifier):** the two originally-cited exemplars (Cerberus, OpenClaw) are demo/proposal-grade; the shipping references are 1Password, Vercel agent-browser, Browserbase. Domain-pinning is explicitly present in Cerberus, OpenClaw, and agent-browser; 1Password substitutes mandatory human approval for domain-pinning as its anti-exfiltration control. Our per-tenant KMS-envelope decryption is a consistent substitution for the vault backends the sources use.

### Worker isolation

- **Run one ephemeral Firecracker microVM per (user,event) login session with no cross-tenant coresidency and a mandatory egress proxy.** [confirmed] Firecracker's canonical published figures (AWS NSDI'20, Agache et al.) — ~125 ms boot, <5 MiB VMM memory overhead per VM, 150 microVMs/second/host — make per-session microVMs cheap enough to destroy after each login. Browserbase's model "pairs each agent runtime 1:1 with a browser on the same host, often the same microVM," brokers "secrets at the wire, never handed to the guest" (guest sees only placeholder env vars; real credentials substituted at the kernel-owned host-side TAP by an egress proxy against an allowlist), where "every outbound packet has to cross it," and signs identity "at the host, not inside the agent." 2026 sandboxing guidance is explicit: "provision one sandbox per execution session rather than sharing across users or tenants," choosing Firecracker (max isolation) or gVisor. **Nuance (verifier):** "the standard 2026 pattern" is slightly strong — Firecracker is one of several max-isolation primitives (gVisor, Kata Containers), which the design already acknowledges. This prevents one shared worker from harvesting many tenants' cookies and lets us allowlist egress to only the target event origin plus KMS.

### Credential lifecycle and boundary defense

- **Prefer short-TTL session cookies over stored passwords, but understand DBSC does NOT protect server-side reuse and can BREAK cookie replay across hosts — bind captured cookies to the same worker identity and add anomalous-use detection.** [high confidence, researcher] DBSC binds a session cookie to a non-exportable TPM/Secure-Enclave key on the ORIGINATING device; the server issues a ~5-minute cookie and re-challenges via a signed nonce on refresh. It is GA in Chrome 146+ on Windows (macOS Secure Enclave "coming" as of April 2026). Two consequences: (a) DBSC gives no protection for server-side cookie replay by our own agent — our worker is the device that authenticated, so a stored cookie is replayable from our own infra; (b) sites adopting DBSC/device-binding will REJECT a cookie replayed from a different host than the one that logged in, so we must reuse cookies only from the same isolated worker/network identity. Because "the vast majority of SaaS apps in 2026 still issue replayable session cookies," short-TTL capture-and-reuse is viable and safer than warehousing plaintext passwords, but requires stolen-cookie-replay monitoring (IP/User-Agent/geo/access-pattern deviation, not auth logs).

- **Defend the browsing boundary with a dual-LLM / capability split so untrusted page content can never reach the credential-injection or action-decision path (CaMeL pattern; Google's production agentic-Chrome design).** [high confidence, researcher] CaMeL splits a privileged, tool-holding LLM from a quarantined LLM that ingests untrusted page tokens but has no tool access and returns only opaque references (`$review-1`), mitigating 67–100% of injections on AgentDojo. Google's shipped agentic-Chrome architecture is the production analogue: a "User Alignment Critic" that "sees only metadata about the proposed action and not any unfiltered untrustworthy web content," a rule that "the model does not have direct access to stored passwords," and "Agent Origin Sets" splitting read-only vs read-writable origins. Indirect prompt injection via malicious sites/iframes/user-generated reviews is the primary agentic-browser threat, so the injection broker must be a deterministic, non-LLM component gated by domain-pinning — never a tool the reasoning loop can be talked into misfiring.

- **Zeroize the plaintext credential immediately after typing using locked, non-swappable, non-dumpable memory, bounding the secret's in-memory lifetime to the injection instant.** [high confidence, researcher] Use guarded-memory primitives — Go memguard (encrypted Enclaves + LockedBuffers) or Rust zeroize/memsec — with `mlock`/`VirtualLock` to keep the secret off swap and `madvise(MADV_DONTDUMP)` to exclude it from core dumps; zeroize guarantees the wipe "will not be optimized away." Flow: decrypt the KMS-envelope DEK just-in-time, hold plaintext in a locked buffer, inject via `fill()`, then explicitly zeroize both the buffer and the DEK before the microVM is torn down.

## Design implications

**Decision: BUILD the injection worker. Do not buy 1Password Secure Agentic Autofill for the unattended path.**

| Concern | 1Password Agentic Autofill | 1Password Service Account | Self-hosted KMS-envelope broker (CHOSEN) |
|---|---|---|---|
| Unattended? | No — live biometric tap per login | Yes | Yes |
| Secret reaches agent process? | No | Yes (plaintext) | No (broker only; LLM sees placeholders) |
| Per-tenant isolation | Per-user device pairing | Single token, shared blast radius | Per-tenant DEK + microVM |
| Vendor lock-in | High (Browserbase Director-only) | Medium | None |
| Fits SLA / API-first posture | No | No isolation gain | Yes |

Directives for our system:

1. **CredentialInjectionPort abstraction.** Keep the injection mechanism behind a port. Optionally wire Agentic Autofill later ONLY as an assisted / human-handoff path for high-value or best-effort browser sources — never for the unattended SLA path.

2. **Self-hosted KMS-envelope Injection Worker.** Store each per-tenant credential as `{KMS-wrapped DEK + AES-256-GCM ciphertext}`. At login an in-worker NON-LLM broker unwraps via KMS, decrypts into a locked buffer, and types via Playwright `fill()`/CDP. The Claude tool-use loop emits only `{{username}}`/`{{password}}` placeholders — the secret is structurally excluded from prompts, tool-args, Temporal activity inputs/history, and logs.

3. **Domain-pinning as the primary anti-exfiltration control.** Before releasing any secret, read the live browser URL via CDP and require an exact match against the credential's bound origin (per-source allowlist, e.g. only `lu.ma`, `meetup.com`). A redirect or prompt-injected navigation to any other origin aborts injection and triggers human-handoff.

4. **One ephemeral Firecracker (or gVisor) microVM per (user,event) login session.** No shared long-lived browser worker, no cross-tenant coresidency. Destroy the microVM after login/RSVP. Front it with a mandatory egress proxy whose per-session allowlist is target-event-origin + KMS-endpoint only; block all other outbound traffic.

5. **Split the browsing-boundary LLM (CaMeL / Google User-Alignment-Critic).** A privileged orchestrator holds the injection tool and never ingests raw page text; a quarantined reader summarizes untrusted DOM/reviews into typed references. Untrusted page content must never flow into the component that decides to inject.

6. **Zeroize on exit.** Hold plaintext only in `mlock`'d, `MADV_DONTDUMP` guarded memory (memguard / Rust zeroize); wipe the buffer and unwrapped DEK immediately after typing; rely on microVM teardown as the backstop.

7. **Credential lifecycle — prefer short-TTL cookies over passwords.** Because DBSC/device-binding sites reject cookies replayed from a different host, reuse a captured cookie ONLY from the same isolated worker/network identity that logged in. On cookie-invalid, silently re-login with the stored password inside a fresh microVM. Store passwords only as the re-auth fallback for sites that force full login.

8. **Re-auth handling in the Temporal workflow.** A failed login or unexpected MFA/CAPTCHA challenge marks the stored credential `invalid`/`needs_reauth`, halts autonomous retries (avoid lockout), and emits a human-handoff re-auth prompt. Support user-initiated revocation that crypto-shreds the tenant DEK. Off-SLA for browser-best-effort sources.

9. **Anomalous-use detection on our stored session artifacts.** Monitor for cookie reuse from unexpected IP/geo/User-Agent or abnormal access patterns (behavioral, not auth-log based); auto-revoke + force re-auth on deviation.

10. **Prefer OAuth/API auth wherever the source offers it (Meetup, Eventbrite)** so no password is ever stored or injected. Reserve the credential-injection worker for browser-best-effort sources (Luma, Partiful) that lack API auth, consistent with the API-first / browser-best-effort posture.
