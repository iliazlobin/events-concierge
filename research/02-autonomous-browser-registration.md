# Autonomous Browser Automation for Form-Filling and Paid Registration

> Determines whether the "found → registered" leg of the Events Concierge can be executed by an agent with no per-action human confirmation, and — if so — on which harness, with what success ceiling, credential model, and failure-handling contract.

## Verified findings

### Real-world web-agent success is ~56–61%, not the ~85–94% WebVoyager implies [confirmed]
On the realistic Online-Mind2Web benchmark (300 live tasks, 136 sites, dual human annotation with third-reviewer tiebreak), the best general web agents top out at ~56–61% end-to-end human-eval success: OpenAI Operator 61.3%, Claude Computer Use 3.7 56.3%, Claude 3.5 29.0%, Browser Use 30.0%, SeeAct 30.7%, Agent-E 28.0%. Success drops ~31.6% from easy (≤5 steps) to medium (6–10 steps) and another 15.4% to hard (≥11 steps). Agents fail most on filtering/sorting (57.7% of failures), navigation (19.6%), and numeric/temporal constraints — exactly the operations in event date/time/price selection. A naive search agent scores 51% on WebVoyager but only 22% here, confirming WebVoyager (top scores bunched 85.8–93.9%) overstates real capability. Newer Steel.dev leaderboard entries (Browser Use Cloud "bu-max" 97.0%, GPT-5.4 native computer use 93.0%, ABP+Claude Opus 4.6 90.5%) use custom/agentic judges (WebJudge), not human eval, and the leaderboard itself flags them as "not directly comparable." (Minor: those entries are timestamped Mar 2026, not Jun 2026 as originally claimed — immaterial.)

### Write-operation benchmarks — the ones resembling registration/checkout — cap near ~64% [medium confidence]
WebVoyager is saturated and no longer differentiates. Web Bench (5,750 tasks, 452 live sites, state-mutating write operations) is the discriminating benchmark; Skyvern leads it at 64.4%, and Skyvern (85.85% WebVoyager) is repeatedly cited as best-in-class for form-filling specifically. Since registration/RSVP/checkout are writes, treat ~64% — not the 90%+ read-task numbers — as the realistic per-attempt ceiling to design guardrails around.

### The Claude-in-Chrome extension routes purchases/account-creation/financial actions through a mandatory approval gate — unusable as our autonomous engine [adjusted]
The Claude-in-Chrome extension (beta, all paid plans, Chrome only) is designed to always route the exact actions our product requires — purchases, financial transactions, permanent deletions, permission/security changes, and account creation — through an interactive human-approval gate, regardless of permission mode ("Ask before acting" or "Act without asking") and even with "Always allow actions on this site." Note this is an LLM-behavioral safeguard Anthropic explicitly states it "can't guarantee," not a cryptographic hard block — which makes it *less* suitable, not more: where the gate fails it fails unpredictably rather than acting reliably. Either way, the extension cannot serve as a fully autonomous paid-registration engine with no per-action confirmation. Team/Enterprise admins can add allow/blocklists but cannot remove the protected-action gate.

### The Computer Use API is the programmatic path, imposes no purchase gate, but defaults to a prompt-injection classifier that inserts human confirmation [confirmed]
The Anthropic Computer Use API (distinct from the Chrome extension) imposes no purchase/commerce/checkout gate. Its only default safety intervention: classifiers automatically run on prompts, and when they flag a potential prompt injection in a screenshot they "automatically steer the model to ask for user confirmation before proceeding." Anthropic states this "won't be ideal for every use case (for example, use cases without a human in the loop)" and you must contact support to opt out. Load-bearing specifics, all confirmed against the docs:
- Beta headers: `computer-use-2025-11-24` (Sonnet 5, Opus 4.8/4.7/4.6, Sonnet 4.6, Opus 4.5); `computer-use-2025-01-24` (Sonnet 4.5, Haiku 4.5).
- Recommended display: 1024×768 or 1280×720 (desktop), 1280×800 or 1366×768 (web apps); avoid >1920×1080. 1280×720 is the accuracy baseline.
- macOS Retina/4K: downscale screenshots 2× before sending or halve returned coordinates.
- Eligible for Zero Data Retention.
- `enable_zoom` (computer_20251124) helps read small text such as prices/dates.
- Sonnet 4.5 scores 61.4% on OSWorld (up from Sonnet 4's 42.2%).

### Architecture should be hybrid DOM-skeleton + vision-CUA fallback, not pure-CUA [adjusted]
Vision-based computer use runs a screenshot→reason→act loop that is slower and higher-cost per step and can require many steps per task (Browser Use averaged 8.5 steps for Coursera up to 36.2 for Google Flights on WebVoyager, at 89.1% overall). Reliability is task-dependent rather than a fixed gap: deterministic DOM/code-first automation is fastest, cheapest, and most auditable on *known, stable* flows but is fragile to DOM redesign, whereas vision-CUA generalizes best across unknown surfaces (2026 vision-first systems like Magnitude ~93.9% and Skyvern 2.0 ~85.85% actually top WebVoyager, above DOM-only baselines ~57%). This argues for a hybrid: a deterministic, cached, replayable DOM/code skeleton (e.g. Stagehand v3, which went direct-to-CDP for ~44% faster iframe/shadow-DOM interaction, with action caching for up to 2× speed / ~30% cost reduction) plus a small vision-CUA fallback loop for the long tail. The field guide's own recommendation: "a deterministic, cached, replayable code skeleton wrapped around a small fallback CUA loop." (REFUTED / dropped: the specific "2–5s/action" latency and "DOM 12–17 percentage points more reliable" figures from the original research are not supported by the cited primary sources — the DOM-advantage framing is directionally wrong on open long-tail tasks. The architectural conclusion stands regardless.)

### Ticketing/RSVP sites run adversarial anti-bot stacks; automated paid checkout on protected on-sales is a losing battle [high confidence]
Major ticketing platforms fingerprint browser, IP, and behavior (Akamai/Cloudflare/DataDome). Ticketmaster uses Verified Fan pre-registration + unique access codes + a $1B+ anti-bot investment; a 2026 push adds World ID identity verification with access codes redeemable on Ticketmaster/Eventbrite/AXS. During on-sales bots are up to 90% of traffic, so defenses are aggressive. Concretely, Browser Use had to remove 55 of 586 WebVoyager tasks partly due to Cloudflare blocking. Datacenter-headless automation is exactly what these stacks detect and challenge.

### Claude-in-Chrome prompt-injection susceptibility and extension CVEs make it a multi-tenant credential-exfiltration vector [high confidence, non-load-bearing]
Anthropic's published safety data reports Claude for Chrome succumbs to prompt injection 23.6% of the time unmitigated / 11.2% with current mitigations. Separately, researchers found a critical trust-boundary flaw in the extension's `externally_connectable` manifest allowing malicious extensions to manipulate the assistant and reach Gmail/Drive/GitHub data. Because our system stores and uses users' Google/Luma/Meetup/Eventbrite logins, a compromised browser agent is a multi-tenant credential-exfiltration risk. Reinforces avoiding the extension for the autonomous leg.

### Computer-use agents assume outcomes without checking and hallucinate click coordinates [high confidence, non-load-bearing]
Anthropic's own guidance warns Claude "sometimes assumes outcomes of its actions without explicitly checking their results" and "might make mistakes or hallucinate when outputting specific coordinates," with reliability lower on niche/multiple apps. The recommended mitigation is an explicit per-step verify prompt: after each step, screenshot and confirm the right outcome was achieved before moving on. These are precisely the guards needed before any submit/pay action — wrong-field entry and double-submit on irreversible checkout are the two most damaging failure modes.

### 1Password Secure Agentic Autofill + Browserbase lets the agent log in without the LLM ever seeing the secret [high confidence, non-load-bearing]
The integration establishes a Noise-Framework E2E-encrypted channel between the user's approving 1Password device and a headless 1Password extension in the Browserbase browser. On login, the agent requests autofill over the channel; on approval, only the minimum credential data (plus TOTP) is injected into the form — "the AI agent and underlying LLM never need to see nor handle the credentials," and secrets are never stored or logged by the agent. The field guide calls this "the most concrete production answer yet to the credential-handoff problem." Caveat: the current design uses a per-request human approval prompt, which we would need to replace with policy-based auto-approval for full autonomy.

### Multi-tenant headless-browser economics [medium confidence, non-load-bearing]
Managed browser infra runs ~$0.10/browser-hour (Browserbase Scale, Hyperbrowser ~100 credits = 1 hour); self-hosting breaks even only above ~5,000 concurrent sessions. On top sits model cost: Claude Sonnet 4.5 is $3/M input, $15/M output (~45 tok/s, 1.43s TTFT, 1M context), and each vision step re-sends a full screenshot, so a 20-step registration accrues significant image-input tokens. Recommended default thinking effort is "medium" on Sonnet 4.6/Opus 4.6 (avoid "max"; "low" can reduce cost by cutting retry mistakes). A single autonomous registration is meaningfully expensive and slow — tens of seconds to minutes.

## Design implications

1. **Do not use the Claude-in-Chrome extension for the autonomous paid-registration leg.** Its permission model routes purchases/account-creation/financial actions through mandatory interactive approval in every mode, and (per its own guarantee disclaimer) fails open unpredictably where it does not. Use the programmatic Computer Use API (beta header `computer-use-2025-11-24`) and/or a DOM-driven harness. Reserve the extension only for interactive/dev or human-supervised flows.

2. **Ports-and-adapters registration port; DOM-first, vision-CUA fallback.** Prefer scripted DOM adapters (Playwright/CDP or Stagehand-style) per source and fall back to vision-CUA only for API-less/JS-heavy/invite-only sites (Luma, Partiful). Pure vision-CUA is highest cost/latency per step and no more reliable on stable known flows — make it the long-tail fallback, not the default.

3. **Engineer for a ~60% (general) / ~64% (write-op) per-attempt ceiling.** Mandatory pre-submit verification (re-screenshot + confirm price/date/field values, per Anthropic's per-step verify prompt); a single-attempt **idempotency key per (user, event)** to prevent double-submit; a policy-gated retry budget — never assume first-try success.

4. **Enforce autonomy safety in configured policy, not interactive prompts.** Per-user spending limits, an idempotency ledger keyed on the money-moving action, and a "confirm outcome before marking registered" step. Because the Computer Use classifier defaults to inserting human confirmation on flagged injections, you must explicitly opt out (contact Anthropic) **and** replace that safety with your own injection isolation, or the "no per-action confirmation" scope silently breaks.

5. **Never let the LLM or agent process see stored third-party secrets.** Adopt the 1Password Secure Agentic Autofill / Browserbase pattern (Noise-framework E2E channel, minimal-field injection, TOTP at runtime), but swap its per-request human approval for policy-based auto-approval scoped to the specific login domain under explicit user consent.

6. **Treat ticketing/RSVP sites as actively hostile.** Prefer official APIs/connectors (Eventbrite, Meetup, Luma) wherever they exist. For browser registration, use persistent per-user real logged-in sessions/cookies over datacenter-headless; expect and gracefully **degrade to human-handoff** on CAPTCHA/identity-verification/access-code walls; never build evasion. Surface an actionable "needs you" state in the found→registered→scheduled lifecycle.

7. **Instrument every browser action for auditability.** Per-step video/screenshot, token cost, latency, and structured `failure_reason`; plus a durable audit log of every attempted and completed money-moving action (idempotency key, amount, timestamp, screenshot of confirmation). Required by the credential-security mandate and to detect known failure modes (hallucinated clicks, wrong field, assumed-but-unchecked outcomes).

8. **Budget multi-tenant economics explicitly.** At ~$0.10/browser-hour + Sonnet-class per-step image tokens over ~18–36 steps, each registration is expensive and slow. Outsource browser infra (Browserbase/Steel) until >~5,000 concurrent sessions, cache deterministic action sequences per source (Stagehand-style, ~30% cost / 2× speed), and cap per-user concurrent sessions.
