# Event Ranking, Relevance & Per-User Personalization

> The concierge's core value is surfacing the right few events for one person from a noisy, multi-source, high-churn corpus — ranking quality and per-tenant personalization are the product, not a feature.

## Verified findings

### Retrieval and reranking architecture

**The 2026 production-standard retrieval stack is two-stage: hybrid (BM25/keyword + dense vector) fused with Reciprocal Rank Fusion, then a cross-encoder rerank pass — superseding a single-index `function_score` approach. [adjusted]**
RRF fuses by rank position only: `RRF_score(d) = Σ 1/(k + rank_r(d))` summed across each ranker's list, with `k≈60` the community default (Cormack et al. tuned k=60 on TREC; benchmarks land in k∈[40,80]). Because it uses rank position and ignores raw scores, it sidesteps the BM25-vs-cosine scale-incompatibility problem with **no normalization**. BM25 and dense retrieval have complementary recall (documents missed by one are found by the other), a long-established BEIR/MS MARCO result — keyword search is NOT obsolete for exact terms (venue names, "jazz", "React meetup").
CORRECTION on provenance: the headline reranking figures — Recall@5 **0.816** for hybrid+cross-encoder vs **0.695** for hybrid-RRF-alone (= +17.4%) — and the "BM25 beats text-embedding-3-large on most BEIR metrics except Recall@20" finding BOTH come from a **single domain-specific benchmark** (arXiv 2604.01733, financial text+table QA with Cohere rerank; BM25 0.644 vs dense 0.587 Recall@5, Recall@20 near-tied 0.797 vs 0.798). They are the same data point stated two ways, not two independent general benchmarks, and the paper's authors frame the lexical-beats-dense result as domain-specific (precise financial terminology favors exact match). Treat as illustrative, domain-dependent evidence and re-validate on the events corpus. The architecture recommendation itself is sound and safe to build on.

**A dedicated cross-encoder reranker (Cohere Rerank v3.5/v4) is the cost/latency sweet spot for stage two. [confirmed]**
Pricing: Rerank v3.5 = **$2.00 per 1,000 searches** ($0.001/search); one search = one query with up to 100 documents. Any document exceeding 500 tokens (including query length) is auto-split into chunks, each counted as an individual document (verbatim from Cohere's pricing page). API: `POST https://api.cohere.com/v2/rerank`; request body `model` (e.g. `rerank-v3.5`, `rerank-v4.0-pro`), `query` (string), `documents` (array of strings), optional `top_n` and `max_tokens_per_doc` (default 4096). Response: `results[]` each with `index` (original position) and `relevance_score` (normalized 0–1), plus top-level `id` and `meta` (billing/usage). Latency ~80–150 ms p50 is a plausible engineering estimate (cross-encoder over ≤100 short docs), NOT a vendor SLA. This fits reranking the ~50–200 candidate events per request against a rich query string built from profile + constraints. Note: the $2.00/1k rate is confirmed for v3.5; v4 tiers (Fast/Pro/Large) may differ.

**LLM listwise reranking (RankGPT-style, or an Opus/Sonnet pass) buys only modest quality gains at ~9x cost and ~35x latency vs a dedicated cross-encoder — reserve it for a final small-N pass, not the main ranker. [confirmed]**
Measured (ZeroEntropy, a reranking vendor's own benchmark — treat exact decimals as illustrative, not canonical): BGE-reranker-v2 = 0.74 NDCG@10 / 12 ms / $2 per 1k; Gemini Flash **listwise** = 0.78 NDCG@10 / 420 ms / $18 per 1k (= 9x cost, 35x latency vs BGE); pointwise LLM = 0.68 / 185 ms / $27. RankGPT-gpt-4 is the strongest listwise reranker (DL19 **75.59**, peer-reviewed, arXiv 2508.16757) but is context-length and latency bound (a 1B listwise variant took 53+ minutes in that study). Viability envelope for LLM listwise: very small candidate lists, low QPS, tolerating 500 ms–2 s at $10–100/1k — e.g. a final top-10 tie-break where cross-document reasoning ("avoid two similar events same night") matters. Engineering levers cut LLM-rerank cost ~8x and latency <1s: tight output format, thresholding, prompt caching, parallel calls, staged cross-encoder→top-10-LLM.

**Current Claude token pricing sets the economics of any Opus/Sonnet ranking or explanation pass. [confirmed]**
Per 1M input/output tokens: Opus 4.8 **$5/$25**, Sonnet 4.6 **$3/$15**, Haiku 4.5 **$1/$5** (output = 5x input across all tiers). Prompt caching cuts cache-hit (read) input by **90%** (0.1x base); cache writes cost 1.25x for 5m / 2x for 1h TTL. Batch API is **50% off** both input and output. Opus 4.8, Opus 4.7, and Sonnet 4.6 include the full **1M-token context at flat rates with no long-context surcharge**. A ~50-event rerank prompt (~7.5k input on Sonnet 4.6 ≈ $0.02–0.03 uncached, dominated by input) is affordable for a personal concierge (few requests/user/week) but expensive as fan-out over a large corpus — favoring cross-encoder for breadth, LLM only for the final short list and the "why this event" explanation. Caveats not affecting design: a `us` data-residency flag adds 1.1x on some models; Fast Mode carries premium pricing.

### Storage and embeddings

**Postgres + pgvector (with tsvector/BM25 for the keyword leg) covers hybrid retrieval, geo/time filtering, and per-tenant isolation in one query plan; a self-hosted OpenSearch/Elasticsearch cluster is NOT warranted for this corpus. [high confidence]**
pgvector ~75% cheaper than Pinecone (self-hosted Postgres ~$835/mo vs Pinecone $3,241–3,889/mo at 50M vectors); with a tuned HNSW index it matches or beats Pinecone latency and beats Elasticsearch decisively for exact/filtered kNN (pgvectorscale 7 ms p99 vs Elasticsearch 1600 ms exact kNN in one test). Decisive point: when most queries combine vector similarity with metadata filters, Postgres filters and searches in one optimizer-pruned query plan. Event ranking is inherently filter-heavy (city/geo radius, date window, price ≤ limit, registration-open) over a small, high-churn corpus (well under 50M rows) — exactly pgvector's regime. Pinecone only wins past ~100M vectors with sustained high QPS / multi-region. pgvector also colocates events with users, preferences, credentials, and lifecycle state, letting tenant isolation ride on Postgres row-level security and avoiding a second datastore to secure.

**Embeddings are cheap enough to not be a design constraint. [high confidence, non-load-bearing]**
OpenAI text-embedding-3-large $0.13/M tokens (3-small $0.02/M), Voyage-4 ~$0.06/M (4-large ~$0.12–0.18/M), Cohere embed-v4 leads MTEB; Batch API halves these. Embedding 1M events at ~200 tokens each = 200M tokens ≈ $26 on 3-large, ~$4 on 3-small — negligible vs LLM ranking. The dense leg can be re-embedded on model upgrades without cost pain; user-preference vectors (aggregates of attended-event embeddings) are effectively free to maintain. Choose 3-large / Voyage-4 / Cohere embed-v4 for quality on short blurbs; 3-small if write-time cost/latency dominates. Matryoshka/truncatable dims (3-large supports shortening) trade recall for pgvector index size.

### Personalization, cold-start, dedup, explainability

**Fold personalization in as a feature-based re-scoring layer (LambdaMART/LightGBM or a lightweight linear/logistic model) on top of the retrieval score — not by baking taste into the retrieval query alone. [medium confidence]**
Proven pattern (LightGBM LambdaRank/LambdaMART for news recsys) combines user/item/session features AND embedding cosine-similarity between the user's history embedding and the candidate as an added feature. This maps onto the 2025 `function_score` signals (popularity, uniqueness, venue quality, food, proximity), which become features alongside user↔event embedding similarity, explicit-profile category affinities, and implicit attended-vs-declined signals. Keep the model small and per-tenant-safe (features derived only from that user's history). LightGBM moved to lightgbm-org/LightGBM (March 2026).

**Cold-start: combine explicit attribute-preference elicitation at onboarding with content-based ranking from event metadata, and use LLM test-time conditioning to infer preferences from the natural-language request itself. [medium confidence]**
Eliciting preferences on item ATTRIBUTES ("small intimate events", "free", "tech talks") is more effective for cold-start than item ratings alone. Content-based ranking from metadata works from day one with zero interaction history. Because every request here is natural language ("something Friday evening after work"), an LLM can do test-time preference inference to seed ranking before implicit signal accumulates. As the user attends/declines, shift weight from explicit profile to implicit LTR features.

**De-dupe the same real-world event surfaced by multiple sources BEFORE ranking: block → pairwise match → merge. [medium confidence]**
Entity resolution is match-then-merge. Block by (normalized city, date) to avoid O(n²); score candidate pairs on fuzzy title similarity (Jaro-Winkler/Levenshtein) + description-embedding cosine + start-time delta + geo distance; above threshold, merge into one canonical event that RETAINS all per-source registration URLs (so the autonomous registrar can pick the best/cheapest source). Resolve conflicting time/venue fields by selecting values most frequent across sources. Dedup before ranking prevents a popular event from flooding the top-N as near-identical rows.

**Ranking explainability is cheap and high-value: a single Haiku/Sonnet pass over the top-N with their feature scores generates a faithful per-event "why this fits you" rationale. [medium confidence]**
2026 user studies show LLM-generated explanations improve understandability, transparency, trust, effectiveness, satisfaction and persuasiveness, with the largest gains when paired with diversity-aware selection. Feed the reranker's per-event feature contributions (proximity, matched interests, price fit, novelty) into the explanation prompt so the rationale is faithful to the actual score rather than confabulated — grounding also makes it auditable.

## Design implications

1. **Two-stage ranker replacing the single `function_score`.** Stage 1: hybrid retrieval (pgvector dense ANN + Postgres tsvector/BM25) fused with RRF (k=60, rank-only, no normalization) to fetch top ~100–200 candidates. Stage 2: Cohere Rerank v3.5/v4 cross-encoder (~$2/1k, ~100 ms) to reorder. Define a single **Ranker PORT** so the impl (Cohere adapter / local cross-encoder / LLM adapter) is swappable. Re-validate the illustrative recall numbers on our own events corpus before treating them as targets.

2. **Do NOT make an LLM listwise pass the primary ranker** (~9x cost, ~35x latency for ~0.04 NDCG). Restrict LLM ranking to a final top-10 tie-break where cross-event reasoning helps (avoid clashing/duplicate nights, balance diversity), behind a feature flag, with prompt caching + tight JSON output + parallel calls to stay <1s.

3. **Standardize on Postgres + pgvector as the single store** for events, embeddings, users, preferences, credentials, and lifecycle state — no separate OpenSearch/Elasticsearch or managed vector DB. Filter-heavy queries over a <50M-row corpus are pgvector's win regime; tenant isolation rides on row-level security in one query plan.

4. **Personalization = feature-based re-scoring layer** (LambdaMART/LightGBM or lightweight linear) consuming the retrieval/rerank score plus: user↔event embedding cosine, explicit category/attribute affinities, implicit attended-vs-declined, and the legacy signals (popularity, uniqueness, venue quality, food, proximity). Derive each user's model/features ONLY from their own history to preserve multi-tenant isolation.

5. **Cold-start from three sources with a decaying blend:** (1) onboarding elicitation of ATTRIBUTE preferences (price sensitivity, size, categories), (2) content-based ranking from metadata on day one, (3) LLM test-time inference of intent from the NL request. Shift weight toward implicit LTR features as attended/declined history accumulates.

6. **De-duplication stage BEFORE ranking:** block by (normalized city, date); score pairs on fuzzy title (Jaro-Winkler) + description-embedding cosine + start-time delta + geo distance; merge above threshold into one canonical event RETAINING all per-source registration URLs. Resolve conflicting time/venue by cross-source frequency.

7. **Treat embeddings as a non-constraint** (≤~$26 to embed 1M events on 3-large; batch halves it). Pick a high-MTEB model (3-large / Voyage-4 / Cohere embed-v4), keep user-preference vectors as cheap running aggregates of attended-event embeddings, and use truncatable/Matryoshka dims to bound HNSW index size.

8. **Generate a faithful "why this fits you" explanation** with a cheap Haiku/Sonnet pass fed the reranker's ACTUAL feature contributions (not free-form) — satisfies both the explainability goal and the system's auditability requirement in one artifact. Pair with diversity-aware top-N selection for the largest trust gains.
