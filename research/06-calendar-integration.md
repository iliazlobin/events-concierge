# Multi-User Calendar Integration, Dedup & Conflict Detection

> The concierge autonomously writes discovered events into each tenant's real calendar; without idempotent writes, queryable dedup keys, and a pre-registration conflict gate it will double-book users and corrupt their calendars at scale.

## Verified findings

### Google Calendar (primary provider)

**Store the source event id in `extendedProperties.private` and query it back — it is a first-class queryable index, not an opaque blob. [confirmed]**
Google Calendar events carry `extendedProperties.private` (scoped to a single calendarId+eventId copy) and `extendedProperties.shared` (visible/editable by all attendees). You query with `events.list?privateExtendedProperty=name%3Dvalue` (the `=` URL-encoded as `%3D`). Repeated constraints on the same scope are OR'ed; private-vs-shared constraints are AND'ed. Hard limits: key <=44 chars, value <=1024 chars, up to 300 properties totaling <=32 kB per event. Use `patch` to add/update without disturbing other props (set a value to `null` to delete). Operational caveats confirmed by the primary doc: `privateExtendedProperty` queries run against a single calendarId (dedup is inherently per-calendar); over-length keys are silently dropped and over-length values silently truncated. Writing `private.concierge_source='luma:evt_abc123'` and `private.reg_state='registered'` lets a later insert run one `events.list?privateExtendedProperty=concierge_source%3Dluma:evt_abc123` to detect an existing entry before creating a duplicate, and to reconcile registration state later.

**Client-controlled event id gives a strong (best-effort) idempotency primitive, not a hard guarantee. [adjusted]**
You may set the event id yourself on `events.insert`: 5-1024 chars, base32hex alphabet (`[a-v0-9]`, lowercase), unique per calendar. If you deterministically derive the id from the source event, a retried insert normally returns HTTP 409 (domain `global`, reason `duplicate`, message "The requested identifier already exists.") rather than creating a second copy — a clean idempotent upsert (on 409, switch to `update`/`patch`). IMPORTANT CORRECTION: Google's own `events.insert` docs state, "Due to the globally distributed nature of the system, we cannot guarantee that ID collisions will be detected at event creation time," and recommend UUIDs to minimize collisions. Under concurrent/rapid retries or replication lag a duplicate can occasionally still be created. Treat 409 as the normal, best-available outcome but pair it with a defensive de-dupe/reconciliation check rather than an absolute guarantee. Separately, `events.import` requires an `iCalUID`, accepts only `eventType=default`, and is for migrating a copy across calendaring systems; `iCalUID` differs from `id` (recurring occurrences share one `iCalUID` but have distinct `id`s), and the docs do NOT promise import dedups by `iCalUID` — so the deterministic-id + 409 pattern remains the reliable mechanism.

**Push notifications (`events.watch`) are content-free triggers; real change data comes from an incremental `events.list` with `syncToken`. Channels are per-calendar-per-user, expire, and have no auto-renew. [confirmed]**
`watch` notifications carry NO body — headers only: required `X-Goog-Channel-ID`, `X-Goog-Message-Number`, `X-Goog-Resource-ID`, `X-Goog-Resource-State` (`sync`|`exists`|`not_exists`), `X-Goog-Resource-URI`, plus optional `X-Goog-Channel-Expiration` and `X-Goog-Channel-Token`. On any notification you call `events.list` with the stored `syncToken`; `nextSyncToken` appears only on the final page of a paginated result. There is no automatic renewal — "When a channel is close to its expiration, you must replace it with a new one by calling the watch method." You need a separate channel per calendar per user (subscribe to A and B separately). If the server invalidates a `syncToken` it returns HTTP 410 GONE, which must trigger a full wipe of local state and a fresh full sync to obtain a new token. Nuance: the specific "~1 week" channel TTL is a widely-observed default, NOT a numeric cap pinned in current primary docs (the docs expose `ttl`/expiration fields without a documented maximum) — schedule renewal off the returned `X-Goog-Channel-Expiration`, not a hardcoded week.

**Use the FreeBusy query endpoint to detect overlaps BEFORE committing a paid registration, so the agent never books overlapping events. [confirmed]**
`POST https://www.googleapis.com/calendar/v3/freeBusy` with body `{timeMin, timeMax, items:[{id:calendarId},...]}` returns a `calendars` object keyed by calendar id, each with a `busy[]` array of `{start,end}` RFC3339 intervals (plus optional `errors[]`). Before the irreversible register/RSVP step, query FreeBusy over the candidate event's window across all of the user's calendars; any intersection with a busy block is a conflict → block/deprioritize registration. The `calendar.freebusy` scope alone grants this read. Refinement: FreeBusy already honors event transparency — events marked `transparent` ("Available") do NOT appear in `busy[]` at all. So the `events.list` fallback is needed mainly to distinguish `tentative` vs `confirmed` `status` and to reason about all-day events (which FreeBusy hides as opaque busy blocks), NOT to filter out transparent events. That makes the "allow overlap with a tentative/all-day event" motivation the accurate reason to drop to `events.list` + `transparency`/`status` inspection.

**Multi-user quota and OAuth model: 600 req/min/user, 10,000 req/min/project; event scopes are sensitive/restricted; per-user OAuth tokens are mandatory. [high]**
Default quotas: 600 requests/minute/user/project, 10,000/minute/project, 1,000,000/day/project (sliding-window; overage returns 403 or 429 `usageLimits`, handle with exponential backoff `min((2^n)+rand_ms, max_backoff)`). Projects created on/after 2026-05-01 get the new quotas; older active projects keep prior limits, with metered overage billing beginning later in 2026. Scopes: `calendar.events`, `calendar.events.owned`, `calendar.freebusy`, `calendar.readonly`, `calendar.app.created`, and full `calendar`. The event scopes are sensitive/restricted and trigger Google's OAuth verification (and possibly a security assessment) for a public multi-tenant app. Each tenant grants their own OAuth2 consent producing a per-user refresh token stored encrypted; incremental authorization (`include_granted_scopes=true`) lets you request calendar access only at the "add to calendar" step. Use the `quotaUser` param to spread project quota fairly across tenants.

**Timezone correctness requires IANA (Olson) zone ids; for recurring events `timeZone` is mandatory. [high, non-load-bearing]**
`EventDateTime.dateTime` is RFC3339; a UTC offset is required UNLESS `timeZone` is given. `timeZone` must be an IANA/Olson name (e.g. `America/New_York`), not a fixed offset — a fixed offset breaks across DST (an event stored `-05:00` in winter renders an hour off after the spring switch). For recurring events (`RRULE`) `timeZone` is REQUIRED so the server can expand occurrences. Always resolve each discovered event's venue/city to an IANA zone and set `start.timeZone`/`end.timeZone` explicitly.

**Homogeneous per-API Calendar batch is still available (the discontinued one was the GLOBAL cross-API batch endpoint). [medium, non-load-bearing]**
Google discontinued JSON-RPC and the global HTTP batch endpoint (`www.googleapis.com/batch`), but the Calendar API retains its own homogeneous batch for grouping multiple Calendar calls into one HTTP request — useful when one natural-language request yields several confirmed events, or when renewing many watch channels, staying within the 600/min/user budget. Batch is a transport optimization, NOT atomic — each sub-request succeeds/fails independently, so idempotent per-event ids remain necessary for safe retries.

### Other providers (adapter divergence)

**Microsoft Graph is the Outlook/Microsoft 365 path; delta query is the sync analog, with a hard 1,000-subscription-per-mailbox webhook ceiling. [high, non-load-bearing]**
Graph calendar sync uses delta query (`GET .../calendarView/delta` or `/events/delta`) returning `@odata.nextLink` during paging and `@odata.deltaLink` at the end (persist this delta token); any `$`-query params are set only on the initial request and baked into returned links. Change notifications come via subscriptions (webhooks) to a validated notification URL, capped at 1,000 active subscriptions per mailbox across all apps — a large multi-tenant fleet must budget/renew carefully. Timezone in the delta parameter value comes from its own offset and is NOT affected by the `Prefer: outlook.timezone` header; missing offset = UTC. The calendar port needs a distinct Graph adapter, not a reskin of the Google one.

**Apple/iCloud coverage is CalDAV-only (RFC 4791) with app-specific passwords and no OAuth — materially heavier, less automatable onboarding. [high, non-load-bearing]**
iCloud Calendar speaks only CalDAV at `caldav.icloud.com:443`, with NO OAuth and NO developer console. Clients authenticate with a 16-char app-specific password the user manually generates at `account.apple.com` — this step cannot be automated, so N users means N manual credential steps. Discovery is a two-request dance (`current-user-principal`, then `calendar-home-set`) landing on a per-account partition host (e.g. `p67-caldav.icloud.com`), so URLs cannot be hardcoded. A single time-range report is capped at 1 year. There is no `extendedProperties` equivalent — embed your source id in the iCalendar VEVENT (a custom `X-CONCIERGE-SOURCE` property or a deterministic `UID`) and match on it.

**Fuzzy secondary dedup is still needed for events the user already added themselves (no concierge source id). [medium, non-load-bearing]**
The primary dedup key is our own source id in `extendedProperties`, but a user may have manually added the same event, or two sources (Luma + Eventbrite) may list one physical event. Before insert, also `events.list` a window around the candidate start and compare: normalized/lowercased title similarity, start within a tolerance (e.g. +/-15 min to absorb source rounding), and location/venue token overlap. Treat a strong match as a merge (patch the existing event to add our source id + `reg_state`) rather than a new insert. Combined: id-hash catches exact same-source retries; fuzzy match catches cross-source and human duplicates.

## Design implications

- **Queryable dedup key.** On every calendar write set `extendedProperties.private.concierge_source='<source>:<sourceEventId>'` and `extendedProperties.private.reg_state` (`found`|`registered`|`scheduled_to_calendar`). Dedup = `events.list?privateExtendedProperty=concierge_source%3D...` before insert; lifecycle/reconciliation updates = `patch` on the same key. Keep keys <=44 chars and values <=1024; namespace prefixes must stay short. Remember dedup is per-calendar.

- **Idempotent writes as upsert.** Use a deterministic client-set event id = base32hex hash of `(tenant, source, sourceEventId)`. Insert; on HTTP 409 `duplicate` switch to `update`/`patch`. Because Google does not guarantee collision detection under concurrency/replication lag, back the 409 path with a defensive list-by-source-id reconciliation check so a slipped-through duplicate is caught on the next pass. This pairs with the money-moving idempotency in the registration step.

- **Mandatory pre-registration conflict gate.** Before any paid/irreversible RSVP, call `freeBusy` over the candidate window across all of the user's calendars; abort/deprioritize on overlap. This enforces the "never book two overlapping events" safety policy without an interactive prompt. When richer reasoning is required (permit overlap with a tentative or all-day event), drop to `events.list` and inspect `transparency`/`status`; do not use `events.list` merely to exclude transparent events, since FreeBusy already omits those.

- **One CalendarPort, multiple adapters.** `GoogleCalendarAdapter` (extendedProperties + syncToken + watch), `GraphCalendarAdapter` (deltaLink + subscriptions, 1000-sub/mailbox cap), `CalDAVAdapter` (Apple/iCloud, VEVENT `UID`/`X-` property for dedup, app-specific-password credential type). Dedup and conflict logic live in the domain layer; adapters only translate to provider primitives.

- **Webhook-triggered incremental sync, not polling.** Store a per-user-per-calendar `syncToken` (Google) / `deltaLink` (Graph); on a content-free push, list-with-token; handle HTTP 410 by full resync + token refresh. Schedule channel/subscription renewal jobs driven by the returned expiration timestamp (Google roughly weekly, no auto-renew), and persist `channel_id`/`resource_id`/`expiration` per user.

- **Per-user OAuth for tenant isolation.** Store each tenant's encrypted refresh token; request only the narrowest scopes (`calendar.events` + `calendar.freebusy`) via incremental authorization at the add-to-calendar step; budget the 600 req/min/user + 10,000/min/project quotas with exponential backoff and the `quotaUser` param. Plan for Google's sensitive-scope OAuth verification (and possible security assessment) before public launch.

- **Explicit IANA timezones.** Set `start.timeZone`/`end.timeZone` to an IANA zone id derived from the event venue/city (required for recurring events; correct across DST) rather than trusting bare UTC offsets from scraped sources.

- **Fuzzy secondary dedup layer.** On top of the id-based key, run normalized-title + start-within-~15-min + venue-token-overlap matching to absorb human-added and cross-source duplicates, resolving matches as a merge/patch that stamps our source id onto the pre-existing event.
